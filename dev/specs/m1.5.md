# M1.5 spec: undo

Transaction-based undo with exact marker and interval restoration, a branching history, and a
byte budget. The architecture rulings this spec implements were made by an architect pass on
2026-09-11 against four reconnaissance maps (the edit funnel, a GNU Emacs 30.2 oracle harvest,
Reticle's undo implementation, and this project's verification conventions); where this spec
disagrees with that pass it says so and gives the derivation.

## 0. What already exists, so it is not reinvented

- **The one edit funnel.** `BufferSnapshot.replaceSubrange(_ byteRange: Range<Int>, with other:
  Rope, insertBeforeMarkers: Bool = false)` (`Sources/Text/BufferSnapshot.swift:56`) applies the
  same `byteRange`/`insertedLength` pair to `text`, then `markers`, then `intervals`. The
  `String` overload (`:75`) forwards to it. Offsets are **byte** offsets on UTF-8 scalar
  boundaries. There is no other mutator, and M1.5 must not add one.
- **`BufferSnapshot` is a `Sendable` struct** (`:25`) of three persistent trees plus two private
  ID counters (`:29-30`). Taking a copy is O(1) and shares structure.
- **Marker key encoding**: `key = 2 * byteOffset + bias.rank`, `.left = 0`, `.right = 1`
  (`Sources/Text/MarkerTree.swift:5`). `markers(in byteRange:)` (`:262`) converts to `[2*lo,
  2*hi)` and so returns **both biases at every offset in `[lo, hi)` and nothing at `hi`**; its
  only precondition is a non-negative lower bound, so an upper bound past the end of the buffer
  is allowed and needs no clamp.
- **The delete rule for markers** (`MarkerTree.applyDeleteAndCollapse`, `:504`, and its doc
  comment): offset `<= lo` untouched; offset in `(lo, hi]` collapses to `lo` keeping its bias;
  offset `> hi` shifts by `-(hi-lo)`. The collapse group is widened to keys `[2*lo, 2*hi+1]` to
  keep the key order non-decreasing.
- **The insert rule for markers** (`MarkerTree.applyEdit`, `:429`): one gap edit at boundary
  `2*lo + 1`, or `2*lo` when `insertBeforeMarkers`, so a `.right` marker at `lo` advances and a
  `.left` marker at `lo` does not.
- **The delete rule for intervals** (`IntervalTree.applyDelete`, `:650`): straddlers (`start <=
  lo < end`) keep their start and lose the deleted portion of their length; starts in `[lo, hi)`
  collapse to `lo`; starts `>= hi` shift by `-(hi-lo)`. **Flag-independent**, oracle- verified
  across twenty combinations (`dev/specs/m1.4.md` 1.4).
- **The insert rule for intervals** (`IntervalTree.applyInsert`, `:837`): straddlers found with
  a **non-strict** `end >= p` prune gain the inserted length; the tie group at `p` is stably
  partitioned by `startMoves(item:p:insertBeforeMarkers:)` (`:1027`), which is `(frontAdvance ||
  ibm) && (length > 0 || rearAdvance || ibm)`.
- **Single-item primitives that exist and are what the restore uses**:
  `MarkerTree.inserting(byteOffset:bias:id:)` (`:295`), `MarkerTree.removing(id:atByteOffset:)`
  (`:326`), `IntervalTree.inserting(range:id:frontAdvance:rearAdvance:)` (`:402`),
  `IntervalTree.removing(id:startingAt:)` (`:442`). Each takes the position because identity
  lookup without it is O(n) — `PLAN.md` 4.5 gives identity resolution to M5.
- **`IntervalTree.visitEndAtOrAfterInclusive`'s prune**, `endAtOrAfterDescendPredicate(_ p:)`
  (`:821`), is the non-strict `prefix.span + subtree.maxEnd >= p` search. M1.5 reuses it; it is
  already `internal` so its tests can wrap the real function (M1.4's lesson that a test with a
  hand-copied predicate is blind to a mutation of the real one).
- **There is no `history`, no `clock`, no `version` and no owner object anywhere in
  `Sources/Text/`.** `PLAN.md` 4.5's `TextBuffer { root, overlays, history, clock }` is a
  sketch. `Sources/Editor/` holds only an inlining probe. There is no command loop (M5), no Lisp
  value (M2) and no point. M1.5 is a data-structure milestone.
- **Already promoted for cross-module inlining** (`dev/check-inlining.sh`): `SumTreeCursor`,
  `Node`, `Summary`, `Summable` are `@usableFromInline package`; `next`, `descendLeftmost`,
  `advanceToNextLeaf` are `@inlinable`. `Rope`, `MarkerTree`, `IntervalTree` and
  `BufferSnapshot` are plain `package`. M1.5 adds nothing to that list: no benchmark has shown a
  cross-module hot call here, and the rule in `CLAUDE.md` is that promotion follows a benchmark.

## 1. The design, and why

### 1.1 The representation: an edit log, and no retained snapshots

A `BufferSnapshot` is a value with O(1) copy, so "retain one per transaction" is a real
candidate and was measured, not dismissed. Retaining one costs **3637-6159 B** per transaction
across the measured fixtures — the low end 1 MB of text with no markers or intervals, the high
end 1 MB of text with 10k markers and 2k intervals; release build, file-scope global plus an
`@inline(never)` sink so the optimiser cannot delete the retention — against about **190 bytes**
for one log entry. A first draft of this sentence wrote the range as "3.8-6.2 KB" with only the
high end's fixture named, and a cold read against the source table found the low end is 3637 B,
not 3792; the rounded restatement is the failure this project's `CLAUDE.md` describes, so the
figures are given here exactly and once. and the decisive experiment — 1000 keystrokes at one
point, retaining every Nth state — measured **5941-5957 B per retained snapshot at every
spacing**, i.e. the cost is per retained state and independent of how many edits separate two of
them. The transient arm nets **0 bytes**: path-copy garbage is allocated and freed either way,
so retention costs memory and never CPU.

That ratio, 19-32x, is **not** the reason for the ruling. Two other things are:

1. **Restoring a snapshot rolls back object identity, which GNU undo never does.** A wholesale
   restore also un-creates every marker and interval created since that state. GNU does not:
   markers are repositioned by `(MARKER . DISTANCE)` rather than resurrected, and overlays are
   not recorded at all. That second half was an inference from the docstring's enumerated shapes
   until a review round found the two reconnaissance maps contradicting each other about it, so
   it was settled directly —

   ```
   $ emacs -Q --batch --eval '(let ((buf (generate-new-buffer "probe")))
       (with-current-buffer buf (insert "hello world") (undo-boundary)
         (let ((o (make-overlay 2 5))) (overlay-put o (quote face) (quote bold))
           (delete-overlay o) (prin1 buffer-undo-list) (terpri))
         (put-text-property 2 5 (quote face) (quote italic)) (prin1 buffer-undo-list)))'
   (nil (1 . 12) (t . 0))
   ((nil face nil 2 . 5) nil (1 . 12) (t . 0))
   ```

   `make-overlay`, `overlay-put` and `delete-overlay` together add **nothing**;
   `put-text-property` adds `(nil face nil 2 . 5)`. The contradiction was
   `recon-reticle-undo.md` conflating that text-property entry with an overlay entry, and it is
   reconciled here rather than left standing. From M2 onward every font-lock, tree-sitter and
   LSP-diagnostic overlay is created continuously by idle machinery; under a restore design each
   one created after the restored state would hold an ID that no longer exists in the tree — a
   dangling-handle class GNU has no equivalent of, manufactured by the undo mechanism itself.
2. **`undo-in-region` cannot exist over whole-buffer snapshots.** The oracle reproduced it in
   batch mode (recon section 7): it selects the entries falling inside the region and applies
   only those. Choosing snapshots now would be choosing against that feature permanently.

**Sparse checkpoints are declined, with the cost recorded.** A checkpoint buys a shorter replay,
and replay is O(d) forward edits at the per-edit costs 4.5's rope rows already carry, so walking
back 1000 transactions is single-digit milliseconds with no checkpoint at all. A checkpoint also
reintroduces argument 1 the moment it is *restored* rather than replayed from.

**Declined, with the number so it is not re-derived**: storing short deleted text inline
(`InlineArray<24, UInt8>` plus a count) instead of a `Rope` would cut a single-character entry
from ~190 B to under 100 B, because the 190 B is mostly the separate heap allocation a one-byte
`Rope` makes. One representation in M1.5; at 190 B the 2 MB budget of 1.9 already holds about
11,000 transactions.

**Where snapshots still earn their keep: as the test oracle** (4.1).

### 1.2 The transaction and the elementary edit

A **transaction** is an ordered list of **elementary edits**, each one exactly one funnel call.
Undoing a transaction applies the inverse of its elementary edits **newest first**; redoing
applies them oldest first. Reticle M72 is the incident that makes the order load-bearing: a
later edit's coordinates are expressed in the buffer state the earlier ones produced, so
applying the inverses in the wrong order corrupts text at the second offset onward, silently.

An elementary edit record holds:

```swift
struct ElementaryEdit: Sendable {
    let byteRange: Range<Int>     // the range replaced, in pre-edit coordinates
    let deleted: Rope             // what was there (a slice; structural sharing)
    let inserted: Rope            // what replaced it (a slice of the post-edit text)
    var markerEntries: [MarkerEntry]      // 1.3
    var intervalEntries: [IntervalEntry]  // 1.3
}
```

`deleted` holds the pre-edit nodes alive, which is the real memory cost and is what the budget
(1.9) counts. `inserted` shares with the live text and is free while that text stands.

**`insertBeforeMarkers` is deliberately not a field.** 1.5 proves it is unobservable during
replay, and `BufferSnapshot.swift:18` already states this project's rule that an unread field is
a standing chance to be wrong. 4.2's test 14 is the guard on the proof.

### 1.3 The entry set, derived

This is the spine of the milestone, so it is derived here case by case rather than cited. Write
`d = hi - lo` for the deleted length and `L` for the inserted length, so the edit is `replace
[lo, hi) with L bytes` and its inverse is `replace [lo, lo+L) with the d original bytes`.

**Markers.** Under 0's two rules, compose the forward delete, the forward insert, and then the
inverse pair, for a marker at pre-edit offset `p` with bias `b`:

| pre-edit `p` | after forward edit | after inverse edit | correct? |
|---|---|---|---|
| `p < lo` | `p` | `p` | ✓ |
| `p == lo`, `b == .left` | `lo` (key `2*lo`, below the inverse edit's boundary `2*lo + 1`) | `lo` | ✓ |
| `p == lo`, `b == .right` | `lo + L` | `lo + d == hi` | **✗** |
| `lo < p < hi` | `lo` or `lo + L` by bias | `lo` or `hi` by bias | **✗** |
| `p == hi`, `b == .left` | collapses to `lo` | `lo` | **✗** |
| `p == hi`, `b == .right` | collapses to `lo`, then `lo + L` | `hi` | ✓ |
| `p > hi` | `p - d + L` | `p` | ✓ |

Two of the four endpoint rows are wrong and the trap is row 3: **a marker the deletion does not
move at all is moved wrongly by the deletion's inverse.** Row 5 is its mirror. Rows 2 and 6 come
back correctly, and they are recorded anyway, because including them costs nothing and removes a
bias-dependent special case from the entry rule.

So the marker entry set is **every marker whose pre-edit offset lies in the closed `[lo, hi]`**,
and since `markers(in:)` is half-open on keys the query is `markers(in: lo..<(hi + 1))`, which
spans keys `[2*lo, 2*hi + 2)` — exactly offsets `lo` through `hi`, both biases. **No clamp to
the buffer end is needed** (0: the only precondition is on the lower bound). The off-by-one is
mutation 1.

**Intervals.** The same composition on 0's interval rules, for an interval `[s, e)`:

| pre-edit | after forward edit | after inverse edit | correct? |
|---|---|---|---|
| `e < lo` | unchanged | unchanged | ✓ |
| `s < lo`, `e == lo` | unchanged by the delete (not a straddler: needs `e > lo`), then `length += L` iff `rearAdvance` | net `length += d` iff `rearAdvance` | **✗ when `rearAdvance`** |
| `s < lo < e <= hi` | `length -= (e - lo)`, then `+= L` iff `rearAdvance` | recovers `e` only with `rearAdvance` | **✗ unless `e == hi` *and* `rearAdvance`** |
| `s < lo`, `e > hi` | `length -= d` | `length += d` | ✓ |
| `s` in `[lo, hi)` | `s -> lo`, length cut | `s -> lo` or `hi` by `startMoves` | **✗** |
| `s == hi` | `s -> lo` | `s -> lo` or `hi` by `startMoves` | **✗ unless `startMoves`** |
| `s > hi` | `s - d + L` | `s` | ✓ |

Rows 2 and 3 were both recorded more loosely in an earlier draft — row 2's net error as `+L`
rather than `+d`, and row 3's exception as `e == hi` without its `rearAdvance` conjunct — and a
review round traced both through `applyDelete` and `applyInsert` with concrete offsets. Neither
changes the entry set: both rows have `end >= lo` before the edit, so the flag-independent end
search takes them unconditionally.

So the interval entry set is **every interval with an endpoint in the closed `[lo, hi]`**. Row 2
is why **the architect pass's suggested conservative query, `intervals(overlapping:
lo..<(hi+1))`, is not a correct superset**: an interval ending exactly at `lo` shares no
character with that range, so the query omits it, and it is precisely the row that needs an
entry. The query is instead two-part, and both parts already exist:

- **Starts in `[lo, hi]`** — a rank range, `rank(startAtOrAfter: lo)` up to
  `rank(startAtOrAfter: hi + 1)` exclusive, one descent plus O(k) cursor steps.
- **Ends at or after `lo` among intervals starting before `lo`** — the non-strict
  `visitEndAtOrAfterInclusive(upperRankExclusive: rank(startAtOrAfter: lo), p: lo)` that
  `applyInsert` already uses. This is a **superset** of rows 2-4: it also returns row 4's
  containers, which need no entry. That is deliberate; see 1.4 on why a superset is the safe
  direction. Its cost carries the same `e` term 4.5's insert row already names.

**A correction to M1.4's doc comment, found while deriving this.** `IntervalTree.applyDelete`'s
straddler comment (`:654-659`) asserts that an interval starting exactly at `lo` with `end > lo`
"is a straddler too, by this same predicate ... so it must not also be picked up by the collapse
group below". Both halves mislead. `rank(startAtOrAfter: lo)` (`:241`) returns the rank of the
first item whose start is `>= lo`, and the straddler walk is restricted to ranks strictly below
it, so a start-at-`lo` item is **excluded from the straddler stage** and the collapse group is
its only handler — which is exactly why its length is cut once rather than twice. The code is
correct; the comment's stated reason ("straddlers are handled first, against the original tree")
does not establish what it claims. Fix the comment (deliverable H).

### 1.4 Applying a traversal: take the irreversible items out

The mechanism follows from 1.3 in one move. The items in the entry set are exactly the ones the
funnel's rules handle irreversibly; so **remove them from the trees, let the funnel apply the
text replacement, and put them back at their recorded positions.** Every item left in the tree
during the replacement is, by 1.3's tables, one the rules restore correctly.

Each entry therefore records the position the item held **both before and after** the live edit
— two queries at edit time, both O(log n + k):

```swift
struct MarkerEntry: Sendable { let id: MarkerID; let bias: MarkerBias
                               let beforeOffset: Int; let afterOffset: Int }
struct IntervalEntry: Sendable { let id: IntervalID
                                 let beforeStart: Int; let beforeLength: Int
                                 let afterStart: Int; let afterLength: Int }
```

Bias and the two advance flags never change under any edit, so they are not part of the
before/after pair; bias is carried because re-inserting a marker needs it.

A traversal of an elementary edit is then four steps, and the two directions differ only in
which stored position they read:

1. Remove every entry's item from its tree, at the position stored for **this** direction
   (`afterOffset`/`afterStart` when undoing, `beforeOffset`/`beforeStart` when redoing). An id
   that is not present is **skipped, not a trap** — marker and interval *removal* is not
   undoable (3), so a branch walked after the user deleted one of these markers must not crash.
   **The existing API cannot express that skip**: both `MarkerTree.removing(id:atByteOffset:)`
   (`MarkerTree.swift:334-335`) and `IntervalTree.removing(id:startingAt:)`
   (`IntervalTree.swift:465`) end in `preconditionFailure` when the id is absent. Deliverable E
   therefore adds `removingIfPresent` to each, returning `nil` instead of trapping, with the
   existing `removing` reduced to that call plus the trap — **one search implementation, not
   two**, which is M1.4's lesson about a second hand-written copy of a predicate drifting from
   the real one.
2. Apply the text replacement through `BufferSnapshot.replaceSubrange` — the one funnel, with no
   new entry point and no second code path.
3. Re-insert every entry's item at the position stored for the **opposite** direction, iterating
   the entry list **in reverse**. The reverse is load-bearing and a review round found the draft
   silent about it: `MarkerTree.inserting` places a new key *before* the first item whose key is
   greater than or equal to it (`MarkerTree.swift:295-318`), so inserting a tie group
   front-to-back reverses it — `[A, B]` becomes `[B, A]`. `IntervalTree.inserting`
   (`IntervalTree.swift:406-407`) splits at `rank(startAtOrAfter:)` and prepends to the tie
   group the same way, so the rule covers both trees; a review round checked that half
   separately, because the derivation above is written on the marker rule. Reverse iteration
   restores the original order exactly, since each insertion prepends to the group built so far.
   The whole tie group is always inside the entry set (the set holds *every* marker at *every*
   offset in `[lo, hi]`), so reversing the list reconstructs each group in full rather than
   interleaving with survivors. M1.3 wrote a tie-order stability test precisely because this
   order is observable; without this clause every traversal would silently reverse it, and 4.1's
   naive model — a list of `(id, offset, bias)` — would not see it.
4. Collect the applied replacement into the traversal's return value (1.6).

The **live** edit does none of this: it queries the entry set before, applies the funnel
normally, queries again after, and stores both. Replay restores; a live edit must not.

**Why the positions cannot go stale.** To traverse an edge a second time you must first return
to the node it leaves from, which means undoing everything done since, which restores the
positions. The history is a deterministic tree, so each edge's two position lists describe the
only two states its endpoints can be in. The one thing that breaks the pairing — the user
removing one of those markers while on another branch — is step 1's skip.

**The two queries return the same id set, and that is a testable invariant, not an assumption.**
Post-edit, a marker from the entry set sits at `lo` or `lo + L` and nothing else can: offsets `<
lo` are untouched and offsets `> hi` map to `p - d + L > lo + L`. So the after-query is the same
shape one zone over, `markers(in: lo..<(lo + L + 1))`, and it returns exactly the before set.
The same argument on the interval rules gives the same conclusion for the two-part search at
`[lo, lo + L]`. Test 13 asserts the equality of the id sets; mutations 1 and 9 narrow one query
each and are killed by it.

### 1.5 `insertBeforeMarkers` is unobservable during replay, and therefore not stored

Every item whose behaviour depends on the flag is in the entry set: a marker at the insertion
point `lo` (both biases are in `[lo, hi]`), an interval with `start == lo` (in `[lo, hi]`), and
an interval with `end == lo` (returned by the non-strict end search). By 1.4 step 1 all of them
are out of the tree while the replacement is applied, and by step 3 their positions come from
the record rather than from the rules. So neither direction of a traversal can observe the flag,
and storing it would store a field with no reader. Test 14 is the guard: a transaction recorded
with `insertBeforeMarkers: true` and one recorded with `false`, undone and redone, must produce
identical trees.

### 1.6 The history: a flat array, with branches native

```swift
struct UndoHistory: Sendable {
    private var nodes: [Node]            // append-only, creation order, never reordered
    private(set) var current: Int32      // the node whose state the buffer is in
    struct Node: Sendable {
        var parent: Int32                // -1 for a root (see 1.9 on re-rooting)
        var firstChild: Int32            // -1 when none
        var nextSibling: Int32           // -1 when none
        var lastVisitedChild: Int32      // -1 until a child is created or redone into
        var edits: [ElementaryEdit]      // the edge from `parent` to here
        var byteCost: Int                // 1.9
    }
}
```

**First-child/next-sibling, not a `children: [Int32]` array.** A per-node array allocates a heap
buffer for every node, including the overwhelmingly common single-child one, at 32-48 bytes of
malloc header and capacity on top of the four bytes it carries; at 1.9's 11,000-transaction
budget that is hundreds of kilobytes that the budget does not count and that a linear history
pays for a feature it never uses. Two `Int32` fields cost nothing, make `Node` a **fixed-size
struct**, which is what the release argument in property 2 below actually needs, and make
enumerating a node's children O(k) — not a hot path. A review round measured the array's cost
and this structure replaced it.

`recordTransaction` appends the new node, links it as a child, **and sets the parent's
`lastVisitedChild` to it** — so a fresh edit is the branch a subsequent redo prefers, which is
what makes "edit, undo, redo" return to the edit just made.

Undo moves `current` to `parent`, applying that node's `edits` backward. Redo moves to
`lastVisitedChild`, applying them forward. A new edit while `current` already has children
appends a sibling. **No code path differs between the one-child and the many-child case**, which
is the whole cost of branching: one array and one `Int32` per node.

**Branching is the cheaper option, not the expensive one.** GNU's linear model records an undo
as a new edit, so undoing N transactions appends N transactions' worth of inverse entries and
the history grows on undo. A cursor move appends nothing. The thing branching is assumed to cost
— keeping states alive — is not a cost here, because 1.1 keeps no states.

Three properties this representation buys, each load-bearing and each free:

1. **Creation order in a flat array makes GNU's linear `buffer-undo-list` a derivable view.**
   Array order is the order GNU would have pushed entries in; `undo-only` is the parent walk,
   `undo-redo` is the `lastVisitedChild` walk, and GNU's `last-command`-sensitive `undo` is a
   walk in array order. The reverse derivation — recovering which branch you are on from a
   linearised log — is the one that is *not* available, which is why this direction is chosen.
   M1.5 commits to no key binding and no command semantics; it guarantees both are expressible.
   The one behavioural difference to be explicit about: with a cursor, `undo` after `undo,
   other, undo` continues backward (GNU's `undo-only`) where GNU's `undo` would redo. That is a
   command-layer choice and it belongs to M5, which has `last-command`.
2. **Indices, not object references, means there is no chain to tear down.** `CLAUDE.md`'s "long
   chains are torn down iteratively" rule exists because releasing a 1M-node linear chain
   recursively segfaults on this machine, measured. A `class Node { var next: Node? }` history
   walks straight into it; a flat array of structs releases in one pass. **This is the most
   important representation decision in M1.5 and it has nothing to do with branching.**
3. **A pruning policy is expressible over it without touching this structure** — the payload
   primitives and the cost accounting are 1.9's, and the policy itself is stage 2's.

**Traversal is observable**, which is how `Text` stays independent of `Lisp` without an escape
hatch: `undo()` and `redo()` return the traversed node id and the ordered list of replacements
actually applied. M5 keeps a side table keyed by node id for GNU's `(apply FUN . ARGS)` entries,
which is semantically what they are — an action attached to a position in the log. The return
value has a reader in M1.5 (tests 11 and 12) and Reticle proved it is needed: M72's silent
multi-window point corruption was caused by its undo step returning too little to reconstruct a
multi-edit group, and the fix widened exactly this return type.

### 1.7 Grouping: open and commit, no policy, no timer, no clock

**The 300 ms window in `PLAN.md` 4.5 is deleted, not deferred.** The oracle is unambiguous: GNU
groups by **command identity** plus a count (`amalgamating-undo-limit`, default 20) plus a fixed
**10-second** safety-net timer whose idle slot is `nil`. There is no millisecond window anywhere
in GNU, and Reticle used a consecutive-character count of 20. The 300 ms figure is pellicle's
own invention recorded as though it were a ported design; a spec citing it would be citing
nothing.

M1.5 ships the mechanism and no policy: an **implicit open transaction**, held in
`TextBuffer.pendingEdits`, which the first edit after a commit starts; and
**`commitTransaction()`, idempotent** — with `pendingEdits` empty it is a no-op, appending no
node. No command identity, no counter, no timer, no `amalgamateWithPrevious()` that nothing
calls.

**`undo()` and `redo()` commit the pending transaction first.** Otherwise typing three
characters and immediately undoing would undo nothing, because the transaction holding them was
never closed — and that is the first thing a user does. The commit is the same idempotent call,
so there is no second path. A review round found this semantics unstated; test 1 exercises both
the committed and the uncommitted entry.

**Do not port GNU's retroactive boundary removal.** What the oracle establishes is the
*removal*: `undo-auto-amalgamate`'s docstring, verbatim, is "It removes the previous
'undo-boundary' if a series of such calls have been made", and the function is not on the global
`post-command-hook` — an amalgamating command calls it itself. What the oracle does **not**
establish is the other half, that a boundary is stamped at the end of every command:
`recon-gnu-undo.md` section 2 lists that under what batch mode cannot observe, because batch
mode has no command loop. The argument below needs only the verified half, and an earlier draft
of this paragraph asserted the unverified half as fact — the same failure this spec's section 3
avoids for `(apply ...)`. Reticle needed a matching one-shot `suppress_next_undo_boundary`,
which then needed `C-g` clearing on two paths after a review round found it leaking forward onto
an unrelated later insertion. With open/commit, M5's loop decides at the **start** of a command,
where it already knows `this-command`, and an amalgamating command simply does not commit.
Observationally equivalent for every command GNU names as amalgamating, and the leak-forward
mode is gone by construction. Evil-style compound commands, electric pairs and completion
acceptance all become "do not commit in the middle", with no flag.

**The 10-second safety net is M5's**, because it needs a run loop, and `CLAUDE.md` requires
every timer to carry a tolerance. Build nothing now.

**No `clock` and no `version` field, and this is evidence rather than inheritance.** The
handover names M1.5 as the first milestone that might need one. It does not, and the four
candidate readers were each checked: undo needs no "is this snapshot current" comparison,
because `TextBuffer`'s class invariant is that its snapshot *is* the state at `current`, so the
two cannot disagree; the history already has a version, namely `current`; a change-group handle
does need a generation counter so a pruned history invalidates it instead of resolving to the
wrong node, but change groups are `atomic-change-group`, i.e. Lisp, i.e. M5; and "is this
snapshot still current" for a background reader is M4/M10's, and belongs on the snapshot, added
with that consumer. This analysis goes into the milestone record so the next milestone that
reaches for a clock does not re-derive which reader it is.

### 1.8 The owner, and where IDs come from

**`Sources/Text/TextBuffer.swift`, `final class TextBuffer`, not `Sendable`.** It holds
`private(set) var snapshot: BufferSnapshot`, `private(set) var history: UndoHistory`,
`private(set) var pendingEdits: [ElementaryEdit]` — the open transaction, which is where 1.7's
"implicit open transaction" actually lives and which a review round found the earlier draft had
nowhere to put — `var isRecordingUndo: Bool`, `var undoByteBudget: Int`, and the two ID
counters. It owns the edit entry points; `BufferSnapshot.replaceSubrange` stays the funnel and
`TextBuffer` becomes the only production caller. A class because undo is inherently a thing that
changes over time, because 4.5 already sketches `TextBuffer` as a class, because M5's Elisp
buffer object needs a stable identity to map onto, and because a value owner forces `inout`
through every command in the stack. The `Sendable` boundary does not move: `BufferSnapshot` is
still the value handed to the UI and to background readers, which is the existing rule that the
UI actor never touches a buffer.

**`Sources/Text/UndoHistory.swift`, `struct UndoHistory: Sendable`** — no identity needed, and a
value is trivially comparable and copyable in tests. `Text` and not `Editor` because M1.5 needs
nothing from `Lisp`, because keeping the owner next to the funnel keeps the no-desync invariant
in one file, and because the marker and interval naive models already live in `Tests/TextTests`.

**The ID counters move to `TextBuffer`, and the fork that worried M1.3 and M1.4 never happens.**
Under 1.1 there is exactly one live `BufferSnapshot` and an undo walks it *forward* through the
funnel; a sibling branch is a set of recorded edges, not a materialised state. The scenario the
three source comments name — fork one snapshot, edit both halves, watch the IDs collide — is not
something undo does. An undone-then-redone history never reissues an ID either, because neither
GNU nor pellicle logs marker or interval *creation*: a collapse moves a record, it does not
remove it. The hazard is real but it comes from elsewhere — `BufferSnapshot` is a value, so any
background holder that edits its own copy allocates from its own counter. So:

1. `nextMarkerID`/`nextIntervalID` leave `BufferSnapshot` and live on `TextBuffer`: one counter
   per buffer, on the one object with identity.
2. `BufferSnapshot.createMarker(id:atByteOffset:bias:)` and
   `createInterval(id:byteRange:frontAdvance:rearAdvance:)` take the id. Allocation is the
   owner's; insertion and the scalar-boundary preconditions stay the snapshot's.
3. `BufferSnapshot` keeps a **high-water pair it can only raise**, and each creator
   preconditions `id > highWater`. A silent collision becomes a trap, which is what the M1.3 and
   M1.4 standing-risk notes asked for. The field has a reader — the precondition — so it does
   not violate 1.2's no-unread-field rule.
4. **There is no initialiser that builds a `TextBuffer` around an existing `BufferSnapshot`.**
   That closes the remaining hole: two owners over one ancestor snapshot would each initialise a
   counter from the same high-water mark and collide. `TextBuffer` is constructed empty or from
   text with no markers — the same reasoning `BufferSnapshot.swift:40-46` already uses to refuse
   `init(text:markers:)`. When M1.6 needs "a buffer restored from a file with markers", that
   initialiser takes the high-water mark explicitly and validates it.

Rejected: a reference-typed shared allocator inside the snapshot (an `Atomic<UInt64>` in a
`final class`). It works and would make even the fork-and-edit case safe, but it puts mutable
shared state inside a type whose whole contract is that it is a value — copying a snapshot and
creating a marker in the copy would advance the original's counter — in exchange for protecting
a case ruling 4 already forbids. Rejected: random 64-bit IDs, because `MarkerID`'s contract is
documented monotone and never reused, `dev/specs/m1.3.md` section 3's M5 argument leans on
ordering, and "overwhelmingly probable" is not accepted where an exact answer is free.

### 1.9 The byte budget, and what stage 2 owns

GNU's measured defaults (`undo-limit` 160000, `undo-strong-limit` 240000, `undo-outer-limit`
`nil` under `-Q --batch`) are byte counts over GNU's cons-cell encoding and are **not
comparable** to pellicle's entries, so the number is not copied. Pellicle's arithmetic from the
measurement: a single-character transaction costs about 190 B, so **2 MB per buffer holds
roughly 11,000 transactions**, which no hand-driven session reaches.

**The detailed pruning policy is deferred to `dev/specs/m1.5-stage2.md`, written when stage 1
lands, and this is a decision rather than an omission.** Four consecutive cold reviews each
found a real defect in the previous round's repair of this one section, and every one of them
was here rather than anywhere else in this spec: the first draft's `byteCost` formula omitted
two unbounded terms; its replacement expressed the root-end drop as pruning "an edge, not a
node", which reconciled two rules by making the only memory-freeing path free no memory; *that*
repair left the promoted root's own payload uncollectable and `canUndo` ambiguous between two
kinds of root; and *that* repair stated the tombstone link rule generally enough to clear a
promoted root's `firstChild` and cut the live tree loose. Each fix was correct about the defect
it addressed. The pattern is the tell: this is the one part of M1.5 with **no oracle, no
measurement and no precedent in the tree** to check a draft against — GNU's policy is not
portable (its limits are checked at GC time over its own cons encoding), Reticle's is a
hardcoded entry count this spec already rejects, and there is no structure to run a mutation
against until stage 1 exists. Prose is the wrong instrument for it, and four rounds of evidence
say so. `m1.1b-stage2.md` is the precedent for a second spec at a stage boundary.

**What stage 2 inherits as settled, because it has evidence behind it.**

- **The `byteCost` formula**: `deleted.utf8Count + inserted.utf8Count + markerEntries.count *
  MemoryLayout<MarkerEntry>.stride + intervalEntries.count *
  MemoryLayout<IntervalEntry>.stride`, plus a fixed per-node constant. Two review rounds
  established both of the terms an earlier draft omitted. The adjustment entries' count is the
  marker and interval count at the edit's endpoints — unrelated to the deleted byte count and
  unbounded, and 1.1's own argument about idle machinery creating overlays from M2 on is exactly
  what makes it dense. `inserted` shares with the live text only while its node is on the path
  to `current`; undo back past a large paste, edit on a new branch, and the abandoned node is
  that text's sole owner. Counting `inserted` overstates nodes on the live path, deliberately:
  the budget is a **cap**, and a cap whose error is toward pruning sooner is the safe direction.
- **The formula's known error, with its direction and size.** `Rope.slice` does **not** retain
  more than it needs — a review round checked `Rope.swift:565-598` and `Chunk.swift:19` and
  found that a mid-chunk cut copies the sub-range rather than sharing the whole leaf — but a
  retained slice still pays each `Chunk`'s fixed 64-80 bytes whatever its fill, plus 72 bytes
  per `Node<Chunk>`, so a large multi-chunk deletion retains roughly 20-40% more than
  `deleted.utf8Count`. The estimate undercounts large deletions by about that much. Recorded
  rather than papered over with a fudge factor.
- **GNU's one promise worth keeping**: `undo-strong-limit`'s docstring undertakes that the most
  recent modifying command's information is never discarded. Whatever policy stage 2 writes,
  that holds.
- **Not GNU's GC-time checking, deliberately.** GNU checks at garbage-collection time because
  its undo list lives in its GC heap; pellicle's does not. A deliberate deviation, recorded here
  so stage 2 does not rediscover it as a choice.
- **Reticle's counter-example**: a hardcoded "at 10,001 entries drop the oldest 5,000" has no
  budget in bytes, so one large kill can hold megabytes while a thousand keystrokes hold
  nothing.
- **The multi-buffer ceiling, recorded rather than solved**: 2 MB x 50 open buffers is a 100 MB
  worst case, and a worst case rather than a typical one because the budget caps retained
  *deleted* text. A global cap across buffers needs a soak measurement that does not exist yet.

**What stage 1 must build now, so that stage 2 is not blocked by the data structure.** These are
structural, not policy, and they are what the four rounds did settle:

- **`byteCost` is computed and stored per node** by the formula above, and `UndoHistory` keeps a
  **running total**, maintained by each release rather than recomputed by a sweep. Stage 1 ships
  the field, the total and test 19; it enforces no budget.
- **Two operations on a node's payload, named apart, because conflating them disconnects the
  tree.** A **tombstone** leaves the reachable graph: its `parent`, `firstChild` and
  `nextSibling` all become `-1`, whoever pointed at it is repaired, and every `lastVisitedChild`
  aimed at it is reset to `-1`, so `children(of:)` on the slot returns nothing rather than a
  live-looking list and a stale index cannot be walked outward from either end. A **promote**
  keeps the node in the graph and discards only its incoming edge: `parent = -1`, `edits = []`,
  `nextSibling = -1`, and **`firstChild` is kept**. A review round found a draft that called
  both "pruned" and stated the tombstone rule generally, which read literally cuts `current`
  loose from its root. Stage 1 implements both primitives and tests them directly; stage 2
  decides when to call them.
- **A subtree is tombstoned leaves-first**, the worklist walking it in full before any link is
  cleared, so the walk cannot lose the nodes it has not reached yet. **The walk is an explicit
  worklist, never recursion**: an undo tree is not height-logarithmic — a linear history is a
  chain as deep as the transaction count, and abandoning a branch after a few thousand undos is
  ordinary use — and `CLAUDE.md`'s "long chains are torn down iteratively" rule exists because
  recursion over a 1M-node chain segfaults on this machine, measured.
- **The invariant that makes `canUndo` a one-liner**: `edits.isEmpty` holds exactly when `parent
  == -1`. No node is ever created empty, because `commitTransaction()` appends nothing when
  `pendingEdits` is empty; and all three ways a node becomes empty — the genesis node, a
  promotion, a tombstone — set `parent = -1`. So `canUndo` is `nodes[current].parent != -1` with
  no second case, and `UndoHistory.checkInvariants()` asserts the equivalence on every node, on
  `MarkerTree`/`IntervalTree`'s precedent of checking structural invariants rather than trusting
  them. **Stage 2 owns the cadence question**: promote and tombstone overwrite the three link
  fields unconditionally, so a sparse check can miss a violation a later operation overwrites —
  the same class M1.4 recorded and declined with a stated reason. In stage 1 the only empty node
  is the genesis node, so the invariant is trivially maintained and a per-edit check in the
  differential test is enough.
- **Index stability**: `nodes` is append-only and every `Int32` indexes into it; a released slot
  is reclaimed only by `discardHistory()`. Compacting the array needs node ids that survive
  renumbering, i.e. the generation counter 1.7 already assigns to M5 with its first real caller.
  A tombstone is a fixed-size `Node` with its payload released, so the residue is bounded by the
  transactions since the last discard; section 8 carries it.

## 4. Tests

`Tests/TextTests/undoTests.swift` and `Tests/TextTests/undoPerfTests.swift`, the latter tagged
`.performance` exactly as the three existing perf files are.

### 4.1 The differential property test, and its oracle

The one test that can catch an **incomplete** entry set — the single failure mode this
representation has and a retained-snapshot design does not. A random walk of edits, marker and
interval creations, commits, undos and redos against a naive model: `[UInt8]` text, `[(id,
offset, bias)]`, `[(id, start, length, frontAdvance, rearAdvance)]`, **and a retained real
`BufferSnapshot` for every state the walk visits**. Undoing back to a visited state must
reproduce that snapshot exactly — text, every marker's offset and bias, every interval's start,
length and flags — and **compared as a sequence in rank order, not as a set**, so that the tie
order of 1.4 step 3 is covered by the oracle rather than by a rule restated in the model. The
retained snapshot is correct by construction, costs about 6 KB per visited state in a test
process, and is the reason the naive model does not have to encode the edit rules a second time.

**Two tiers, per this project's convention and for the reason it records.** About 20,000
operations verified every step in the default `swift test`; 1,000,000 operations verified
sparsely in the perf-gated suite, **which belongs to stage 2**, so that pruning exists to bound
the history it builds. A review round did the arithmetic the draft omitted: retaining a snapshot
for *every* visited state at the default tier is about 120 MB live in a debug test process, so
"every state the walk visits" is bounded to a **sliding window of the 64 most recent visited
states** — enough that an undo chain reaching back through dozens of transactions is checked
against a real snapshot, and about 400 KB rather than 120 MB. `markerTreeTests.swift:725-746`
records a million-operation per-step-verified differential being killed after 12+ minutes of CPU
in debug — do not put one in the default run. Seeds fixed and printed on failure, as the
existing differentials do.

### 4.2 Correctness tests

1. **Undo a pure insertion**, redo it, undo again. Text and both trees exact at each state. Run
   it twice, **once committing before the undo and once not**, since 1.7 has `undo()` commit the
   pending transaction itself; a review round found 1.7 claiming this test covered both entries
   while the test said nothing about either.
2. **Undo a pure deletion** that contains markers strictly inside it; every marker returns to
   its exact original offset and bias. The M1.3 collapse is visible before the undo and gone
   after.
3. **The row-3 trap**: a marker at `lo` with bias `.right`, deletion of `[lo, hi)`, undo. It
   must be at `lo`, not `hi`. Without its entry the inverse insert moves it.
4. **The row-5 mirror**: a marker at `hi` with bias `.left`, under a **deletion** of `[lo, hi)`
   with `lo < hi`. It must return to `hi`, not stay at `lo`. The deletion is fixture, not
   scenery: at `lo == hi` rows 2 and 5 collapse together and mutation 1 becomes unobservable.
5. **Rows 2 and 6** (`lo`/`.left` and `hi`/`.right`), which the inverse edit would restore
   correctly anyway — asserted so that a later narrowing of the entry set to "only the rows that
   need it" is a visible change in behaviour rather than a silent one.
6. **Interval row 2**: an interval ending exactly at `lo` with `rearAdvance`. Undo must leave
   its length unchanged. This is the row the `intervals(overlapping:)` query would have missed.
   **The fixture must not put an interval with a larger end in the same leaf as the target**:
   the non-strict prune decides on each node's local `maxEnd`, which folds in every item sharing
   that leaf, so a neighbour reaching further right makes mutation 5 invisible. Use the isolated
   fixture shape of `intervalTreeTests.swift:31-37`, not test 7's bundled one.
7. **Interval rows 3, 5, 6**: a straddler ending inside the range, a start inside the range, a
   start exactly at `hi`, each with the flag combinations that make `startMoves` true and false.
8. **A replace** (both `d > 0` and `L > 0`) with markers and intervals on every endpoint, undone
   and redone.
9. **A multi-edit transaction at two different offsets**, undone — and **the spatially earlier
   edit must change the buffer's length**. A review round built the counterexample that makes
   this clause load-bearing: "replace `[2,5)` with three bytes" followed by "insert two bytes at
   7" gives the *identical* final text whether the inverses run newest-first or oldest-first,
   because a length-preserving left edit shifts nothing, so no coordinate is ever used against
   the wrong state; markers outside both ranges do not rescue it either. This is Reticle M72's
   shape and the only test that can see mutation 3 — but only with a length-changing left edit.
10. **Commit grouping on a non-empty history**: two edits, commit, two more edits, commit, then
    undo twice and assert the grouping **and `history.nodeCount`**. The node count is what makes
    mutation 6 visible: whether a spurious unconditional append shows up in the text at all
    depends on whether it moves `current`, which is an implementation detail a test must not
    lean on. Reticle M83's trailing review is where this was found, and the lesson is that a
    grouping test starting from a fresh buffer is structurally blind, because the boundary under
    test is a no-op there.
11. **Branching**: edit A, undo, edit B, assert two children, redo-into-B semantics, then
    navigate back to A's branch and assert A's text is reachable and exact.
12. **The traversal return value**: the applied replacements of an undo are the inverses of the
    transaction's edits, newest first, with absolute ranges. Asserted explicitly, because
    without it 1.6's forward-compatibility argument is unguarded (mutation 8).
13. **The two queries return the same id set** (1.4), over a fixture with markers and intervals
    on every endpoint of the edit.
13b. **Tie order survives a traversal** (1.4 step 3): several markers at one offset inside the
     deleted range and several intervals sharing a start, undone and redone, with the rank-order
     sequence asserted — M1.3's tie-order stability test is the precedent, and the
     reverse-iteration clause is invisible to every set-wise comparison.
14. **`insertBeforeMarkers` is unobservable during replay** (1.5): the same transaction recorded
    with `true` and with `false`, each undone and redone, produces identical trees.
15. **A removed marker does not break a traversal** (1.4 step 1, 3's "never" row): remove one of
    the entry set's markers, then redo the edge; no trap, and every other marker is exact.
16. **`isRecordingUndo == false`** records nothing and leaves the history untouched, and an edit
    made while it is false is not undoable.
17. **Empty and degenerate edits**: `commitTransaction()` with nothing pending; `undo()` with an
    empty history; `redo()` at a leaf; a zero-length replacement; an edit at offset 0 and at the
    buffer end (the `hi + 1` query running past the end, which 1.3 says needs no clamp).
18a. **The payload primitives** (1.9, stage 1): `tombstone` on a node with children clears all
     three of its links, resets every `lastVisitedChild` aimed at it, repairs the parent's child
     list, and leaves `children(of:)` on the slot empty. `promote` on the same shape clears
     `parent` and `nextSibling`, empties `edits`, and **keeps `firstChild`**, so a walk from the
     promoted root still reaches `current`. A review round found a draft whose wording would
     have cleared that `firstChild` and cut the live tree loose; this is the test that sees it.
     Tombstoning a subtree **at least two levels deep** walks it leaves-first and reaches every
     node, asserted by count — a depth-1 fixture would make mutation 14 a coin flip rather than
     a kill.
18b. **The invariant** (1.9): `edits.isEmpty` exactly when `parent == -1`, and `canUndo`
     agreeing with it, across a fresh history, after a commit, after `discardHistory()`, and
     after each primitive. `checkInvariants()` must also fail on a hand-built violation — the
     negative-test precedent `sumTreeTests.swift` sets — so that it is known to be able to fire
     at all.
18c. **`discardHistory()`** leaves the text untouched, `canUndo == false`, and the running total
     zero.
19. **`byteCost` and the running total** (1.9, stage 1): the formula asserted directly on a
    transaction with a known deleted length, a known inserted length and a known number of
    adjustment entries — including a pure insertion at a point carrying many intervals, the case
    an earlier draft's formula reported as a constant. The running total must equal the sum over
    live nodes after a sequence of commits and releases, which is what catches a total
    maintained by a sweep rather than on release.

### 4.3 Perf tests

All release-only, nanosecond clock taken once around the sample loop, absolute **and** ratio
bounds, per `ropePerfTests.swift`'s recorded reasons.

20. **Cost of recording a transaction**, against the same edit with `isRecordingUndo == false`
    as the baseline arm in the same process. Both arms alternating, as the M1.2 chunk-streaming
    test does.
21. **Cost of one undo and one redo** of a single-character transaction at 1 MB, against 4.5's
    existing per-edit rows.
22. **Memory per retained transaction**, by the allocation-counting route the architect pass
    used: a file-scope global plus an `@inline(never)` sink. **It must be environment-gated and
    run alone, the way `cursorTraversalAllocatesNothing` is.** A review round caught this spec
    reusing a whole-process allocation counter without the lesson of the commit immediately
    before it: `2820c79` exists because such a counter is contaminated by every other suite
    allocating in the same process under `swift test --parallel`. `dev/gate.sh` takes a second
    isolated filter, and its two load-bearing grep clauses (`gate.sh:43-49`) must cover it too,
    or a silently skipped probe passes the gate.
23. **The post-commit cost of maintaining the running total**: committing into a history of
    thousands of nodes against committing into an empty one, both arms in the same process,
    asserting the two are within noise of each other. **Thousands, not a handful of large
    transactions** — a review round found that unstated, and at a small node count an
    implementation that recomputes the total by sweeping the whole array is as fast as the
    running total, so the assertion would be vacuous. The budget *check* that sits beside this
    on the typing path is stage 2's, and its spec owns that measurement.

24. **Discarding a large history** — thousands of transactions, which needs no budget and so is
    stage 1's: absolute bound under 1 ms with the measured basis of 127-128 us for 1000
    one-kilobyte entries, plus the no-super-linear ratio.

**The methodology warning that applies to 22 and 24 and to nothing else in the tree.** To
measure a release you must put it *inside* the timed region, the opposite of the
`withExtendedLifetime` discipline every other perf test here uses. Two defences are mandatory
and the architect pass's first probe failed for want of them, reading **zero bytes and five
microseconds** — a plausible wrong answer: hold the subject in a **file-scope global** so the
optimiser cannot sink or delete the release, and feed something derived from it into an
`@inline(never)` sink. There is no template for this in the tree; `ropePerfTests.swift:315` is a
crash smoke test that times nothing. New test code, and it deserves its own review attention.

## 5. `PLAN.md` edits this spec requires

1. **4.5's undo prose bullet**, which currently reads "Undo is transaction-based (grouped by
   command and by a 300 ms window), stored as edit logs plus retained snapshot checkpoints;
   branches are native, so an undo-tree UI is a view." Three of its four clauses are wrong or
   unsourced: there is no 300 ms window (1.7, oracle), there are no retained snapshot
   checkpoints (1.1, measured), and grouping by command is M5's policy over M1.5's mechanism.
   Native branches survive and "an undo-tree UI is a view" is strengthened, because the
   GNU-compatible linear list is a view of the same structure.
2. **Five new rows** in 4.5's complexity table: record one transaction; undo or redo one
   transaction; memory per retained transaction; discard a buffer's undo history; and
   **maintaining the byte-cost running total**, O(1) per commit, the one on the typing path. The
   pruning policy's own costs are `dev/specs/m1.5-stage2.md`'s row to add when it lands. Numbers
   go in the table and nowhere else.
3. **Amend 4.5's "Close a large buffer" row.** Its sentence "M1.5's branching undo and M1.6's
   mmap view will hold many snapshots at once" stops being true of M1.5 once this lands. M1.6
   still owns its half.
4. **The `BufferSnapshot` sketch line** in 4.5, which still shows `history` and `clock` on

5. **Section 9 ("Not in v1")**: undoable overlay creation and removal, with the oracle citation.

## 6. Mutation focus points

Each is a change a careless suite would not notice. The named test is a **hypothesis until the
mutation is run** — both M1.3 and M1.4 shipped a test named in a spec that turned out to be
blind to the mutation it was named for, and only running it showed that.

1. Narrow the marker entry query from `lo..<(hi + 1)` to `lo..<hi`. Killed by test 4 (a marker
   at exactly `hi`, under a deletion) and also by test 13, which sees the two id sets disagree.
2. Drop the tie group at `lo` from the entry set. Killed by test 3 (`.right` at `lo`).
3. Apply a transaction's elementary inverses oldest-first instead of newest-first. Killed by
   test 9.
4. Re-insert the recorded positions **before** applying the text replacement instead of after.
   Killed by tests 2 and 3: an interior position re-inserted first is collapsed again by the
   inverse edit, and at the buffer's end it traps, the offset not existing yet. Named because a
   review round found this was the one entry in this list with no test at all.
5. Make the interval end-search strict (`end > lo`). Killed by test 6.
6. Make `commitTransaction()` append unconditionally. Killed by test 10, and **not** by any test
   starting from a fresh buffer.
7. *Stage 2's.* The draft listed two pruning-policy mutations here — discard `current`, discard
   the newest transaction — killed by the old test 18. Both the policy and that test left this
   spec with 1.9's restructure, so they belong in `dev/specs/m1.5-stage2.md` with the rules they
   mutate; a review round found this entry still pointing at a test that no longer exists. The
   note that they are observable only when the fixture separates `current` from the newest node
   carries over and is worth keeping there.
8. Return an empty applied-replacement list from `undo()`. Killed by test 12.
9. Narrow the after-query to `lo..<(lo + L)`. Killed by test 13.
10. *Withdrawn.* The draft listed "skip raising the ID high-water mark", killed by creating a
    marker after an undo. A review round showed that kill is unreachable: a traversal re-inserts
    through `MarkerTree.inserting(byteOffset:bias:id:)` directly, never through
    `BufferSnapshot.createMarker`'s checked path, and `TextBuffer.nextMarkerID` does not roll
    back on undo, so no undo sequence produces a colliding id whether or not the high-water mark
    rose. The precondition exists to trap a programming error and, like the scalar-boundary
    preconditions M1.3 and M1.4 record, cannot be reached by an in-process test. Section 8
    carries it as a gap rather than this list carrying a mutation nothing can kill.
11. Trap instead of skipping on a missing id in 1.4 step 1. Killed by test 15.
12. Re-insert the entry list front-to-back instead of in reverse (1.4 step 3). Killed by test
    13b, and by nothing else in the list — every other marker and interval assertion is
    position-wise, and a reversed tie group has identical positions.
13. Clear `firstChild` in `promote`, i.e. treat a promotion as a tombstone (1.9). Killed by test
    18a's walk from the promoted root to `current`.
14. Tombstone a subtree root-first instead of leaves-first, so the walk loses what it has not
    reached. Killed by test 18a's node count.
15. Recompute the running total by sweeping live nodes instead of maintaining it on release.
    Killed by test 19's sum assertion, and by test 23 only because its fixture has thousands of
    nodes.
16. Make `canUndo` test `edits.isEmpty` instead of `parent != -1`, or the reverse. Equivalent
    under 1.9's invariant, so this one **should survive**, and it is listed as a *consistency
    check on the invariant's two spellings* rather than as evidence of anything: a passive
    survival demonstrates less than `checkInvariants()` does, and 18b is what actually guards
    it. A review round pushed back on the stronger claim the draft made here.

## 7. Fixed clauses for the implementer

- **Scope**: `Sources/Text/UndoHistory.swift`, `Sources/Text/TextBuffer.swift`,
  `Sources/Text/BufferSnapshot.swift`, `Sources/Text/MarkerTree.swift`,
  `Sources/Text/IntervalTree.swift`, `Tests/TextTests/undoTests.swift`,
  `Tests/TextTests/undoPerfTests.swift`, and the call-site migration in
  `Tests/TextTests/markerTreeTests.swift` and `Tests/TextTests/intervalTreeTests.swift`. Nothing
  else. `PLAN.md` is the main conversation's.
- **No git writes**: `commit`, `push`, `reset`, `checkout --`, `restore`, `clean` are forbidden.
- **No sub-delegation**: do not spawn agents; stop and report if you cannot finish.
- **Foreground execution**: no `nohup` or `&` followed by waiting for a notification that will
  never come; split anything over ten minutes into steps.
- **Effort budget and stop-loss**: if three rounds of the targeted test loop are not green, stop
  and report the state and what remains. If more than the scoped files need changes, stop and
  report the scope change.
- **Do not run the full gate and do not report pass/fail.** Run only the targeted tests you
  need, attach the exact command line and the last lines of raw output, state whether you ran
  the whole suite or a filter, and never write "verified", "all green" or "confirmed".
- **Do not run a mutation pass.** Self-check with a file backup, a targeted edit and `touch`.
- **"Flaky" requires evidence**: no "environmental noise" without an observation that
  distinguishes it; rerun a dozen times first.
- **Deviations**: if a ruling in section 1 turns out to be wrong or unimplementable as written,
  **stop and report it** rather than working around it. M1.4's most valuable implementer report
  was exactly this.
- **Wrap-up**: `git status` converged to the original file set plus the new files; no scratch
  files left.

## 8. Known gaps to write into the file headers

- **Marker and interval creation and removal are not undoable**, deliberately, matching GNU (3's
  table). A traversal skips an id that is no longer present (1.4 step 1).
- **`undo-in-region`, point restoration, `(apply ...)` entries, text-property entries and a
  Lisp-visible `buffer-undo-list` are M5's** (3).
- **The 2 MB default budget is arithmetic from a measured per-entry cost, not a measured
  session.** The first soak run is what validates it, and the 50-buffer 100 MB ceiling is
  recorded in 1.9 rather than solved.
- **`(apply ...)` parity is unverified** — the oracle could not trigger either form, so 1.6's
  side-table mechanism is a design sketch and not a parity claim.
- **`isRecordingUndo` covers undo suppression only.** GNU's `with-silent-modifications` also
  suppresses the modified flag and text-property recording; only the undo half is settled here.
- **Interval and marker offsets must be UTF-8 scalar boundaries**, and like M1.3's and M1.4's
  that precondition cannot be reached by a test without an out-of-process crash harness this
  project does not have. **The ID high-water precondition of 1.8 is in the same class** — a
  review round showed no undo sequence can violate it, so it traps a programming error that no
  in-process test can stage, and mutation 10 was withdrawn rather than left standing as a
  mutation nothing kills.
- **Tombstoned history slots are reclaimed only by `discardHistory()`** (1.9). The residue is a
  fixed-size `Node` with empty arrays per pruned transaction, bounded by the transactions since
  the last discard. Compaction needs node ids that survive renumbering, which is M5's generation
  counter with its first real caller.
- **Nothing in the type system stops a holder of a bare `BufferSnapshot` from calling
  `createMarker(id:)` directly** and allocating an id `TextBuffer` does not know about; the
  high-water precondition turns the collision into a trap rather than preventing the call. 1.8's
  rule 4 closes the only path that reaches it in production.
