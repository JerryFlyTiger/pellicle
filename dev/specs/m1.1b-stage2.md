## 2. What to build

### 2.1 `Fragment`

```swift
package enum Fragment<Item: Summable>: Sendable {   // transient; never stored in a tree
    case items(ArraySlice<Item>)                       // 0...2B items, height 0
    case nodes(ArraySlice<Node<Item>>, height: UInt8)  // 0...2B same-height nodes
}
```

A `Fragment` may be **underfull or empty** — that is its entire reason to exist. The type
distinction is the enforcement mechanism: an underfull group is representable as an argument
and not representable as a stored `Node`, which is why `checkInvariants()` keeps its
assertions verbatim. `case nodes` carries the common height explicitly because an empty
slice cannot report one.

### 2.2 `TreeBuilder`

```swift
package struct TreeBuilder<Item: Summable>: ~Copyable {
    package init()
    package mutating func push(_ fragment: Fragment<Item>)
    package mutating func push(subtree: Node<Item>)   // well-formed subtree
    package consuming func finish() -> SumTree<Item>
}
```

Semantics: `finish()` returns the tree whose in-order item sequence is the concatenation, in
push order, of everything pushed. Every node in the returned tree satisfies `checkNode`'s
bounds (non-root `B...2B`; the root gets the looser root bounds and a single-child root chain
is collapsed, as `collapseRoot` already does — reuse it rather than writing a second one).
`finish()` with nothing pushed, or with only empty fragments pushed, returns the empty tree
(`SumTree()`), matching `buildFromNodes([])`'s current empty-leaf result.

Algorithm: the prototype's right-spine join. Keep one accumulator node; to push, descend the
accumulator's right spine until the heights match, splice there, and propagate a split upward
if the spliced node exceeds `2B`. The step that dissolves the obstruction is the prototype's:
when the argument is the same height as the spine node, splice **its children in flat**,
because each of those children is individually well-formed even when their parent group is
not. Deviation to record explicitly in your report: the M1.1b design comment calls
`push(subtree:)` "O(1) amortised", which describes a per-height-slot builder; the right-spine
join is O(height difference) per push and O(h) for a whole monotone-height fragment run. Do
not chase the O(1) claim — say in your report that the shipped shape is the right-spine join
and what it costs.

### 2.3 `splitFragments` — one descent, no rebuilding

```swift
// Free function alongside `splitNode`/`cutNode`, or a `SumTree` method — your call, but it
// must be reachable from `Rope.swift` (so `package`, not `private`).
package func splitFragments<Item: Summable>(
    _ node: Node<Item>, prefix: Item.Item_Summary,
    where predicate: (Item.Item_Summary) -> Bool,
    left: inout [Fragment<Item>], right: inout [Fragment<Item>]
) -> (item: Item, itemPrefix: Item.Item_Summary)?
```

One descent. It appends to `left` and `right` the per-level groups on either side of the flip
point, and **returns the flip item itself, isolated**, together with the summary of everything
before it — i.e. it is `cut` in fragment form. Returns `nil` when the predicate never fires
(then `left` receives the whole tree and `right` nothing). Precondition: `!predicate(prefix)`,
same as `cutNode` (`SumTree.swift:300-302`), with the same reason.

Fragment ordering is part of the contract and must be documented in the doc comment: `left`
is emitted highest-level-first and `right` is emitted deepest-first-then-upward, and both must
be pushed into a builder **in the order emitted**. Say it in words, because it is the one
thing a later reader cannot recover from the types.

`split(where:)` (the flip item folds **left**) and `cut(where:)` (the flip item comes back on
its own) both keep their current `package` signatures and semantics exactly, and are
re-implemented on top of `splitFragments` plus two `TreeBuilder`s.

### 2.4 Deletions and rewrites

- **Delete `buildFromNodes`** and both call sites (`splitNode:267`, `cutNode:329`). If
  `splitNode`/`cutNode` become redundant with `splitFragments`, delete them too rather than
  leaving two descents; the public `split`/`cut`/`find` API is what must survive.
- `concatNodes` and `rewrap` become thin wrappers over the builder, so there is **one**
  rebalancing implementation rather than two. `SumTree.concat` and `SumTree.build` keep
  working through them. If a `preconditionFailure` in the old `concatNodes` (170/174/184/191/
  201) no longer corresponds to anything the new implementation can produce, do not carry it
  over verbatim — either re-derive it against the new structure or drop it and say which in
  your report.
- **Delete `Rope.concatMergingSeam`** and rewrite `generalPathReplace` as: two
  `splitFragments` descents into the **original** tree (one at the lower bound, one at the
  upper), then one builder that is pushed the prefix fragments, the replacement chunks, and
  the suffix fragments. That is two cursor walks and one build, down from six walks and three
  builds. The straddling chunk at each boundary comes back as `splitFragments`'s returned
  item; slice its bytes yourself as `splitTree` does today (`Rope.swift:247-280`) and push the
  pieces as `Fragment.items`.
- **The seam policy survives, done leaf-locally.** Today `concatMergingSeam` merges the
  boundary pair when their byte counts sum to `<= 64`. After the rewrite, the boundary chunks
  are the last element of the last left fragment and the first element of the first right
  fragment — plain array elements in the rope's own hands. Apply the same `<= 64` rule to
  them there, before pushing, and to the seams on both sides of the inserted text. Do **not**
  put a coalescing hook inside `TreeBuilder`: it is generic over `Item` and must stay ignorant
  of chunk sizes, and `Rope.init(unmergedChunks:)` depends on bulk construction **not**
  coalescing.
- Update the stale doc comments that name the deleted functions: `Rope.swift:44`,
  `Rope.swift:557`, `SumTree.swift:296-300`, and `ropeTests.swift:942`.
- **Update, do not delete, `SumTree.swift:47-59`** — the paragraph that says `split`/`cut`
  are O(B·h²) and that round 2 is what makes the O(log n) claim true. The file itself
  instructs this ("Do not delete this paragraph once round 2 lands — update it to describe the
  code as it then is"). Rewrite it to describe the code as it then is, keeping the same
  honesty about what is and is not measured. `Rope.locate`'s doc comment (`Rope.swift:199`)
  carries the same claim about the caller and needs the same treatment.
