## 1. The design, and why

### 1.1 The item

Intervals are stored in a `SumTree<IntervalRecord>` ordered by **start**, with the start
gap-encoded relative to the previous item's start and the extent stored as a **length**:

```swift
package struct IntervalRecord: Sendable, Equatable {
    package var gap: Int      // this item's start minus the previous item's start, >= 0
    package var length: Int   // end - start, >= 0
    package var id: IntervalID
    package var frontAdvance: Bool
    package var rearAdvance: Bool
}
```

Two consequences, and they are the whole reason for this encoding:

- **A suffix shift is one item's edit.** Gaps are relative, so "add L to every start from rank
  r on" changes only item r's gap, exactly as in `MarkerTree`.
- **An interval entirely after the edit needs no visit at all.** Its end is `start + length`,
  so shifting its start shifts its end for free. Only intervals whose *length* genuinely
  changes — the ones straddling the edit point — need an item-level edit, and there is no
  encoding that avoids that: their extent really did change.

### 1.2 The augmented summary, and why `maxEnd` is relative

```swift
package struct IntervalSummary: Summary {
    package var count: Int     // order statistic: prefix count = rank
    package var span: Int      // prefix sum of gaps = the last item's absolute start
    package var maxEnd: Int    // max end in this range, measured from the range's own base
    static var identity: Self { IntervalSummary(count: 0, span: 0, maxEnd: 0) }
    static func + (a: Self, b: Self) -> Self {
        IntervalSummary(count: a.count + b.count, span: a.span + b.span,
                        maxEnd: max(a.maxEnd, a.span + b.maxEnd))
    }
}
// IntervalRecord.summary = IntervalSummary(count: 1, span: gap, maxEnd: gap + length)
```

`maxEnd` is stored **relative to the base of the range it summarises** (the start of the item
before the range), for the same reason the start is: an absolute `maxEnd` would have to be
rewritten in every summary on the path for a shift that changes no item. Relative, it is
shift-invariant, so the suffix shift above stays one item's edit.

**It is a monoid; the right identity law is the one that needs the invariant `maxEnd >=
span`.** Left identity:
`(0,0,0) + (c,s,m) = (c, s, max(0, 0+m)) = (c,s,m)` because `m >= 0` (every item contributes
`gap + length >= 0`). Right identity: `(c,s,m) + (0,0,0) = (c, s, max(m, s))`, which equals
`(c,s,m)` only when `m >= s` — true because the last item's own end, `s + length_last`, is one
of the values `m` is a max over. Associativity is the standard affine-max composition.
`checkInvariants()` asserts `maxEnd >= span` on every node, so a future edit that breaks it is
caught rather than silently returning wrong query answers.

**`find` returns `nil` where `seek` traps, and the common case is the one that would trap.**
`SumTree.find(where:)` (`SumTree.swift:797`) yields `nil` when the predicate is never true of
the whole tree; `SumTreeCursor.seek(where:)` (`SumTreeCursor.swift:131-141`) calls
`preconditionFailure` in that case — in release too. "No interval ends after `x`" is the
ordinary state of a buffer whose overlays are all before the cursor, and "`k = 0`, a keystroke
inside no overlay" is the ordinary edit, so every use of the `maxEnd` predicate must either go
through `find` or be guarded before `seek`, as `MarkerTree.markers(in:)` already does
(`MarkerTree.swift:268-273`) — a guard whose absence M1.3's cold read found untested.

**The prefix `maxEnd` is monotone**, which is what makes the descent legal: over a growing
prefix from the tree's base, `maxEnd` is a max over a growing set, hence non-decreasing, and
it is `0` for the empty prefix. So "the first item whose end exceeds `x`" is a legal
`find`/`seek` predicate for any `x >= 0` — a single O(log n) descent.

### 1.3 Ordering: start only, no doubled key

`MarkerTree` doubles its key to `2 * offset + bias` so that "shift every marker at or after K"
is a suffix in rank order even when only some markers at K move. The same problem exists here
(at an insertion point, an interval whose start is exactly there moves only if
`frontAdvance`), but the solution is different: this milestone's insert stage already
rebuilds the tie group at the insertion point, so it **stably partitions that group into
non-movers then movers**, after which the movers are a suffix and one gap edit finishes the
job. No bias dimension in the key, no bias dimension in the summary.

The tie order among equal starts is otherwise arbitrary and no query depends on it — GNU's
own `overlays-in` docstring says the returned order is "arbitrary unpredictable" and
`overlays-at` documents an order only for its `SORTED` argument, which is a caller-side sort
by priority (a concept this milestone does not have; see section 3).

### 1.4 The edit rule, from the oracle

Every row below is from GNU Emacs 30.2 (`/opt/homebrew/bin/emacs`), buffer `"0123456789"`,
overlay `(3,7)` unless stated. Emacs positions are 1-based; this tree's offsets are 0-based
bytes, so a transcript position `p` is byte offset `p - 1`. The transcripts are reproduced in
the tests (section 4) with their commands.

**Insertion of `L` bytes at `P`** — per endpoint, independently:

```
start' = start + L   if start > P || (start == P && (frontAdvance || insertBeforeMarkers))
end'   = end   + L   if end   > P || (end   == P && (rearAdvance  || insertBeforeMarkers))
if start' > end' { start' = end' }
```

- The two flags matter **only** at the endpoint they name. Oracle, insert `"X"` at 3 / 5 / 7
  with the four flag combinations: `(nil,nil)` gives `(3,8)`, `(3,8)`, `(3,7)`; `(nil,t)` at 7
  gives `(3,8)`; `(t,*)` at 3 gives `(4,8)`. Multi-character insertions behave identically
  with `L = 3` (`(t,nil)` at 3 gives `(6,10)`).
- **`insertBeforeMarkers` overrides both flags**, and this was not obvious: the funnel already
  carries the flag for markers, and the oracle shows it applies to overlays too. With
  `insert-before-markers`, *every* endpoint at `P` advances — `(nil,nil)` at 3 gives `(4,8)`
  where a plain insert gives `(3,8)`, and `(nil,nil)` at 7 gives `(3,8)` where a plain insert
  gives `(3,7)`.
- **The clamp is not decoration.** An empty overlay at 5 with `(frontAdvance t, rearAdvance
  nil)`, insert `"X"` at 5: the per-endpoint rule would give `(6,5)`, an inverted interval.
  GNU gives `(5,5)`. The other three combinations need no clamp: `(nil,nil)` -> `(5,5)`,
  `(nil,t)` -> `(5,6)`, `(t,t)` -> `(6,6)`. `insertBeforeMarkers` makes all four `(6,6)`, so
  the clamp is unreachable when it is set. This is the only reachable inversion: for a
  non-empty interval, `start == P` implies `end > P`, so if the start moves the end moves too.

**The implementation must use the predicate form, not the clamp form.** The tree stores
`start` as a gap and the extent as a `length`, so "shift this interval's start" moves its end
with it — there is no representation in which an endpoint moves alone, and therefore no place
for a clamp applied *after* a shift. Restate the same rule as two predicates, which is what
deliverable C implements:

```
startMoves(i) = start > P || (start == P && (fa || bm) && (length > 0 || ra || bm))
endMoves(i)   = end   > P || (end   == P && (ra || bm))
```

`startMoves` implies `endMoves` (if `start > P` then `end >= start > P`; if `start == P` and
the start moves, then either `length > 0`, so `end > P`, or `ra || bm` holds). So an interval
either shifts whole (`startMoves`, a gap edit, `length` untouched), or grows by `L`
(`endMoves && !startMoves`, a `length` edit, gap untouched), or is untouched. **The third
conjunct of `startMoves` is the clamp**: an empty interval at `P` with `fa` and neither `ra`
nor `bm` is exactly the `(6,5)` case, and the predicate makes it a non-mover, which is GNU's
`(5,5)`. A cold read of this spec caught the first draft omitting it, where "movers are the
tie-group members with `fa || bm`" would have shifted that interval to `(P+L, P+L)`.

**Deletion of `[lo, hi)`, `d = hi - lo`** — per endpoint, and **independent of both flags**
(oracle: all twenty combinations of the four flag pairs against five deletion shapes give the
same positions):

```
x' = x                 if x <= lo
x' = lo                if lo < x < hi
x' = x - d             if x >= hi
```

An interval the deletion empties **stays in the tree**: `overlay-buffer` remains non-nil and
`overlay-start == overlay-end`. Zero-width intervals are a normal state here, not an error.

**A replace is a delete then an insert, never one fused delta.** This is M1.3's finding
re-verified for intervals: the twelve `delete-region` + `insert` rows of the oracle are
reproduced exactly by composing the two rules above, including the four cases where the
overlay is emptied by the delete and then meets the insert's empty-interval rules — e.g.
`(t,nil)` deleting `(3,7)` and inserting two bytes at 3 gives `(3,3)` (the delete empties it
at 3; the insert hits the clamp), while `(t,t)` gives `(5,5)` and `(nil,t)` gives `(3,5)`.
`applyEdit` therefore composes two stages and does not attempt a fused pass.

### 1.5 What each stage touches

Let `k` be the number of intervals whose extent genuinely changes (those straddling the edit
point) and `a` the number of intervals whose start lies strictly inside a deleted range.

**Stage 1, delete `[lo, hi)`.** An interval with `end <= lo` cannot change (its start is
`<= end <= lo`). The rest split into two disjoint jobs:

1. **Straddlers** — `start <= lo < end`. Their start does not move and their end does, so
   only `length` changes. A `length` edit does not touch any gap, so these are `k`
   independent `pathCopyEdit`s targeting one rank each, and they do not interact.
   **Finding them is the three-part search of 1.6, not a single descent**: straddlers are not
   contiguous in rank order — A(0,1), B(10,200), C(20,21) with `lo = 60` has only B
   straddling, between two non-straddlers — so enumerating them needs piece 2 of that search
   plus a tie-group scan at `lo`, at their cost, not a `find`/`seek` that follows one path.
   Note **piece 1's mechanism, not its range API**: at a single point the range `[lo, lo)` is
   empty and piece 1 as a query would return nothing, so what is reused is its descend-to-
   first-item-then-scan-while-the-start-is-unchanged, exactly as 1.6's last paragraph says.
2. **Starts inside or after the range** — a *contiguous* rank range, because starts are
   sorted. Those with `lo < start < hi` collapse to `lo` (their lengths recomputed by the
   same rule); those with `start >= hi` shift by `-d`, which is one gap edit at the first of
   them. Built like `applyDeleteAndCollapse`: `split`/`items()`/`concat` over the collapsing
   group, then `cut` to rebase the tail's first gap.

**Stage 2, insert `L` at `P`.**

1. **Straddlers** — those whose end moves while their start does not. Same shape: `k`
   independent `length += L` edits.
2. **Movers** — the intervals for which `startMoves` (1.4) holds: every interval with
   `start > P`, plus the members of the tie group at `P` that satisfy the predicate's second
   clause **including its third conjunct**, so the empty `(fa, not ra, not bm)` interval at
   `P` stays behind. Stably partition the tie group at `P` into non-movers then movers; the
   movers are then a rank suffix and one gap edit of `+L` at the first of them shifts all of
   them. **The tie group must be partitioned as a whole, residents included** — this is
   M1.3's second correction, and it is reachable here for the same reason: stage 1 has just
   collapsed intervals onto `lo`, so the group at `P == lo` mixes newcomers with intervals
   that were already there.

Cost: `O((k + 1) log n + a + m)` per edit, where `m` is the size of the tie group at the
insertion point and the straddler enumeration is included (it is the same `O(log n +
k)`-ordinary, `O((k + 1) log n)`-worst search as the query, so it is dominated by the term
already there rather than adding one). **`m` is a real term, not bookkeeping**: stage 2's
stable partition rewrites that group. It is not bounded by `k` or `a` — a keystroke where
several overlays happen to start pays it with `k = 0` — and the implementation should skip the
partition entirely when the group is uniform (every member a mover, or none), which is the
usual case, since a tie group of size 0 or 1 cannot be mixed. **The doubled key of 1.3 would
not have removed this**: the exception in `startMoves` depends on `insertBeforeMarkers`, which
is a property of the *edit*, not of the item, so no static key can sort the movers into a
suffix for every edit. The partition is inherent to the semantics.

`k` above is per stage; a replace pays both stages, which is the same order. The
common editing case has `k = 0` (a keystroke inside no overlay) or `k` in single digits, and
`a = 0` unless the deletion swallowed whole intervals. The bound is honest about `k` and `a`
being unavoidable: those items' stored fields really do change.

**The rejected alternative, recorded so it is not rediscovered as new**: one rank-span rebuild
covering everything from the first straddler to the last affected item. It is simpler, but its
span starts at the *first interval ending after `lo`*, so a single buffer-wide overlay at rank
0 — a region highlight, a narrowing indicator — makes every edit O(number of intervals before
the edit point). The `k`-independent-`pathCopyEdit` shape above has no such cliff.

### 1.6 The query, and the complexity claim 4.5 actually earns

**The query is three searches, not one traversal**, and this shape is the third attempt. The
first draft pruned strictly on `maxEnd > lo`, which loses an empty interval at `s == lo`
(its end *is* `lo`, and 1.7's oracle says GNU returns it). The second relaxed the prune to
`maxEnd >= lo`, which finds it and destroys the complexity claim: `M` intervals `(i, M)` for
`i = 0 ..< M` all end at `M`, so a query at `lo == M` returning **nothing** would still
descend into every one of them — `O(n)` for `k = 0`, and their starts are scattered across
every rank, so no "boundary tie group" argument bounds it. The fix is not a third prune
threshold; it is to notice that the result set splits into three pieces, each of which has its
own efficient search:

1. **Starts inside the range** — items with `start` in `[lo, hi)`. Rank-contiguous, because
   the tree is ordered by start: one descent to the first such item, then a cursor scan until
   `start >= hi`. **Every one of them is a result** and needs no filtering: if non-empty, then
   `end > start >= lo`; if empty, 1.7's empty clause covers it. This is where the empty
   interval at `lo` is found, which is why the prune below does not have to be weakened for it.
2. **Straddlers** — items with `start < lo < end`. Only these need the augmented summary, and
   for them the prune is **strict** (`maxEnd > lo`), restricted to the rank prefix before
   piece 1's first item. Every subtree surviving that prune holds an item with `end > lo`, and
   every item in the prefix has `start < lo <= hi` — note `<=`, since `lo == hi` is a legal
   query and the two facts that matter are `start < lo` from the rank restriction and
   `end > lo` from the prune — so **every visited node yields at least one result**. That is
   the output-sensitivity argument, and it holds only because the prune is strict and the
   region is start-bounded.
3. **The empty interval at `hi`**, when `lo == hi` or `hi == bufferEnd` (1.7). Also a tie
   group, also rank-contiguous: one descent, scan the group at `hi` for `length == 0`.

Piece 2's visits are `O(log n + k)` when its results are rank-contiguous — the ordinary case,
since straddlers of one point tend to be neighbours — and `O((k + 1) log n)` in the worst case,
where `k` scattered results each cost their own root-to-leaf path. Pieces 1 and 3 cost one
descent plus their own output. **4.5's row promises a flat `O(log n + k)`; section 5 amends it
to that two-part claim, which is what an augmented B-tree with items only in the leaves can
actually deliver.** A test counts the visits rather than timing them (M1.3's third measurement
lesson), and the count is derived from the tree's own height so it cannot go stale.

The same decomposition is what `applyEdit` uses to enumerate straddlers (1.5): straddlers of a
point `P` are piece 2 with `lo = P`, plus the members of the tie group at `P` with `end > P`.
The second part reuses piece 1's *mechanism* — descend to the first item at `P`, scan while
the start is unchanged — not piece 1's range API, which would be vacuous at `lo == hi == P`.
Nothing in the edit path needs a non-strict prune either.

### 1.7 GNU's query boundaries, which are not what the docstring says

`overlays-in`'s docstring says "at least one character contained within the overlay and also
contained within the specified region", plus a clause for empty overlays at BEG, between BEG
and END, or at END when END is the end of the accessible portion. The empty-region case
refutes the first half: with `(overlays-in 5 5)` on the buffer above, GNU returns the
**non-empty** overlay `(3,7)`, which shares no character with an empty region. The observed
rule, over seven query ranges against five overlays:

```
include a non-empty interval  iff  end > lo && start < hi
include an empty interval at s iff  lo <= s < hi  ||  (s == hi && (lo == hi || hi == bufferEnd))
```

which reproduces every row. The transcript, buffer `"0123456789"` (positions 1-11, `point-max`
= 11), overlays `A(3,7) B(5,5) C(3,3) D(11,11) E(7,7)`, each `overlays-in` result sorted by
name for legibility:

```
overlays-in (5,5)    -> (A(3,7) B(5,5))
overlays-in (3,3)    -> (C(3,3))
overlays-in (7,7)    -> (E(7,7))
overlays-in (11,11)  -> (D(11,11))
overlays-in (3,7)    -> (A(3,7) B(5,5) C(3,3))
overlays-in (5,6)    -> (A(3,7) B(5,5))
overlays-in (1,11)   -> (A(3,7) B(5,5) C(3,3) D(11,11) E(7,7))

overlays-at 3   -> (A(3,7))
overlays-at 5   -> (A(3,7))
overlays-at 7   -> nil
overlays-at 11  -> nil
```

The `(5,5)` row is the one that refutes the docstring: a **non-empty** overlay is returned for
a region containing no character. `(3,3)` is the row that keeps the rule honest in the other
direction — `A(3,7)` is not returned there, because `start < hi` fails. `overlays-at P` is a
different predicate again: `start <= P < end`, so it excludes empty intervals and anything
ending at `P`, which is why `overlays-at 7` is nil while `overlays-in (7,7)` is not.

**The `bufferEnd` clause is the caller's, not the tree's.** The tree does not hold the text, so
`IntervalTree` takes the decision as a parameter and `BufferSnapshot` supplies it from
`text.utf8Count`, exactly as `createMarker` owns the scalar-boundary precondition that
`MarkerTree` cannot check.

## 2. Deliverables

### A. `Sources/Text/IntervalTree.swift`

`IntervalID` (`package typealias IntervalID = UInt64`, monotone and never reused, documented
like `MarkerID` at `MarkerTree.swift:126`), `IntervalSummary`, `IntervalRecord`,
`IntervalSpan` (what queries return: `range: Range<Int>`, `id`, `frontAdvance`,
`rearAdvance`), and `IntervalTree` wrapping a `private var tree: SumTree<IntervalRecord>`.

**`IntervalTree` must never expose the underlying `SumTree`**, for `MarkerTree`'s reason
(`:172-179`): gaps are relative, so a bare `concat` of two trees is wrong without rebasing the
right-hand side's first gap. The only exception is `internal var testOnlySumTree`, for the
node-visit test.

API:

```swift
package init()
package init(sortedIntervals: [(range: Range<Int>, id: IntervalID, frontAdvance: Bool, rearAdvance: Bool)])
package var count: Int
package var isEmpty: Bool
package func start(ofRank r: Int) -> Int
package func end(ofRank r: Int) -> Int
package func id(ofRank r: Int) -> IntervalID
package func span(ofRank r: Int) -> IntervalSpan
package func inserting(range: Range<Int>, id: IntervalID, frontAdvance: Bool, rearAdvance: Bool) -> IntervalTree
package func removing(id: IntervalID, startingAt byteOffset: Int) -> IntervalTree
package func intervals(overlapping byteRange: Range<Int>, includingEmptyAtUpperBound: Bool) -> [IntervalSpan]
package func intervals(at byteOffset: Int) -> [IntervalSpan]
package func applyEdit(byteRange: Range<Int>, insertedLength: Int, insertBeforeMarkers: Bool = false) -> IntervalTree
package func checkInvariants() throws
```

`init(sortedIntervals:)` preconditions non-decreasing starts and `range.lowerBound <=
range.upperBound`; it does not sort, mirroring `MarkerTree.init(sortedMarkers:)` (`:196`).
`checkInvariants()` calls the generic checker and adds: gaps non-negative, lengths
non-negative, every node's `maxEnd >= span`, and every node's cached `maxEnd` equal to the
fold of its children.

Preconditions are `precondition`, not `assert` (they must hold in release), with the message
style `"IntervalTree.applyEdit: ..."` already used in `MarkerTree`.

**Not promoted for cross-module inlining.** Plain `package`, matching `MarkerRecord`'s note
(`MarkerTree.swift:154-156`). Do not touch `Sources/Text/InliningProbe.swift` or
`dev/check-inlining.sh`, whose `check_attr` guards `Node`, `Summary`, `Summable` and
`SumTreeCursor` by name.

### B. The one addition to shared machinery: a pruned traversal in `SumTree`

`find`, `cut` and `seek` all follow a **single** path: their predicate is monotone over the
prefix, so exactly one child can be entered per level. An overlap query enters several. Add
one generic primitive to `SumTree.swift`, next to `find`:

```swift
/// Visits items in order, skipping any subtree the caller declines. `prefix` is the summary
/// of everything strictly before the node or item being offered, so a caller with a
/// prefix-sum dimension can compute absolute positions. Returning `false` from `visit` stops
/// the traversal. `descendInto` is given the prefix and the candidate subtree's own summary.
package func visitItems(
    descendInto: (_ prefix: Item.Item_Summary, _ subtree: Item.Item_Summary) -> Bool,
    visit: (_ prefix: Item.Item_Summary, _ item: Item) -> Bool
)
```

It knows nothing about intervals; it is tested against `IntItem` in `sumTreeTests.swift` as
well as through `IntervalTree`. Recursion is bounded by height, like `items()`.

### C. `IntervalTree.applyEdit`

Exactly the two stages of section 1.5, in that order, with the delete stage skipped when
`byteRange.isEmpty` and the insert stage skipped when `insertedLength == 0` (mirroring
`MarkerTree.applyEdit`, `:429-441`). Preconditions: `byteRange.lowerBound >= 0`,
`lowerBound <= upperBound`, `insertedLength >= 0`.

### D. `BufferSnapshot`

Add `package private(set) var intervals: IntervalTree` and `private var nextIntervalID:
IntervalID`, thread the existing funnel through `intervals.applyEdit(...)` with the same three
arguments already passed to `markers.applyEdit`, and add:

```swift
package mutating func createInterval(
    byteRange: Range<Int>, frontAdvance: Bool = false, rearAdvance: Bool = false
) -> IntervalID
```

preconditioning both endpoints in range and on scalar boundaries via `Rope.isScalarBoundary`,
exactly as `createMarker` does, and

```swift
package func intervals(overlapping byteRange: Range<Int>) -> [IntervalSpan]
```

which supplies `includingEmptyAtUpperBound: byteRange.isEmpty || byteRange.upperBound == text.utf8Count`
— the GNU rule of section 1.7, applied in the only place that knows the buffer end.

Do not add a `clock`, an `init(text:markers:intervals:)`, or a second edit funnel.

## 3. Explicitly out of scope, with the reason

- **Text properties, plists and stickiness.** 4.5 puts overlays and text properties in one
  tree, and they will share this one — but a text property is a *plist*, and there are no Lisp
  values until M2. What this milestone can do is record the oracle so the polarity is not
  rediscovered: text properties default **rear-sticky and not front-sticky** (the opposite
  default from an overlay's `(nil, nil)`), `insert` never inherits while `insert-and-inherit`
  does, and `front-sticky` / `rear-nonsticky` invert the default at the edge they name (both
  the `t` and the per-property list form were checked). M5 wires them onto this tree.
- **Resolving an interval by identity in less than O(n).** The obstruction is the one written
  up for markers in `dev/specs/m1.3.md` section 3, unchanged: an edit is contiguous in
  position order and an arbitrary subset in ID order. 4.5's table gives identity resolution to
  M5. `IntervalRecord` carries `id` from the first commit so the later index has a target, and
  `removing(id:startingAt:)` takes the start so the caller pays O(log n + tie group), not O(n).
- **`next-overlay-change` / `previous-overlay-change`.** No client until the redisplay planner
  (M6). The derivation is recorded here so the next milestone does not rediscover it: the next
  change after `P` is the smaller of the next start after `P` (one descent) and the smallest
  end among the intervals straddling `P` (one overlap query at `P`), i.e. O(log n + k).
- **Priority, faces, and any ordering guarantee.** `overlays-at`'s `SORTED` argument sorts by
  priority, which is an overlay *property* — M5's business. The unsorted order is undocumented
  in GNU and the oracle shows it is not stable in any useful sense, so this tree promises
  ascending start order and nothing else.
- **An item-merge hook on `Summable`.** M1.1b stage 2 deferred the chunk-coalescing question
  until a second `Item` type could vote (`PLAN.md:2158-2163`). **This milestone votes no.**
  Intervals carry identity: two adjacent intervals with equal fields are two distinct overlays
  and merging them would destroy an object the Lisp side holds. So the second client does not
  want the hook either, and the deferral stands with one interested client instead of a tie.
- **Cross-module promotion.** Nothing here is on a measured hot cross-module path.

## 4. Tests

**`Tests/TextTests/intervalTreeTests.swift`** — `@Suite("IntervalTree")`, no tag (the default
run must include it).

*Oracle-backed conformance.* Each test quotes the `emacs -Q --batch` command and its raw
output in a doc comment above the expectation, per `CLAUDE.md`, and converts 1-based positions
to 0-based offsets in the test body with the conversion visible.

1. `oracleInsertAtBoundaries` — insert 1 byte at start / middle / end for the four
   `(frontAdvance, rearAdvance)` combinations (12 rows of section 1.4).
2. `oracleInsertMultiByte` — the same with 3 bytes, so no rule accidentally hardcodes `L = 1`.
3. `oracleInsertBeforeMarkersOverridesBothFlags` — the twelve rows where
   `insert-before-markers` and `insert` differ, plus the four empty-overlay rows.
4. `oracleEmptyIntervalInsertClamp` — the four empty-at-5 rows, including the `(t, nil)` row
   that would invert without the clamp.
5. `oracleDeletionIsFlagIndependent` — five deletion shapes x four flag pairs; assert the
   twenty results and that they do not depend on the flags.
6. `oracleDeletionKeepsEmptiedIntervals` — an interval the deletion empties is still present,
   with `start == end`.
7. `oracleReplaceIsDeleteThenInsert` — the twelve replace rows, which is the M1.3 refutation
   re-run for intervals: assert the composed rule reproduces them.
8. `oracleOverlapQueryBoundaries` — the seven query ranges of section 1.7 against the five
   overlays, including `(5,5)` returning the non-empty `(3,7)` and `(3,3)` not returning it,
   and the `bufferEnd` clause through `BufferSnapshot`. **Build the fixture twice, in both
   tie orders of `A(3,7)` and `C(3,3)`**, which share the start 3, and assert the same results
   from both. 1.3 says no query depends on tie order, so this is asserting a stated property —
   and it is load-bearing for the mutation pass: under mutation 6 the order `C, A` gives a
   combined `maxEnd` of `max(3, 4) = 4` where the correct combine gives `max(3, 3 + 4) = 7`
   (positions written as in 1.7's transcript, which is 1-based; the test body converts, and
   the conclusion holds for any positive gap since `gap + 4` is never `max(gap, 4)`),
   so the `(5,5)` and `(5,6)` rows lose `A`; the order `A, C` gives 7 under both the correct
   and the broken combine, because `A`'s own `maxEnd` already dominates, and the mutation
   survives. A cold read found that, with one order written, whether this test catches
   mutation 6 was decided by which order the author happened to type.
9. `oracleIntervalsAt` — `overlays-at` at 3 / 5 / 7 / 11.

*Structural.*

10. `invariantsHoldAfterRandomEdits` — `checkInvariants()` after each of a few hundred edits.
11. `maxEndInvariantIsChecked` — hand-build a tree with a stale `maxEnd` and assert
    `checkInvariants()` rejects it (the negative-test section of `sumTreeTests.swift:477-553`
    is the precedent: an invariant checker nobody has seen fail is not evidence).
12. `tieGroupPartitionKeepsOrder` — intervals at the same start with mixed `frontAdvance`,
    inserted so that residents and newcomers mix; assert starts stay non-decreasing and both
    subsets land where the oracle says.
13. `straddlersAreTheOnlyLengthChanges` — an edit inside one interval and outside another;
    assert the second interval's stored `length` is untouched **and its absolute start is
    where it should be**, with that second interval ranked **after** the straddler. Both
    halves are needed and the ranking is not optional: a mutation that shifts the straddler's
    gap instead of its length leaves every `length` in the tree correct and moves the absolute
    start of every *later* item, so a neighbour ranked before the straddler would see nothing
    (gaps are relative to the previous item, so a gap error cascades forward only).
14. `emptyTreeAndEmptyQueries` — every query on an empty tree, and empty query ranges.
15. `removingRebasesTail` — the `MarkerTree` test of the same name, for intervals.
16. `bufferSnapshotFunnelKeepsTreesInStep` — edits through `BufferSnapshot.replaceSubrange`
    leave `text`, `markers` and `intervals` consistent.

17. `queriesPastTheLastInterval` — every query and every edit at offsets beyond the last
    interval's end, where the `maxEnd` predicate is never true. This is the `find`-versus-
    `seek` trap of 1.2: `MarkerTree`'s equivalent guard had no test until a cold read found it
    (`markerTreeTests.swift:428-444`).

*Counted, not timed.*

18. `queryVisitsAreOutputSensitive` — feed a counting predicate to the real `visitItems` (the
    `CallCounter` pattern of `markerTreeTests.swift:551-553`) and assert, for a contiguous
    result set, that visits are within `height + k` — derived from the tree's own `height`,
    never hardcoded. Include the scattered-results case as a recorded number, not a bound.
19. `editVisitsAreConstantWhenNothingStraddles` — an edit with `k = 0` visits `height + 1`
    nodes per `pathCopyEdit`, at 10^4 / 10^5 intervals.

20. `boundaryEmptyIntervalsAtScale` — one fixture, **two assertions on two different
    queries**, because 1.6's two failure modes are not visible to the same one. The fixture is
    a few thousand intervals, so the tree is several levels deep: empty intervals placed
    exactly at chosen `lo` and `hi` positions, and — this is the shape that matters — **many
    non-empty intervals whose `end` equals one chosen position `Q` while their starts are
    scattered across every rank**, which is 1.6's counterexample. (a) *Results*: query the
    positions carrying empty intervals and compare against a brute-force filter using 1.7's
    rule; these queries return results, and this is what mutation 7(a) breaks. (b) *Visits*:
    query `[Q, Q+1)`, which returns **nothing**, and assert the visit count stays within
    `height + 1` plus the tie groups scanned; this is what mutation 7(b) breaks, and without
    it an implementation that walks every node and still returns the right answer passes.

*Differential.* 21. `manyEditDifferential` — 20,000 random edits against a naive model (an
array of intervals with the section 1.4 rules applied by brute force), comparing the full
interval set after each edit **through both paths: the rank accessors and a random
`intervals(overlapping:)` query**. The two paths are not interchangeable — `maxEnd` feeds only
the query, so a rank-only comparison is blind to every corruption of it, which is how mutation
6 could otherwise survive this test. The query's `includingEmptyAtUpperBound` must be computed
the way `BufferSnapshot` computes it (`byteRange.isEmpty || upperBound == bufferEnd`) and the
naive model must apply the same choice, or the two disagree on empty intervals at the upper
bound for reasons that are not a defect. **This test drives `IntervalTree` directly — test 16
is the one that goes through `BufferSnapshot` — so there is no `text.utf8Count` in scope.**
`bufferEnd` here is the model buffer length the generator already maintains to draw valid edit
offsets, read from that one variable by both sides; do not track a second length for the
query, which is how the two would drift apart. `checkInvariants()` is O(n) over the whole tree, so
call it **every hundredth edit and after every edit that empties an interval**, not every
round: this suite runs in the default `swift test` in a debug build, and 20,000 whole-tree
folds would make the gate pay for a check that a hundredth of the edits already covers. The generator must **assert the distribution it reached** —
M1.3's differential drew deletions from `Uniform[0,64]` against insertions from `Uniform[0,7]`
and spent its run on an 8-byte buffer. Include intervals that straddle, nest, share starts,
share ends, and are empty; assert that each of those classes actually occurred.

## 6. Mutation focus points

Designed here, executed by the main conversation after the reviewer has read the diff — the
implementer does not verify its own fix. Each must be **observable**: a test must fail.

1. Drop the third conjunct of `startMoves` — the clamp, in its implementation form (1.4).
   Test 4 must fail, and so must test 7's `(t, nil)` replace row.
2. Make `insertBeforeMarkers` stop overriding `frontAdvance`. Test 3 must fail.
3. Make the deletion rule consult `frontAdvance`. Test 5 must fail.
4. Fuse the two stages into one delta, as the M1.3 spec wrongly did. Tests 7 and 21 must
   fail — the differential reaches it because `applyEdit` takes a byte range and an inserted
   length in one call, so every random edit with both a non-empty range and a non-zero
   length is the replace shape this mutation corrupts.
5. Partition only the newcomers in the tie group, leaving residents in place. Test 12 must
   fail, and this is the mutation M1.3 says a spec written from memory gets wrong.
6. Change `maxEnd`'s combine to `max(a.maxEnd, b.maxEnd)` — dropping the affine shift. Tests
   8, 20 and 21 must fail, each for a reason written into its entry above: test 8 only because
   it builds both tie orders, test 21 only because it queries as well as comparing ranks.
   Test 11 will fail too, since two adjacent zero-length items with gaps 10 and 1 give a
   combined `maxEnd` of 10 against a `span` of 11, which `checkInvariants()` rejects — but
   **the query tests are the ones that must fail**: if only the invariant checker notices, the
   query tests are too weak to be protecting anything.
7. Two mutations against 1.6's three-part search, because it has two independent failure
   modes and no single assertion sees both. (a) **Filter piece 1's items by `end > lo`**,
   which is what a reader who remembers only the non-empty half of 1.7's rule would write.
   Note this is *narrower* than "drop every empty interval piece 1 returns": the filter only
   removes those with `start == lo`, since an empty interval strictly inside the range has
   `end == start > lo` and survives it. Use the filter, not the broader edit — a mutation
   with a larger blast radius than the defect it models proves less. Tests 8 and 20 must
   both fail on *results*: test 8's `overlays-in (3,7)` row contains `C(3,3)`, an empty
   interval sitting exactly at `lo` with `lo != hi`, which is piece 1's job and no tree shape
   can hide. (b) **Relax piece 2's prune to `maxEnd >= lo`.** No result changes, so every
   correctness test still passes, test 8 included — only test 20's **visit count** fails.
   That is why test 20 exists, and why it asserts a count as well as results: this is the
   mutation two drafts of this spec got wrong in opposite directions, and counting is the
   only thing that sees it.
8. Make the straddler update also shift the gap. **Test 21, the differential, is the
   guaranteed catch**, because it compares whole interval sets: corrupting one item's gap
   moves every later item's absolute start, which is a position error, not a `length` error.
   Test 13 catches it only if it asserts the neighbours' *positions* as well as the
   untouched `length` — so write it that way, and note that most conformance tests with a
   straddler (test 1's insert-at-middle row among them) would also fail.
9. Skip the `length` update for straddlers entirely. Tests 1 and 21 must fail.
10. In `visitItems`, descend into every subtree regardless of `descendInto`. Test 18 must fail
    — this is the M1.3 lesson that a visit count catches what an answer comparison cannot.

## 8. Known gaps to write into the file header

- Identity lookup is O(n) without the caller's start offset; M5 owns the index.
- Text properties are not here yet; the tree is shaped for them and the stickiness oracle is
  in this spec.
- A snapshot is a value, so forking one and editing both branches reuses interval IDs — the
  same gap `MarkerTree` records, and M1.5's branching undo owns it.
- Dropping a large interval tree is O(n) in distinct nodes, paid by whoever releases the last
  reference (4.5's "Close a large buffer" row).
- Interval endpoints must be UTF-8 scalar boundaries; the precondition lives in
  `BufferSnapshot` and, like `MarkerTree`'s, cannot be tested without an out-of-process crash
  harness this project does not have.
