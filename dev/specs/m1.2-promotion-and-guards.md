# M1.2 fix round: the promotion, and making its guard real

Written 2026-09-09 by the main conversation, after an architect pass and a mutation pass.
Addendum to `dev/specs/m1.2.md`; that spec's fixed clauses (its section 6) apply here
unchanged unless this file overrides them.

## Why this exists

M1.2's `SumTreeCursor` measured **31.8 ns/chunk called across a module boundary and 3.58
ns/chunk called from inside `Text`** — same process, same code, same rope, measured by the
main conversation. The algorithm was never the problem; it is *faster* than the flatten it
replaces (stage 2's 5.5-5.8 ns/chunk) once specialised. An architect pass then found that the
remedy this project had written down was wrong in an interesting way, and the corrections
below are the result.

**The promotion itself is already applied** (`Sources/Text/SumTreeCursor.swift`,
`Sources/Text/SumTree.swift`): 14 declarations gained `@usableFromInline`, `@inlinable`, or
both. **Nothing became `public`.** Do not redo it and do not extend it.

Three facts it established, which the tasks below act on:

1. **`@usableFromInline` on a `package` type is a promotion.** `dev/check-inlining.sh:23-29`
   records "`@inlinable` on a member of a `package` type is NOT inlined ... hence the
   convention promotes the *type*, not just the member". The conclusion is right and the
   implied remedy — make it `public` — is not the only one, nor the best one. Measured:
   `public` 3.56 ns/chunk, `@usableFromInline package` 3.49. Identical speed, no public API.
2. **The promotion unit is the whole call chain the benchmark walks, not the entry point.**
   Promoting `next()` alone and leaving `descendLeftmost`/`advanceToNextLeaf` merely visible
   recovered only ~35% (20.7 ns/chunk). Those two run once per leaf, i.e. once per <= 6
   chunks, and an opaque cross-module call there costs ~17 ns/chunk on its own.
3. **A plain-`package` `@inlinable` is not merely ineffective, it is unchecked.** The compiler
   does not verify `@inlinable` bodies while the enclosing type is plain `package`. Adding
   `@usableFromInline` to `TextMetric` immediately produced six errors of the form "struct
   `TextSummary` is package and cannot be referenced from an `@inlinable` function" — for code
   that compiles silently today.

## Task 1 — `TextMetric`: delete the annotation, do not promote

`Sources/Text/Rope.swift:50` declares `@frozen package enum TextMetric` and its `count(in:)`
carries `@inlinable`. By fact 3 that annotation is unverified, and by fact 1 it does nothing
across a boundary. Promoting it properly is not one attribute: `@usableFromInline` on the enum
forces `TextSummary` and its seven stored properties to follow, eight more declarations, and
buys nothing measurable — every caller of `count(in:)` is in-module, and the only cross-module
route is `Rope.convert`, measured at 0.5-0.8 us per call, against which a non-inlined call is
single-digit nanoseconds.

**Delete the `@inlinable`.** Replace the part of the doc comment that justifies it with one
sentence: `TextMetric` is a promotion candidate whose benchmark has not asked for it yet, and
the annotation was removed because a plain-`package` `@inlinable` is unchecked and reads as
"promoted" to anyone skimming. Keep `@frozen` and keep the rest of the comment — the argument
for one enum over twelve hand-written conversions is unaffected.

## Task 2 — make `dev/check-inlining.sh` a guard rather than a decoration

Three changes; the third is a pre-existing defect, not something this milestone introduced.

**2a. A third probe shape.** The script's probes today are `TextHotProbe` (`public` +
`@inlinable`) and a cold one. Neither is the shape actually shipping. Add a **warm** shape —
`@usableFromInline package struct` with an `@inlinable package` member, body byte-identical to
the existing probes — in `Sources/Text/InliningProbe.swift` and its `Lisp` counterpart, with
the matching caller in `Sources/Editor/InliningProbe.swift`, and assert its symbol is absent
from the caller's object file exactly as the hot probe's is. This is what proves the toolchain
still honours the shape `SumTreeCursor` uses.

**2b. A literal assertion over the real declarations.** Probes can never prove `SumTreeCursor`
still has the shape: deleting one attribute costs 8x, leaves every probe green and every test
passing. Add a check that greps the real declarations by name and fails if any has lost its
attribute — at minimum `SumTreeCursor`, `Node`, `Summary`, `Summable` for `@usableFromInline`,
and `next`, `descendLeftmost`, `advanceToNextLeaf` for `@inlinable`. Fail with a message
naming the file and the declaration.

Keep both 2a and 2b; they answer different questions and conflating them loses one. The probes
answer "does the compiler still do this?"; the greps answer "do we still ask it to?".

**2c. A pre-existing defect in the body-length counter.** The awk at
`dev/check-inlining.sh:49-54` sets `where` on the hot and cold struct headers and never resets
it, so **anything appended to a probe file after the cold probe is silently counted into the
cold body**. Adding a warm probe takes cold's count from 12 to 24 and the script then errors
about the *cold* body. Rewrite it to `next` on each recognised header, classify any other type
header as `other`, and fail if `other` is non-zero — so the next person adding a fourth shape
is told, rather than getting a misattributed count.

## Task 3 — give the perf ceiling teeth

`Tests/TextTests/ropePerfTests.swift`'s `iterationCost` asserts `chunks()` under **60
ns/chunk**. The de-promoted state measures 27-57 ns/chunk, so the gate is green with the
promotion silently reverted — the assertion cannot detect the thing this fix round exists to
protect.

Set the `chunks()` ceiling to **15 ns/chunk**. Justification, both bands measured on this
machine today: promoted 3.5-4.0 ns/chunk across quiet and noisy windows; de-promoted 27-57.
15 sits clear of both. Put that reasoning in the message the assertion prints, not only in a
comment, because the person who trips it needs it.

Leave the `bytes()` ceiling alone: it measured 0.15 ns/byte before and after, because
`bytes()` materialises its `[UInt8]` inside the module and hands back an array — the boundary
cost lands only on `chunks()`, which streams. Add that asymmetry as a comment; it is the shape
of every future decision here.

## Task 4 — replace the allocation defence, which a mutation defeated

`cursorTraversalAllocatesNothing` (`Tests/TextTests/conversionAndCursorTests.swift`) is
supposed to catch spec section 5's mutation "have the cursor materialise the current leaf's
items into an array on each descent". The main conversation ran that mutation and **it
survived**: all 99 tests passed.

The reason is that the test measures `malloc_zone_statistics`'s `blocks_in_use` **before and
after**, which is a net gauge. The mutation's arrays are transient — freed as frames pop — so
the net delta at the end stays under the bound while the allocation traffic it was written to
detect happens freely.

Replace it with a **deterministic** check rather than a bigger statistical bound: compare the
storage identity of what the cursor holds against the tree's own array, via
`withUnsafeBufferPointer { $0.baseAddress }`. If the cursor copied, the addresses differ; if it
shares, they are equal. This needs a small `@testable`-visible accessor on the cursor exposing
the current leaf's base address — that is a legitimate test hook, and it must be documented as
one.

Keep a statistical allocation check too if you judge it still worth having, but it is no
longer the defence, and its comment must stop claiming it is. **Verify your replacement by
running the mutation yourself**: apply "materialise per descent", confirm the new test fails,
restore with a file backup and prove the restore is byte-exact. Report the before/after.

## Task 5 — deliverable D, the seam policy revisit

`dev/specs/m1.2.md` section D. The previous round reported this as "declined" and then said
plainly it had run out of budget before measuring, which makes it **not revisited** rather than
considered. Do it properly: measure chunk fill on the boundary-aligned and scattered patterns
stage 2 used, with the bulk loader now in place, and decide with the numbers in front of you.
Declining again is a legitimate outcome; declining without measuring is not. Record the
numbers either way.
