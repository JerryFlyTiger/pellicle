# M1.3 spec: the marker tree

## 0. What already exists, so it is not reinvented

Two read-only surveys and one architecture pass established the following. Anchors are
`file:line` as of the commit this spec is written against (`5095d58`).

**The generic tree is fully generic, and needs no change.**

- `Summary` (`Sources/Text/SumTree.swift:82`) requires only `identity` and an associative
  `+`. `Summable` (`:88`) requires one associated type `Item_Summary: Summary` and one
  `var summary`. There are no default implementations and no other requirements.
- A `private struct` in a test file already conforms and drives the whole machinery
  (`Tests/TextTests/sumTreeTests.swift:9-21`). **A marker item needs `package` visibility
  and these two conformances and nothing else.** `Chunk` opts in the same way, from a
  same-file extension (`SumTree.swift:958`).
- `SumTreeCursor.seek` (`Sources/Text/SumTreeCursor.swift:131`) takes an arbitrary
  predicate over the item's own summary type. It is not tied to `TextSummary`.
- `SumTree.init(items:)` is an O(n) bottom-up bulk loader; `pathCopyEdit`
  (`SumTree.swift:914`) rebuilds only the O(h) path to one leaf.
- `branchingFactor = 6` is `internal` (`SumTree.swift:153`), readable from another file in
  the same module.

**Three preconditions this design lives or dies by. All three were read in the source, not
assumed.**

1. `pathCopyEdit` has `precondition(!predicate(.identity), "pathCopyEdit: predicate must be
   false of .identity")` (`SumTree.swift:918`). `split` and `splitFragments` say the same.
2. `SumTreeCursor.seek` preconditions the same thing **and** calls
   `preconditionFailure("SumTreeCursor.seek: predicate never true of the tree's own total")`
   when the predicate never triggers (`SumTreeCursor.swift:139`). "No marker at or after p"
   is the ordinary case for an edit near the end of a buffer, so `seek` may never be called
   unguarded.
3. `split` folds the item where the predicate flips into the **left** result
   (`SumTree.swift:755`, `leftBuilder.push(.items(ArraySlice([item])))`).

**The rope has exactly one funnel.** Every mutator — `insert`, `removeSubrange`, `append`,
both `replaceSubrange` overloads — reaches `replaceSubrange(_ byteRange: Range<Int>, with
other: Rope)` (`Sources/Text/Rope.swift:835-845`), which dispatches to `tryLeafLocalReplace`
(fast path, ≤ 64 bytes, one leaf) or `generalPathReplace`. That call site is the only place
where both `byteRange` and `other.utf8Count` are in scope. **Single-character edits take the
fast path**, so anything hooked deeper than that funnel misses the common case entirely.

**What does not exist.** No `TextBuffer`, no `BufferSnapshot`, no clock, no edit log, no
delta type; `Rope` is a struct over one `SumTree<Chunk>` and a snapshot today is `let before
= rope` (`Rope.swift:20-23`). Nothing in the rope models what happens to a position inside a
deleted range. There is no marker or anchor code anywhere.

**One correction to the M1.2 handover.** It records `combineUnderflowedSiblings` as an
"unchecked join point that still wants a `Summable` item-merge hook". The function
(`SumTree.swift:468`) does pure array concatenation and a midpoint split and calls nothing
on `Item`; **no such hook exists anywhere, declared or invoked.** M1.3 does not need one and
does not add one. Section 4 records the correction.

## 1. The design, and why

**Markers are stored gap-encoded in a `SumTree<MarkerRecord>` ordered by a doubled key.**

```
key = 2 * byteOffset + biasRank        biasRank: .left = 0, .right = 1
byteOffset = key >> 1                  biasRank = key & 1
```

`.left` is GNU's `marker-insertion-type nil` (stays before inserted text) and is the
default; `.right` is type `t`. **The bias is not stored separately from the key**, so the
two cannot disagree.

```swift
package struct MarkerSummary: Summary {   // count = order statistic, span = prefix sum of keys
    package var count: Int
    package var span: Int
}
package struct MarkerRecord: Summable {   // 16 bytes
    package var gap: Int                  // this key minus the previous key, >= 0
    package var id: MarkerID              // UInt64, monotone, never reused
    package var summary: MarkerSummary { MarkerSummary(count: 1, span: gap) }
}
```

An item's absolute key is the prefix sum of gaps up to and including it, which is exactly
what the cursor/`find` machinery threads. **The seek predicate is**

```swift
{ $0.count > 0 && $0.span >= K }
```

The `count > 0` clause is not decoration: `.identity` is `(0, 0)` and `0 >= 0` is true, so
without it every edit at byte offset 0 — the single most common edit in an editor — trips
precondition (1) above. The predicate is monotone because both fields are non-decreasing.

**Why gap encoding rather than the lazily propagated offsets 4.5's prose describes.**
Because gaps are relative, "add δ to every key at or after K" changes **exactly one item**:
the first with `key >= K`. That is one `pathCopyEdit` descent — about seven node
reconstructions at a million markers — independent of how many markers follow. Lazy
propagation is the mutable-tree way to buy the same thing, and it is in tension with
persistence by construction: pushing a pending delta into children mutates nodes that older
snapshots share, and path-copying the push-down makes it not lazy, only a differently
spelled path copy. It would also need a slot on `Node` (`SumTree.swift:96`), which is shared
with the rope and is one of the declarations `dev/check-inlining.sh` guards by name.
**The requirement in 4.5 is the complexity bound, not the mechanism**; section 4 amends the
prose to say so.

**Why the key is doubled.** Without doubling, an insertion at a position where several
markers sit has to split that tie group by bias, which is O(m) in the group and needs bias
to be a seekable summary dimension. With doubling the group is *already stored partitioned*
— every `.left` marker at `p` has key `2p`, every `.right` one has `2p+1`, contiguous and
ordered — so the whole of GNU's insertion-type behaviour becomes a choice of which numeric
key to seek to.

## 2. Deliverables

### A. `Sources/Text/MarkerTree.swift`

`MarkerID` (`UInt64`), `MarkerBias`, `MarkerSummary`, `MarkerRecord` with their conformances
declared in this new file — `SumTree.swift` is not edited — and a `MarkerTree` wrapper
struct holding a `private var tree: SumTree<MarkerRecord>`.

**`MarkerTree` must never expose the underlying `SumTree`.** Gaps are relative, so
`SumTree.concat` (`:800`) is not marker-safe: joining two marker trees produces silently
wrong positions everywhere after the seam unless the right-hand tree's first gap is rebased
against the left-hand total span. Every split/concat inside `MarkerTree` rebases; no caller
can reach one that does not.

API, all O(log n) unless stated:

- `init()`, `init(sortedMarkers:)` — bulk, via `SumTree.init(items:)`, O(n). The input is
  `(byteOffset, bias, id)` in non-decreasing key order; the initialiser computes gaps and
  preconditions the ordering.
- `count: Int`, `isEmpty: Bool`
- `position(ofRank r: Int) -> Int` and `bias(ofRank:) -> MarkerBias`, `id(ofRank:) -> MarkerID`
- `rank(atOrAfterKey k: Int) -> Int` — the order statistic; `count` when nothing is at or after.
- `markers(in byteRange: Range<Int>) -> [ (offset: Int, bias: MarkerBias, id: MarkerID) ]` —
  O(log n + k), via a rank query then a cursor walk. **Guard the cursor**: check `rank <
  count` before seeking, per precondition (2).
- `inserting(byteOffset:bias:id:) -> MarkerTree`
- `removing(id:atByteOffset:) -> MarkerTree`
- `checkInvariants() throws`

### B. `MarkerTree.applyEdit(byteRange:insertedLength:insertBeforeMarkers:)`

The one operation the milestone is judged on. **It is two stages composed, not one fused
pass** — see the correction note below, which the implementation found by running the oracle.

*Stage 1, delete and collapse*, with `lo = byteRange.lowerBound`, `hi = byteRange.upperBound`:

| marker key `k` | new key |
|---|---|
| `k < 2*lo + 2` (offset ≤ lo) | unchanged |
| `2*lo + 2 <= k <= 2*hi + 1` (lo < offset ≤ hi) | `2*lo + (k & 1)` — collapse, bias kept |
| `k >= 2*hi + 2` (offset > hi) | `k - 2*(hi - lo)` |

*Stage 2, insert*, with `L = insertedLength`: add `2*L` to the first item with `key >= B`,
where `B = 2*lo + 1` normally and `B = 2*lo` when `insertBeforeMarkers` is true.

A **pure insertion** (`lo == hi`) is stage 2 alone; a **pure deletion** (`L == 0`) is stage 1
alone. Both named perf cases below therefore reduce to exactly one stage, so neither
benchmark's shape depends on this correction.

> **Correction, 2026-09-10.** This section first described a single fused pass with one
> `Δ = 2 * (L - (hi - lo))` applied uniformly. That does not reproduce this spec's own
> `replace-at-marker` oracle row. With `lo=2, hi=5, L=4` (0-based bytes), a `.right` marker
> at `lo` has key 5, which the fused table's first row leaves unchanged at offset 2; GNU puts
> it at offset 6. The reason is that **GNU has no atomic replace primitive with its own marker
> rule** — a replace is a delete followed by an insert, each adjusting markers by its own rule
> in sequence, so a marker that survives the delete sitting at `lo` is afterwards
> indistinguishable from any other marker at `lo` and is pushed by the insertion. A second
> probe confirms the mechanism directly: a `.right` marker strictly *inside* the deleted
> range, which the fused table says merely collapses to `lo`, is pushed by the full inserted
> length. Both probes are transcribed in `Sources/Text/MarkerTree.swift`'s header.
>
> **A second correction, inside stage 1, not oracle-checkable.** The collapse must extract
> and repartition a group that also includes markers *already* sitting exactly at `lo`, both
> biases — not only those collapsing in from inside the range or from `hi`. Repartitioning
> the narrower group can place a newly-collapsed `.left` marker (key `2*lo`) after an
> already-resident `.right` marker at `lo` (key `2*lo + 1`) that the narrower group leaves
> alone, which breaks non-decreasing key order and with it the non-negative-gap invariant.
> GNU exposes no observable order among markers tied at one position, so this one is settled
> by the tree's own `checkInvariants()` under the randomised property test, not by an oracle.
> Say so rather than implying oracle backing it does not have.

Two paths, and the fast one must exist:

- **No marker in the collapse range** (always true for a pure insertion): one rank query and
  one `pathCopyEdit` that adds `Δ` to a single item's gap. If no item has `key >= B` there
  is nothing to do at all. **O(log n), and this is the path the perf test measures.**
- **k markers in the collapse range**: rank-query both ends, `split` twice to extract the
  group, stably partition it by `k & 1` (all rank 0, then all rank 1), rewrite the group's
  gaps (first gets `2*lo + rank − previousKey`, the rest 0 or 1), rebase the tail's first
  gap by `Δ`, `concat`. **O(k + log n), and that is inherent** — no representation makes k
  distinct positions become equal in less than O(k) without a retained history, which 4.5
  rejects. GNU pays linearly here too.

`split`'s flip-item-goes-left rule (precondition (3)) means extracting "items from rank r"
is *not* `split(where: key >= K)`. Use the rank: `find` the key to read the prefix `count`,
then `split(where: { $0.count >= rank })`, which `split` already special-cases correctly at
rank 0.

### C. `Sources/Text/BufferSnapshot.swift`

```swift
package struct BufferSnapshot: Sendable {
    package private(set) var text: Rope
    package private(set) var markers: MarkerTree
    package mutating func replaceSubrange(
        _ byteRange: Range<Int>, with other: Rope, insertBeforeMarkers: Bool = false)
    package mutating func createMarker(atByteOffset: Int, bias: MarkerBias) -> MarkerID
}
```

Rationale for the shape, so it is not relitigated:

- **Not a field on `Rope`.** `Rope` is `Equatable` comparing text (`Rope.swift:1099`); two
  ropes with equal text and different markers would break that contract, and `Rope.slice`
  and the `other:` argument of `replaceSubrange` would each need a marker answer that has no
  sensible one.
- **Not a free-standing tree with deferred pairing.** The rope has exactly one edit funnel;
  if markers are free-standing, every caller must remember a second call with the same
  arguments. That desync is silent and position-dependent, and M1.4 and M1.5 would each add
  another chance to forget.
- **Not `TextBuffer` yet.** 4.5 sketches it as a class with `overlays`, `history` and
  `clock` — three fields that do not exist. A value type with a `mutating` edit gives
  atomicity without inventing an ownership model before there is an owner.
- **No `clock`/`version` field.** Nothing would read it, and an unread field is a standing
  chance to be wrong. M1.5 adds it with its first consumer.
- The pairing also buys a real invariant: a marker offset must be a UTF-8 scalar boundary,
  which `MarkerTree` alone cannot check because it does not hold the text.
  `createMarker` preconditions it via `Rope.isScalarBoundary` (`Rope.swift:373`).
- The monotone ID counter lives on `BufferSnapshot`.

## 3. Explicitly out of scope, with the reason

- **Resolving an anchor by marker identity, and the `Anchor` type itself.** The marker tree
  is ordered by position; an edit touches a contiguous range in position order and an
  arbitrary subset in ID order, so no ID-ordered structure absorbs an edit in less than O(k)
  unless what it stores per marker is shift-invariant. The only shift-invariant quantities
  are rank (destroyed by marker creation) and relative order (needs order-maintenance
  labelling plus a persistent ID→label map — a milestone of its own). No M1.4 or M1.5 client
  asks "where is marker #N": overlays are keyed by position and undo stores positions in
  edit records. The real client is the Elisp `marker` object, which 4.5 already places
  behind an identity wrapper. **Shipping an `Anchor` with no honest `resolve` would be worse
  than not shipping it.** `MarkerRecord` carries `id` from day one and the key ordering is
  total and deterministic, so the later index has a well-defined target.
- Elisp `marker` objects, `set-marker`, insertion-type mutation, marker arithmetic (M5).
- `TextBuffer`, overlays, history, clock (M1.4, M1.5).
- Giving the marker tree its own branching factor. `branchingFactor` is one module-wide
  `internal let`; per-item B would mean editing shared machinery. Measure at B = 6, record
  the number, revisit only if it demands it.
- Any edit to `Rope.swift`, `SumTree.swift`, `SumTreeCursor.swift`, `Chunk.swift` or
  `TextSummary.swift` **except** one comment: `pathCopyEdit`'s `4 * branchingFactor`
  growth precondition (`SumTree.swift:514-516`) is written as though
  `Rope.tryLeafLocalReplace` were its only caller's caller. The marker caller stays well
  inside the bound (at most 2B+1 items), but the comment becomes stale; correct it in place
  and change no code.

## 6. Mutation focus points

Designed here, executed by the main conversation. **Do not run a mutation pass yourself.**

1. **Drop `count > 0` from the seek predicate.** An edit at byte offset 0 must then trip
   `pathCopyEdit`'s identity precondition. If the test suite still passes, no test edits at
   offset 0 — which would be the commonest edit in a real editor going unexercised.
2. **Change the insertion boundary from `2*p + 1` to `2*p`.** A `.left` marker sitting
   exactly at the insertion point must then wrongly advance. This is the `>` versus `>=`
   boundary error the M1.2 spec names as its archetype, and the oracle row
   `insert-at-marker type-nil=3` is what catches it.
3. **Change the collapse upper bound from `<= 2*hi + 1` to `< 2*hi`.** A marker exactly at
   `byteRange.upperBound` must then wrongly survive at its old offset instead of collapsing
   to `lo`. The oracle row `marker-at-bounds at-hi=3` is what catches it. This is the single
   easiest rule in the table to get wrong, because "the range is half-open" reads as though
   the upper bound is excluded, and for *markers* it is not.
4. **Delete the gap rebase after a `concat`.** Positions after the seam must go wrong. A
   round-trip test that only ever splits at the tree's end will still pass, so the test that
   catches this has to split in the middle.
5. **Make the collapse partition unstable** (sort by rank without preserving order within a
   rank). Marker *positions* stay correct and only the relative order of same-key markers
   changes, so a test asserting positions alone will not catch it; the test that does has to
   assert the id order within a tie group.
6. **Replace `split(where: count >= rank)` with `split(where: span >= key)`.** The flip item
   lands on the wrong side, off by one marker at the boundary.
7. **Remove the `rank < count` guard before a cursor seek.** An edit past the last marker
   must then hit `SumTreeCursor.seek`'s `preconditionFailure`.

## 8. Known gaps to write into the file header

- Marker offsets are UTF-8 byte offsets and must be scalar boundaries. The scalar-boundary
  preconditions are **untested by construction**, exactly as `Rope.swift:30-39` already
  records for its own: every randomised test draws offsets from a metric's valid-boundary
  set, so reaching the trap would need an out-of-process crash harness this project does not
  have. Say so up front rather than discovering it later.
- Keys are `2 * byteOffset`, so a 2 GB buffer reaches about 2³². `Int` is 64-bit on this
  target; state the bound so M1.6's mmap view does not silently break it.
- A snapshot is a value, so forking one and editing both branches reuses marker IDs. M1.5's
  branching undo is the milestone that must decide the allocation story.
- O(k) collapse when a deletion contains k markers, per section 2.B.
