## 0. What already exists, so it is not reinvented

Read this before designing anything. The reconnaissance found that three of the four things a
naive reading of "M1.2" would build are already built:

- **The summary fields are complete.** `TextSummary` (`Sources/Text/TextSummary.swift:19`)
  already carries `utf8`, `utf16`, `scalars`, `lines`, `firstLineLen`, `lastLineLen`,
  `maxLineLen`. M1.1 added `scalars` deliberately so that adding it later would not mean
  recomputing every leaf summary (`PLAN.md section 11, the M1.1 record`). **No new summary field is needed.**
- **The generic navigation primitive is complete.** `SumTree.find(where:)`
  (`Sources/Text/SumTree.swift:704`) takes any monotone predicate over the accumulated summary,
  returns the triggering item plus its prefix summary, runs in O(h), and **allocates nothing** —
  `findNode` (`SumTree.swift:396-434`) never calls `makeLeaf`/`makeInterior`. **Do not write a
  new tree walk for conversions.**
- **The `Rope`-layer routing pattern is established, for one metric only.** `Rope.locate`
  (`Sources/Text/Rope.swift:222-259`) is the byte-offset router built on `find`. The line,
  UTF-16 and scalar routers do not exist and are modelled on it.
- **There is no cursor of any kind.** No `IteratorProtocol` conformance, no `Sequence`
  conformance that streams, no type named `Cursor`. `Rope.chunks()` (`Rope.swift:752`) returns
  `tree.items()`, which flattens the whole tree into one array (`SumTree.swift:722-737`). The
  cursor is written from scratch.

## 1. Deliverables

### A. Metric conversions

Convert an offset in any of four metrics to any other, plus line/column.

**Decision — one metric abstraction, not eight hand-written functions.** Introduce
`TextMetric`, a `@frozen enum` with cases `utf8`, `utf16`, `scalars`, `lines`. Give it two
operations: reading its count out of a `TextSummary`, and a chunk-local scan that converts
within one `Chunk`. Everything else is one generic routine,
`Rope.convert(offset:from:to:)`, built on `SumTree.find(where:)` with the predicate
`{ metric.count(in: $0) > offset }`. The named APIs are thin wrappers over it.

An enum with an `@inlinable` switch, not a protocol: this is a hot path (`PLAN.md 4.3, the hot-path promotion candidates`
lists the snapshot cursor among the promotion candidates for `dev/check-inlining.sh`), and a
protocol boundary was measured non-devirtualised in every configuration in M0
(`PLAN.md 4.16` decision log). Eight hand-written conversions were rejected for the reason
stage 2 gave when it deleted `buildFromNodes`: one implementation of a rebalancing idea, not
two.

Public surface on `Rope` (names are the spec's, not a suggestion):

```
func convert(offset: Int, from: TextMetric, to: TextMetric) -> Int
func lineAndByteColumn(atByteOffset: Int) -> (line: Int, byteColumn: Int)   // both 0-based
func byteOffset(line: Int, byteColumn: Int) -> Int
func byteOffsetOfLineStart(_ line: Int) -> Int
var lineCount: Int   // summary.lines + 1
```

Columns come out of the primitive in **UTF-8 bytes**, because that is the unit
`firstLineLen`/`lastLineLen`/`maxLineLen` are already stored in
(`Sources/Text/TextSummary.swift:4-6`). A caller wanting an LSP (UTF-16) or Emacs (scalar)
column composes `lineAndByteColumn` with `convert`. Do not add a second column unit in this
sub-milestone; add it when a real caller exists, and record the decision either way.

Complexity: O(log n) to reach the chunk, then O(chunk) within it — bounded by 64 bytes, so
O(log n) overall. This is what `PLAN.md 4.5, on summaries giving O(log n) conversion` promises and what `PLAN.md 4.8, on LSP UTF-16 positions` (LSP: "UTF-16
positions are converted by rope summaries, never by scanning") depends on. A conversion that
scans from the start of the buffer fails this deliverable even if its answers are right.

**Boundary contract, and a known gap it inherits.** Offsets are required to sit on scalar
boundaries, as the rest of `Rope` requires (`Sources/Text/Rope.swift:4-6`). Use `precondition`
for violations, consistent with the file. **Record in the file header that these new
preconditions have no regression test for the same reason the two in `generalPathReplace` do
not** (`PLAN.md section 11, the M1.1b stage 2 record on the untested preconditions`): every randomised test draws offsets from `scalarBoundaries`, and
asserting a trap needs an out-of-process crash harness this project does not have. Say it in
the header rather than letting a later review rediscover it.

### B. Bottom-up bulk loader

`Rope(String)` runs at ~91 MB/s: 1 MB takes ~11 ms, and a 10 MB file would spend 110 ms in
construction before anything else happens (`PLAN.md section 11, the M1.1b stage 1 record's known gaps`). The cause is
`SumTree.build` (`Sources/Text/SumTree.swift:612-620`), which halves recursively and joins
through `concat`; the file's own comment admits it was chosen for simplicity
(`SumTree.swift:44-46`).

**Decision — fix it in the generic `SumTree` layer, not in `Rope`.** `SumTree.build` is the
single shared bottleneck: `Rope.buildTree`, `Rope(unmergedChunks:)` and `Rope.splitTree`'s
single-chunk construction all reach it today, and M1.3's marker tree will be the fourth
client. A `Rope`-only fast path would leave the same defect in place for the next `Item` type.
Keep the `SumTree(items:)` signature; replace the body with a true bottom-up level-by-level
build: pack items into leaves of the target fill, then repeatedly pack the previous level's
nodes into interiors until one root remains.

`TreeBuilder` is **not** obviously the right vehicle and reusing it is not required. Its
`push` descends the accumulator's right spine to a matching height (`SumTree.swift:167-173`)
and its own documentation says it is not an amortised-O(1) per-height-slot builder; feeding it
a whole leaf level one node at a time may reproduce the cost being removed. Measure before
committing to it. If a separate bottom-up routine is cleaner, write one — but then say in the
record why there are two construction paths, because stage 2's stated principle was to end up
with one.

Acceptance, stated absolutely rather than as a ratio (`CLAUDE.md:113-134`):

- 1 MB `Rope(String)` in **under 3 ms**, 10 MB in **under 30 ms**, `-O -wmo`, one process,
  median of at least three runs.
- **Linearity**: the 10 MB time divided by the 1 MB time is **at most 12**. A ratio alone would
  pass for a uniformly slow implementation, which is exactly the trap M1.1's scaling test fell
  into (`CLAUDE.md`, "How to measure"); the absolute bound above is the real gate and this is
  the shape check on top of it.
- The resulting tree passes `checkTreeInvariants()` and is `Equatable`-equal to a tree built by
  the old path for the same input. Add this as a differential test, not only an eyeball.

There is **no bulk-build benchmark today** — 91 MB/s lives only in prose (`PLAN.md section 11, the M1.1b stage 1 record's known gaps`), not
in any `@Test`. Write one, modelled on `iterationCost`/`scalingRatio` in
`Tests/TextTests/ropePerfTests.swift`, gated by the existing `PELLICLE_PERF` + release tag
mechanism in `perfTag.swift`.

### C. Lazy cursor

`SumTree.items()` and everything on it (`Rope.chunks()`, `Rope.bytes()`, `Rope.toString()`)
flatten the entire tree into an array first; `bytes()` allocates twice. Stage 2 measured the
flatten at 6.4 ns/chunk and 0.176 ns/byte (`PLAN.md section 11, the M1.1b stage 2 record's measurements`); the benchmark in the tree
records 5.5-5.8 ns/chunk (`Tests/TextTests/ropePerfTests.swift:316-318`). Treat the in-tree
numbers as the baseline to beat, since they are reproducible.

Build `SumTreeCursor<Item>` at the generic layer, with `Rope` wrappers. Requirements:

- **Allocates nothing per traversal.** The descent stack is bounded by tree height; size it
  from the height bound, not from the item count. A cursor that allocates an array of nodes
  has missed the point.
- Conforms to `IteratorProtocol`/`Sequence` so `for chunk in rope.chunks()` streams. Re-express
  `chunks()` and `bytes()` on it. `toString()` legitimately allocates its result, but must not
  allocate the intermediate `[Chunk]`.
- **Seekable by a metric**, reusing deliverable A's `TextMetric`: positioning the cursor at an
  offset is the same descent `find` does, kept resumable. This is what makes A cheap when a
  caller converts many offsets in sequence, and it is the shape `PLAN.md 4.3, the hot-path promotion candidates` names ("the
  `Text` snapshot cursor and its chunk-batch iteration") as a future inlining-promotion
  candidate.
- Value semantics consistent with the rest of the module: a cursor over a snapshot must not
  observe later edits to the rope it came from.

Acceptance: at or below the recorded per-chunk and per-byte costs, measured the same way, with
**zero allocation during traversal** demonstrated rather than asserted in prose — a test that
traverses a large rope twice and shows the second traversal does no additional allocation, or
an equivalent observation the record explains.

### D. Seam policy revisit (stage 2 deferred this here explicitly)

Stage 2 declined a fix and named M1.2 as the place to reconsider it: the seam merge declines
when the boundary chunk is buried in a `Fragment.nodes` group, costing ~12% more chunks per
byte on a boundary-aligned adversarial pattern while being *better* than the old code on a
scattered one. Its recorded fix direction is to "peel the boundary item out of a `.nodes`
fragment by descending its right (or left) spine and re-emitting the ancestors as fragments,
which is O(h) and needs no rebuild", and the record says "Revisit it in M1.2 alongside the bulk
loader, where chunk fill is already on the table" (`PLAN.md section 11, the M1.1b stage 2 record's seam-policy decline`).

This is a **revisit, not a mandate**. Chunk fill is on the table because the bulk loader chooses
a fill target. Decide it with the measurement in front of you and record the decision either
way. Declining again, with a reason, is a legitimate outcome.

### E. Re-run the `B` sweep after the cursor lands

`B = 6` was re-swept in stage 2 and kept, with one stated exception: "re-run it when the cursor
lands, because that is the event that could move the answer" (`PLAN.md section 11, the M1.1b stage 2 record's `B` sweep`, restated in
the handover at `PLAN.md's handover as of stage 2`). The reason is that iteration wanted a larger `B` and the
fast path wanted a smaller one, and iteration's cost was measured on `chunks()` — the exact
operation deliverable C replaces.

This is an **acceptance step of M1.2, not optional**. Do not redo the parts stage 2 already
settled; re-run the sweep on the axes the cursor changes, following the sweep protocol in the
measurement memory (build once per value, at least three runs per binary, compare medians,
treat the within-binary spread as the noise floor). Changing `B` invalidates dozens of
hard-coded `B = 6` fixtures in `sumTreeTests.swift`; if the answer moves, that cost is part of
the decision and goes in the record.

## 3. Tests

Follow the module's existing conventions rather than inventing new ones.

- **Correctness, hand-written fixtures.** Extend `Tests/TextTests/textSummaryTests.swift`'s
  style (fixture plus randomised-split associativity) with a new suite for conversions. Cover
  at minimum: empty rope; no trailing newline; leading newline; consecutive newlines; CRLF;
  4-byte scalars where `utf8`, `utf16` and `scalars` all disagree; an offset exactly on a chunk
  boundary; an offset on the last byte; `lineCount` on a buffer with and without a trailing
  newline.
- **Round-trip property.** For every ordered pair of metrics, converting an offset out and back
  is the identity, over randomised ropes and offsets drawn from that metric's own boundaries.
- **Differential property against the naive model.** `ropeTests.swift:546` already runs ~2,000
  operations against a naive `[UInt8]` model. Extend that harness: after each operation, check
  each conversion against an independently computed answer over the model array (count `\n`,
  count non-continuation bytes, count UTF-16 units) rather than against the rope's own
  summaries — a test that asks the summaries to check the summaries proves nothing.
- **Oracle for line/column.** The project's rule is that no specification is written from
  memory (`CLAUDE.md`, "Three oracles"). Generate line/column expectations for at least one
  real fixture with `emacs -Q --batch` (`line-number-at-pos`, `current-column`) and commit the
  transcript, so the 1-based/0-based and end-of-buffer conventions are settled by the oracle
  and not by the implementer's assumption. **State the base convention explicitly in the API
  docs**: this spec's `line` and `byteColumn` are 0-based, and GNU's are 1-based for lines, so
  the transcript will need the offset applied — do that in the test, visibly, not silently in
  the implementation.
- **Benchmarks**, all under the existing `PELLICLE_PERF` release gate: bulk-build throughput at
  1 MB and 10 MB (new); cursor traversal per chunk and per byte (extend `iterationCost`);
  conversion cost at 1 MB and 10 MB, asserted as an absolute bound.

## 5. Mutation focus points

Where a wrong implementation would still pass a careless test:

- **Off-by-one at the metric boundary.** Change `>` to `>=` in the conversion predicate. A test
  that only converts mid-chunk offsets will not notice; a test that converts an offset exactly
  on a chunk boundary and exactly on a line start will.
- **Column base.** Return `byteColumn + 1`. Only the oracle transcript catches this.
- **Bulk loader fill target.** Build leaves at `B` instead of the chosen fill. Invariants still
  pass (`B...2B` is legal), the tree is still correct, and only a fill or chunk-count assertion
  notices. Decide what the loader's target fill is and assert it.
- **Bulk loader linearity.** Keep the recursive halving but memoise something so the 1 MB case
  passes the absolute bound while 10 MB still degrades. The linearity check is what catches it.
- **Cursor allocation.** Have the cursor materialise the current leaf's items into an array on
  each descent. Every correctness test still passes and the per-chunk timing may barely move at
  small sizes. The zero-allocation observation is the only defence.
- **Cursor staleness.** Let the cursor hold a reference that observes later edits. A test that
  traverses a snapshot taken before an edit is the defence.

## 6. Fixed clauses for the implementer

- **Scope**: `Sources/Text/*.swift` and `Tests/TextTests/*.swift` only. Do not touch `PLAN.md`,
  `README.md`, `CLAUDE.md`, `dev/`, or any other module.
- **No git writes**: `commit`, `push`, `reset`, `checkout --`, `restore`, `clean` are
  forbidden.
- **No sub-delegation**: do not spawn agents. If you cannot finish, stop and report.
- **Foreground execution only**: no `nohup`, no `&` followed by waiting for a notification that
  will never arrive. Split anything over ten minutes into steps.
- **Effort budget and stop-loss**: if **three** rounds of the test loop are not green, stop and
  report the state and what remains. If more than **six** files need changes, stop and report
  the scope change before continuing.
- **Do not run the full gate and do not report pass/fail.** Run only the targeted tests you
  need. Attach the exact command line and the last lines of raw output, and state whether you
  ran the whole suite or a filter — the two can disagree. Never write "verified", "all green"
  or "confirmed".
- **Do not run a mutation pass**: section 5 is executed by the main conversation, because an
  implementer must not verify its own fix. Self-check with a file backup, a targeted edit and
  `touch`.
- **Performance numbers you report are a sanity check only.** The main conversation re-measures
  every before/after on this machine. Still follow the protocol when you measure: `-O -wmo` via
  `swift build -c release`, A/B within one process, absolute bounds, medians of at least three
  runs. `swift test` builds in debug, so a number from an ungated test is not evidence.
- **"Flaky" requires evidence**: no "environmental noise" without an observation that
  distinguishes it. Re-run a dozen times first.
- **Wrap-up**: `git status` converged to the original file set plus the files this spec names.
  No scratch files left behind.
