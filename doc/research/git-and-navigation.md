## A. Git integration at Magit level

### A1. What makes Magit best-in-class

Note: `magit.vc` returned HTTP 404 on every path tried during this session (manual root, `Staging-and-Committing.html`, `Staging-and-Unstaging.html`) — the site may have restructured or been temporarily unreachable. Feature claims below rely on well-established prior knowledge of Magit plus the `transient` GitHub README (fetched successfully) and are marked **medium confidence** where the primary manual could not be confirmed live in this session.

Feature inventory (medium confidence unless noted):

- **Status buffer with sections** — a single collapsible-outline buffer (untracked / unstaged / staged / stashes / recent commits / branch tracking info) that is the hub for almost every git action. Everything is a "magit-section" with a mode-line-free, keyboard-navigable tree; sections lazily populate. This is the core UX insight: one buffer, one mental model, instead of separate modal dialogs per operation.
- **Hunk/line-level staging** (medium confidence, could not confirm live but is extremely well-documented general knowledge): Magit renders the unified diff directly in the status/diff buffer and lets the user stage/unstage/discard at the level of a whole file, a whole hunk, or an arbitrary region selection *within* a hunk. For a full hunk it can use `git apply --cached` on the hunk's patch text, or index plumbing; for a sub-hunk region selection, Magit constructs a synthetic patch (splits the hunk so only the selected lines are "added"/"removed" and the rest treated as context) and feeds that synthetic patch to `git apply --cached` (and `--reverse` for unstaging, `--index`/working tree for discarding). This "diff buffer IS the interaction surface" pattern (no separate hunk list) is the single highest-leverage feature to copy.
- **Commit message buffer** — a separate buffer (COMMIT_EDITMSG via `GIT_EDITOR`) with font-locking of the summary/body convention, verification (50/72 line-length highlighting), and the diff of what's about to be committed visible in another window while composing.
- **Log/reflog/blame** — `git log --graph`-style rendering with sections per commit, expandable to show the diff inline; reflog browsed the same way; blame shown as an overlay/margin annotation on the buffer with the ability to step to a blame chunk's commit and re-blame at the parent (blame "time travel").
- **Interactive rebase editor** — Magit replaces the todo-file text edit with a structured buffer: each pick/squash/fixup/drop line is a section that can be reordered with keybindings, retagged (`r` reword, `s` squash, etc.) without hand-editing text, then written out and fed to git via `GIT_SEQUENCE_EDITOR` pointed at a small script/executable that Magit controls. This is directly implementable: pellicle can set `GIT_SEQUENCE_EDITOR` to a helper that reads the desired sequence from a temp file the UI wrote, or writes the buffer contents straight into the `rebase-todo` path Git already created before invoking the editor.
- **Stash, branches, remotes** — all exposed as sections in the status buffer or dedicated list buffers, with the same "point at a line, act on it" model.
- **Diff rendering** — word-level highlighting (git's own `--color-words`/`--word-diff` machinery, which Magit consumes and re-renders with faces instead of ANSI colors), plus a refined "highlight the smallest changed region" pass; side-by-side is not Magit's default (Emacs is fundamentally a single-column text UI) — this is one place a native macOS UI can exceed Magit rather than copy it.
- **Transient-style menus** (confirmed via GitHub README fetch, high confidence): `transient` is a standalone library (originally built for Magit, later split out) providing keyboard-driven, self-documenting command palettes with prefix/suffix/infix arguments — press a key to open a menu (e.g. `l` for "log"), the menu shows all relevant flags/args as toggleable infixes with current state, and a final key invokes the command with the assembled argument list. This solves "git has too many flags to remember" better than either a modal dialog (loses discoverability of combinations) or a plain CLI (loses discoverability of flags at all). It is a clean model to reimplement natively (e.g. a floating palette view driven by a small declarative menu spec, with keyboard-first navigation and visible current-argument state) rather than pixel-copy Emacs's rendering.
- **Forge (PR/issue) integration** — a separate package layering GitHub/GitLab/etc. issues and PRs into the same section-based browsing model, backed by each host's REST/GraphQL API with a local SQLite cache for offline browsing. Lower priority than the core git primitives.
- **3-way merge/conflict UI** — Magit shows conflicted files as sections in status and lets the user jump into the conflict markers in the buffer; it does not have a dedicated 3-pane merge view (this is another spot where Zed/VS Code's side-by-side 3-way merge editor is more advanced and worth adopting rather than copying Magit exactly).

### A2. Implementation choice: git CLI vs libgit2/SwiftGit2

**git status --porcelain=v2** (confirmed via git-scm.com, high confidence): a machine-parseable, extensible line format with `#` header lines for branch/upstream/ahead-behind/stash-count, then per-entry lines (`1` ordinary changed, `2` renamed/copied with a similarity score, `u` unmerged with 3-way mode/hash fields, `?` untracked, `!` ignored). Modes and object hashes for HEAD/index/worktree are all present per entry, which is enough to reconstruct the whole status-buffer tree without any additional `git diff --stat` calls.

**--no-optional-locks** (confirmed, high confidence): by default `git status` opportunistically refreshes and rewrites the on-disk index (updating cached stat info) as a side effect, taking a write lock. `--no-optional-locks` skips that rewrite, which is exactly what a UI wants when it polls status from a background timer/FSEvents callback — it avoids fighting the user's own foreground `git commit`/`git add` for the index lock, and avoids doing disk writes purely for a read-oriented poll.

**Diff / word-diff** (confirmed, high confidence): `git diff --word-diff[=color|plain|porcelain]` and `--color-words[=<regex>]` compute a word-level diff *within* each line/hunk (default word boundary = whitespace, overridable with `--word-diff-regex`). A UI-native renderer should ask for `--word-diff=porcelain` (script-stable, unambiguous +/-/space-prefixed runs with `~` for embedded newlines) rather than parsing ANSI-colored `--color-words` output, then render its own highlight spans/backgrounds instead of terminal colors. Diff algorithm choice (`myers` default, `minimal`, `patience`, `histogram`) is a `--diff-algorithm` flag; `histogram` (patience-family) generally produces the diff humans find easiest to read for code with repeated tokens, and is a reasonable default to expose as user-configurable.

**Blame** (confirmed, high confidence): `git blame --porcelain` emits, per line, a header (`<sha1> <orig-line> <final-line> [<num-lines>]`) followed by full commit metadata *only the first time* that commit is seen (author/committer name/mail/time/tz, summary, filename), then a tab-prefixed content line. This is exactly the shape needed to drive an editor-gutter blame annotation with per-commit color grouping and de-duplicated tooltips; `--incremental` gives the same data unordered/streaming (newest-first) with no line content, which suits an async "blame arrives progressively" UX. `--line-porcelain` (full metadata repeated every line) trades bandwidth for simplicity and is not needed here.

**Interactive rebase sequence editor** (confirmed, high confidence): Git writes `.git/rebase-merge/git-rebase-todo` and invokes whatever `$GIT_SEQUENCE_EDITOR` names on it; a UI that wants a structured "pick/squash/reorder" buffer can point `GIT_SEQUENCE_EDITOR` at a trivial helper (e.g. `cat <path-the-UI-wrote>` or a small script) after presenting its own reorderable list UI and serializing the user's choices back to that file — no real text editor is ever spawned. `--autosquash` (auto-reorders `squash!`/`fixup!`/`amend!`-prefixed commit messages) and `--autostash` (stashes/unstashes automatically around a rebase on a dirty tree) are both useful UI defaults to expose as toggles.

**libgit2 / SwiftGit2** (confirmed, high confidence for license, medium for maturity): libgit2's COPYING is **GPLv2 with a linking exception** — the exception explicitly grants "unlimited permission to link the compiled version of this library into combinations with other programs, and to distribute those combinations without any restriction," so a closed/differently-licensed Swift app can link it freely; only modifications to libgit2 itself must stay GPLv2. SwiftGit2 (MIT-licensed Swift bindings) wraps libgit2 with value-object structs/enums instead of exposing raw libgit2 handles, which the authors say gives thread-safety benefits ("values can be used concurrently," disk access confined to the `Repository` class) — but the project's README itself flags that its API surface is deliberately not a 1:1 mapping of libgit2, i.e. **gap coverage is real and unspecified**: libgit2 historically lags behind CLI git on newer plumbing (partial clone, sparse-index performance paths, some merge/rerere strategies, newer protocol v2 negotiation features) and SwiftGit2 lags further behind libgit2's own surface. GitHub stats seen (705 stars, 189 forks, 519 commits) suggest a small-to-modest community project, not a heavily-funded one; recent commit cadence could not be confirmed (unverified).

**Recommendation (must/should/could):**

- **MUST: drive the `git` CLI as the primary backend**, the same choice Magit made and (per VS Code's own docs, confirmed) the same choice VS Code made ("VS Code uses your machine's Git installation... Install Git 2.0.0+"). Rationale: git 2.55 is already installed and kept current by the OS/user outside the app's release cycle; CLI porcelain (`--porcelain=v2`, `--word-diff=porcelain`, `--porcelain` blame, rebase-todo file) is a stable, versioned, well-documented machine interface that tracks every new git feature (partial clone, sparse checkout, worktrees, new merge strategies) automatically, with zero binding-maintenance burden. This avoids inheriting SwiftGit2's confirmed API-coverage gap and unverified maintenance velocity risk.
- **SHOULD: use `--no-optional-locks` on every read-only/background poll** (status, diff-for-display, log listings) to avoid index-lock contention with either the user's own concurrent CLI use or the app's own foreground commit action.
- **SHOULD: reimplement Magit's core interaction model** — one collapsible status buffer as the hub, hunk/line-level staging via a synthetic-patch-plus-`git apply --cached` (mirroring Magit's approach, confirmed as the standard technique for partial-hunk staging in git tooling generally), a transient-style command palette for the long tail of git flags, and a structured interactive-rebase list view driving `GIT_SEQUENCE_EDITOR`. This is the "minimal slice that gives most of Magit's value": status-buffer-as-hub + hunk staging + commit buffer + transient-style menu covers roughly what a working Emacs+Magit user touches all day, before log-browsing polish, blame, or forge integration are needed.
- **SHOULD: render diff word-highlights and blame gutters natively** using `--word-diff=porcelain` and `--blame --porcelain`/`--incremental` output rather than parsing git's ANSI color output, giving full control over faces/animations and native rendering quality exceeding what a terminal-bound Magit can do.
- **COULD: use SwiftGit2/libgit2 as a narrow supplementary path** for specific hot operations where shelling out has measurable overhead or where synchronous polling is undesirable (e.g. computing the *working-tree diff stat for many files at once* for a live gutter, or repository-open/does-a-repo-exist checks) — its license (GPLv2 + linking exception) is confirmed safe to link even from a differently-licensed or closed app. This should stay optional/isolated behind an internal protocol so the CLI path remains the source of truth and libgit2 gaps never block a feature.
- **COULD: forge (PR/issue) integration and a first-class 3-way merge editor** are later-milestone features; Zed and VS Code (confirmed) both ship a dedicated 3-way merge editor, which is a concrete example worth copying since Magit itself does not have one — track this as a "beyond Magit" enhancement, not a parity requirement.
- **Pitfall to flag**: `git apply --cached` for partial-hunk staging is finicky about hunk-header line-number recomputation when multiple hunks in the same file are staged out of order; Magit has years of edge-case fixes here (e.g. staging a hunk that overlaps a rename). Budget real test time for this rather than treating it as a one-afternoon feature.

## B. Project navigation, search, indexing

### B1. Fuzzy finder / quick-open landscape

- **VS Code** (confirmed for search panel, unverified for Quick Open internals — the codebasics doc fetched did not mention ripgrep or the fuzzy algorithm by name): Search-across-files (Cmd+Shift+F) groups hits by file with counts, supports glob include/exclude, and an explicit "Use Exclude Settings and Ignore Files" toggle governing `.gitignore` respect (confirmed). VS Code is widely known (prior knowledge, **medium confidence**, not re-confirmed live this session) to shell out to a bundled `rg` (ripgrep) binary for the search panel, and to use its own internal fuzzy-scoring (not ripgrep) for Quick Open file matching plus a separate index for workspace symbols sourced from language servers (LSP `workspace/symbol`).
- **fzf** (unverified live — `ALGORITHM.md` fetch 404'd; relying on well-established prior knowledge, **medium confidence**): fzf V2's default algorithm is a Smith-Waterman-style local-alignment scoring pass with bonuses for matches at word boundaries, after a delimiter, and camelCase transitions, plus a penalty for gaps — tuned so that "tighter, more left-aligned, more boundary-aligned" matches score higher, which is what makes fzf's ranking feel intuitive for path/identifier fuzzy matching.
- **nucleo** (confirmed via GitHub fetch, high confidence): a Rust fuzzy matcher built for Helix, explicitly positioned as a faster fzf/skim replacement. It uses the *same scoring system* as fzf but implements the Smith-Waterman algorithm with two matrices instead of one, producing more optimal alignments (example given: matching `foo` in `xf foo` — nucleo finds `x__foo`, fzf finds `xf_oo`). Benchmarked ~6x faster than `skim`/the `fuzzy-matcher` crate, and handles non-ASCII correctly where skim's bonus/case-insensitivity is ASCII-only. On a ~3M item corpus, nucleo matches "nearly instantaneously" versus fzf's ~1s. License MPL-2.0. The fetched README did not state whether it streams/matches incrementally on a background thread — **unverified**, though Helix's own usage of it (a modal, single-threaded-feeling but async-internally editor) strongly implies an incremental/cancelable match loop is at least the intended usage pattern.
- **JetBrains Search Everywhere**: not fetched this session (no primary doc URL was in the assigned list and budget was prioritized elsewhere) — **unverified in this pass**. Prior general knowledge (low confidence, flag for follow-up): JetBrains maintains its own persistent project-wide index (built once, incrementally updated, covering PSI/symbols beyond plain-text) rather than doing per-keystroke subprocess search, which is why Search Everywhere feels instant even on huge Java monorepos but requires an indexing pass on project open — a real trade-off to weigh against Reticle's "search when asked" model.

### B2. Emacs consult/embark/wgrep/projectile model (baseline most relevant to pellicle, since the owner wants an Emacs-shaped editor)

- **consult-ripgrep / consult-line** (confirmed via GitHub README fetch, high confidence): consult's async grep commands split the minibuffer input at a configurable punctuation character — the first segment is sent to the external `ripgrep` process as its own regex, the remainder is used to further filter the *already-returned* candidates using Emacs's normal completion-style matching. Typing beyond `consult-async-min-input` characters (re)starts the ripgrep subprocess; each new keystroke that changes the ripgrep-bound portion kills the running process and relaunches it, keeping the candidate list live without ever blocking the minibuffer. Process state is surfaced directly in the minibuffer prompt (`:` idle, `*` running, `!` error, `;` interrupted) with a `*consult-async*` log buffer for diagnostics.
- **embark-export → wgrep** (confirmed, high confidence): `embark-consult` can export the *live* candidate set from `consult-grep`/`consult-ripgrep`/`consult-git-grep` into a standalone `grep-mode` buffer (the same format `M-x grep` would have produced), which can then be flipped into `wgrep` editing mode. This is the "search is a first-class editable artifact" pattern the Reticle PLAN.md explicitly names as the reference point for its own M82-M85 milestones (`grep -n "embark-export\|wgrep" reticle/PLAN.md` shows this framing directly: M82's spec cites "Embark's embark-export (dumps live-search candidates ... into a push-able candidate panel)" as a target pushed to M85, and wgrep-grade editability as M83's explicit goal).
- **wgrep.el** (confirmed via GitHub fetch, high confidence): converts a read-only grep-results buffer into an editable one (`C-c C-p`), lets the user edit match lines in place with edits highlighted before commit, supports discarding a single line's edit (`C-c C-d`... note: overloaded per-command, exact keys vary by version) or the whole session (`C-c C-k`), applies accepted edits back to the real file buffers on `C-c C-e`, and has an explicit safety knob (`wgrep-change-readonly-file`) for whether it's allowed to touch files that are themselves read-only on disk. It also understands grep's `-A/-B/-C` context lines so context text isn't misapplied as an edit.
- **Reticle's own implementation** (from local repo, high confidence — this is the codebase being extended): `/Users/jerrychen/My_Projects/reticle/README.md` describes a background project search streaming into a `*search*` buffer with wgrep-style editable results, "orderless" (out-of-order token) filtering, and live filter-as-you-type (README lines ~159-161). PLAN.md's M82 (background search + results buffer), M83 (editable results, explicitly "wgrep-level"), M84 (orderless out-of-order matching + type-to-filter for `M-x`), and M85 (live filtering + `M-.` jump to module declaration) record the actual build order and the hard lessons: M82 alone hit the same *shape of bug* six times (an implicit/shared resource swapped for something similar-but-not-identical, silently changing observable behavior at the edges) across three different reviewing roles; the project's own retrospective (PLAN.md ~line 12865) says M85 took 8h45 and the owner questioned the process afterward, and identifies as a known-gap-turned-lesson that "the incremental value gained is small" relative to what M82 already delivered — i.e., diminishing returns after the background-search + editable-results core landed. Known shipped limitations recorded in Reticle's README: `C-g` during filtering does not restore prior state, and result navigation re-ranks the *whole* result set on every `n`/`p` keypress (O(N) per navigation step) — both are concrete anti-patterns to design around from day one in pellicle rather than retrofit.

### B3. Indexing for huge trees (100k-file Verilog scale)

- **universal-ctags** (confirmed via docs.ctags.io fetch, medium confidence — page was thin): supports 40+ language parsers (C/C++ with an "extended" parser, Python, JS, Java, Go, Rust, and more), plus a fully generalized "optlib" mechanism letting users define new language parsers via regex from the command line with no core-code changes — directly relevant for Verilog/SystemVerilog if a maintained parser needs tuning. Supports both traditional `tags` and Emacs-style `TAGS` output, plus JSON output. The fetched page did **not** cover large-codebase performance characteristics or a tree-sitter comparison — **unverified**; note that ctags-generated tags are line/regex-based (fast, approximate, no real semantic model) versus tree-sitter tag queries which parse a real (if error-tolerant) syntax tree per file and can extract structurally precise definitions (e.g. distinguishing a Verilog module header from a similarly-shaped macro), at higher per-file CPU cost.
- **LSP workspace symbols vs a private index**: the owner's environment already has `verible-verilog-ls` and `slang-server` installed. Both are real Verilog/SystemVerilog language servers and in principle answer `workspace/symbol` and `textDocument/definition` queries, which would make a private ctags/tree-sitter index redundant for symbol lookup *if* the LSP server itself scales to 100k files without prohibitive indexing time or memory — this is genuinely unverified for either server at that scale (not fetched this session; would need direct testing against the owner's actual RTL tree). Reticle's own approach (confirmed from README, cross-file module jump section) did **not** rely on an LSP-provided index for Verilog cross-file jump; it built its own **recursive BFS library search plus `verible.filelist` support** — i.e., a from-scratch project index driven by the same file-list convention Verible itself uses, sidestepping the question of whether the LSP server's own indexing is fast enough. Given the explicit 100k-file target in this brief, the safer default is to assume any general-purpose LSP server's workspace-wide indexing may not scale cleanly and to keep an app-owned lightweight index as the fallback/primary path, using LSP only for what it's authoritative for (live diagnostics, precise per-buffer semantic info) rather than as the sole cross-file jump mechanism.
- **FSEvents-based freshness**: not independently fetched (WWDC transcripts were suggested as a fallback source but budget was spent elsewhere) — **unverified in this pass, but low-risk**: FSEvents is Apple's standard low-overhead recursive directory-change-notification API and is the obvious mechanism to keep any private index (ctags-style or otherwise) fresh without polling or full-tree rescans; this should be validated against Apple's official FSEvents docs directly (not web search) in an implementation-phase spike, since exact latency/coalescing behavior and per-volume limits matter for a 100k-file tree and were not confirmed here.

### B4. Regex engine choice in Swift

- No hard, sourced performance comparison between `NSRegularExpression` (ICU-backed) and Swift's native `Regex`/`Swift Regex` (from `swift-experimental-string-processing`, confirmed via GitHub fetch to still be labeled **experimental**, requiring a Swift trunk snapshot and an experimental compiler flag as of the fetched README) was found — **this specific ask ("performance evidence you can cite") could not be satisfied; treat any claimed number as unverified** unless re-confirmed with an actual local benchmark.
- What is confirmed: `swift-experimental-string-processing` is explicitly experimental, tightly coupled to specific compiler snapshots (a "lockstep integration" risk the project's own docs call out), which argues against depending on it as of Swift 6.3.3 (the owner's installed toolchain) for a production feature like project-wide search.
- Architectural conclusion (reasoning, not a citation): for project-wide multi-file search at 100k-file scale, the actual regex engine embedded in the app almost does not matter, because **ripgrep as a subprocess (Rust's regex crate, a finite-automaton engine with SIMD literal prefiltering) is already installed on the owner's machine and is what every serious editor (VS Code, confirmed to use "your machine's Git installation" pattern for git, and widely known to bundle/shell to `rg` for search) leans on**. Re-implementing a competitive regex/search engine in Swift (whether via `NSRegularExpression`, the experimental `Regex`, or a hand-rolled engine) to beat a subprocess call to a mature, SIMD-optimized, actively maintained Rust binary is a large, high-risk undertaking with no evidence of payoff. PCRE2/RE2-via-C-bridge is a middle path (in-process, no subprocess-spawn latency) but inherits real integration cost (C interop, bundling/vendoring a C library, keeping it patched) for a benefit (removing process-spawn overhead, tens of milliseconds) that mostly matters only for very-low-latency single-keystroke-interactive search, not for background/async search of the kind Reticle and consult both use.

### B5. Freshness, .gitignore respect, editable results, bookmarks/jump lists/breadcrumbs

- **.gitignore respect**: confirmed as a first-class, user-toggleable feature in VS Code's search panel ("Use Exclude Settings and Ignore Files"); ripgrep itself respects `.gitignore`/`.ignore`/global gitignore by default and this is almost certainly why VS Code, Zed, and virtually every modern search-across-files feature "just works" against build output and vendored dependencies without per-project configuration — inheriting ripgrep's own ignore-file handling (rather than reimplementing gitignore parsing) is the low-risk path.
- **Editable results (wgrep)**: covered in B2; Reticle already has this shipped (M82/M83) and its own recorded lessons (the "diminishing returns after M82" note, the O(N) re-rank-on-navigate bug, and `C-g` not restoring state) are the concrete punch list to fix rather than reinvent when porting the design to Swift.
- **Bookmarks/recent files/jump lists, breadcrumbs/outline, multi-project workspaces**: not independently researched this session (not covered by any of the assigned primary URLs and budget was prioritized on git/search-algorithm topics) — **unverified/not researched in this pass**; flag for a follow-up agent or a later milestone spec pass specifically on these features, since they were listed in Brief B but no primary source for them was in the assigned URL set.

### B6. Recommended architecture (building on Reticle's background-search + editable-results baseline)

**MUST:**
- **Keep the "search is an editable buffer" model from Reticle (M82/M83)** as the foundation — it is independently validated by consult+embark-export+wgrep in Emacs and by Zed's multibuffer search results (confirmed: "one excerpt for each matching line," directly editable, edits sync to real files). Three independent ecosystems converge on the same idea; do not regress from it.
- **Shell out to `ripgrep` as a subprocess for project-wide multi-file text search**, mirroring VS Code and (very likely, though unverified) Zed and Reticle's own prior design. Do not attempt to reimplement a competitive regex/search engine in Swift for this purpose; the experimental status of Swift's native `Regex` engine and the lack of any performance case for beating a SIMD-optimized Rust binary make in-process reimplementation the wrong investment.
- **Respect `.gitignore` by relying on ripgrep's own ignore-file handling**, not a custom reimplementation.

**SHOULD:**
- **Fix Reticle's two recorded search bugs by design, not patch**: make result navigation (`n`/`p`) operate on a pre-sorted/indexed structure (not a full O(N) re-rank per keystroke) — e.g., maintain results in a data structure that supports incremental re-insertion or accept eventually-consistent ordering that re-sorts only on filter-text change, not on cursor movement; and make cancel (`C-g`-equivalent) restore prior state explicitly by snapshotting before starting a new filter session.
- **Use a nucleo-or-fzf-style Smith-Waterman fuzzy scorer** (nucleo is a strong reference implementation: confirmed same scoring family as fzf, faster, correct non-ASCII handling, MPL-2.0-licensed Rust) for interactive fuzzy file/symbol matching (Quick Open equivalent). Since nucleo itself is Rust, either vendor/bridge it via a small C-compatible shim (feasible, similar in shape to linking libgit2) or reimplement its scoring formula natively in Swift (the algorithm itself — Smith-Waterman with word-boundary/camelCase bonuses — is well-documented and not large); either is reasonable, but avoid a naive single-pass substring/Levenshtein scorer, which is what makes fuzzy finders feel "dumb" by comparison.
