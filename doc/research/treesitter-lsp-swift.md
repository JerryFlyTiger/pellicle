## 1. tree-sitter from Swift

**SwiftTreeSitter (ChimeHQ)** — https://github.com/ChimeHQ/SwiftTreeSitter — confidence: high (fetched README directly).
- Swift wrapper around tree-sitter's C API, "close to full coverage," using Swift/Foundation types where possible.
- Two products: `SwiftTreeSitter` (low-level, close to C API, requires integration work) and `SwiftTreeSitterLayer` (higher-level: nested-language support, transparent cross-injection querying, async language resolution).
- Query support: highlights and injections via query execution, `ResolvingQueryMatchSequence` for predicates/directives, conflict resolution sorting matches by depth/location/specificity.
- Grammars ship as **separate SwiftPM packages** (50+ listed by the ChimeHQ ecosystem, e.g. Swift, Python, Rust) — i.e. grammars are **compiled in as SwiftPM C targets**, not loaded as dylibs at runtime, in the typical ChimeHQ pattern. `LanguageConfiguration` loads bundled `.scm` query files from SPM resource bundles.
- Encoding: operates on **UTF-16 by default** (matches Foundation `NSString`/LSP convention) — important for keeping tree-sitter byte offsets, UTF-16 offsets (LSP), and Swift `String.Index`/grapheme offsets all reconciled.
- Swift concurrency support "where possible" (exact `Sendable`/actor isolation unconfirmed — unverified).
- License: **BSD-3-Clause** — compatible with a proprietary/source-available app.
- Incremental parsing (`ts_tree_edit` equivalent) is inherited from the wrapped C API; SwiftTreeSitter itself doesn't appear to add a rope-backed `TSInput` — that plumbing (reading a rope/piece-table as UTF-16 code units on demand for the parser's read callback) is left to the app. **Unverified**: whether SwiftTreeSitter ships a ready-made rope-based `TSInput`, or only the raw `Parser.parse(string:)` / callback-based entry points — need to inspect source, not just README, to confirm.
- Dylib-vs-compiled-in tradeoff for swiftemacs: ChimeHQ's own ecosystem pattern is "one SwiftPM package per grammar, statically linked," which conflicts with the brief's "language pack as an extension later" goal. Runtime dylib loading of grammars (like Neon/Zed and Emacs 29's own dynamic-module tree-sitter grammars) is the standard tree-sitter C-level capability (`dlopen` + `tree_sitter_LANGUAGE()` symbol lookup) and works independent of SwiftTreeSitter — it's an alternate integration path where the app finds/loads a `.dylib` per language at runtime instead of linking a Swift package per grammar. This is architecturally sound but not what ChimeHQ's own consumer apps (e.g. Neon-based editors) typically do — **medium confidence**, inferred from ecosystem norms rather than a doc explicitly describing runtime dylib loading in SwiftTreeSitter.

## 2. Query language and query file kinds

Confidence: high (general tree-sitter knowledge, consistent with Reticle's own file layout and unverified against fresh docs this run — not independently re-fetched, budget spent on Swift-specific and grammar-specific sources instead).
- `.scm` (Scheme-syntax) query files, the standard kinds an editor consumes: `highlights.scm` (syntax highlighting captures), `injections.scm` (embedded-language regions, e.g. SQL in a string, Verilog inside `` `include``-like macros, or Markdown code fences), `locals.scm` (scope/definition/reference tracking for local-variable-aware highlighting and rename), `tags.scm` (symbol outline / "ctags"-like definitions consumed by tools like GitHub's tree-sitter-based code nav), `indents.scm` (an Atom/Zed/Helix-style convention, not upstream tree-sitter core, used to derive indentation from node scope rules).
- Reticle (Rust, local reference) shipped only `*-highlights.scm` per language (`bash`, `c`, `cpp`, `elisp`, `java`, `perl`, `python`, `rust`, `verilog` — see `/Users/jerrychen/My_Projects/reticle/crates/core/queries/`) and no `locals`/`tags`/`indents` queries — confidence: high, verified by direct `ls` this run. This is a concrete gap swiftemacs could close: shipping `locals.scm` (for accurate local-variable highlighting and a homegrown "rename in scope" without invoking the LSP) and `indents.scm` (tree-sitter-driven indentation instead of hand-written per-mode indent logic) would be new work relative to what Reticle had.
- Grammar crate versions actually pinned in Reticle's `Cargo.toml` (confidence: high, verified): `tree-sitter = "0.25"`, `tree-sitter-rust = "0.23"`, `tree-sitter-c = "0.24"`, `tree-sitter-cpp = "0.23"`, `tree-sitter-python = "0.25"`, `tree-sitter-bash = "0.25"`, `tree-sitter-java = "0.23"`, `ts-parser-perl = "1.2"` (not the canonical `tree-sitter-perl` crate name — worth checking why Reticle used this alternate crate; possibly a Rust-native wrapper around the perl grammar or an alternate build), `tree-sitter-elisp = "1.6"`, `tree-sitter-systemverilog = "0.4"`. Notably **no Tcl grammar** and **no Swift grammar** were used by Reticle (Reticle doesn't self-host in Swift), so Tcl and Swift are net-new integration work for swiftemacs, not something to copy from Reticle.

## 3. Incremental parsing, timeouts, cancellation, threading

Confidence: medium — general tree-sitter C API knowledge, not re-verified against fresh docs this session (budget was prioritized toward Swift/grammar/server-specific sources).
- `ts_tree_edit` (exposed through SwiftTreeSitter's low-level API, name likely wrapped e.g. as `Tree.edit(_:)`) lets the parser reuse unaffected subtrees on the next `parse` call given the previous tree plus the edited byte/point ranges — this is the whole point of incremental parsing and is essential for keeping large-file (Verilog UVM, generated RTL) editing responsive.
- tree-sitter's C API exposes `ts_parser_set_timeout_micros` (older) / cancellation flag (`ts_parser_set_cancellation_flag`) so a parse can be aborted mid-way if it's taking too long or the buffer changed again — **unverified whether SwiftTreeSitter exposes these**; this needs source inspection (not just README) before committing to a design that assumes it, since editors on huge SV files (post-macro-expansion, UVM-heavy) can hit pathological parse times.
- Recommended pattern (matches what Neon/Zed/Helix do, and what the brief calls out): run `Parser.parse` on a background thread/task, feed it a **rope-backed `TSInput`** (a C struct with a `read` callback returning UTF-16 or UTF-8 code units from arbitrary byte offsets) so the parser never needs a fully materialized contiguous string of the whole buffer — critical for both large files and for not blocking the main/UI thread. SwiftTreeSitter's own README emphasizes UTF-16 operation by default, which lines up with feeding it UTF-16 code units directly from a rope keyed the same way NSString/AttributedString are, avoiding conversion round-trips against Swift's grapheme-cluster-based `String`.
- Practical pitfall: three different offset spaces have to be kept in sync — tree-sitter byte offsets, LSP UTF-16 code-unit offsets (unless a server negotiates `positionEncodings: [utf-8]` per LSP 3.17), and Swift `String.Index`/`Character` (grapheme cluster) offsets used for UI rendering/selection. This three-way translation is a known source of off-by-one and multi-byte/emoji/combining-character bugs in editor implementations generally (medium confidence — this is a well-documented class of bug across many editors, not sourced from a single doc this run).

## 5. LSP client libraries in Swift (ChimeHQ stack)

- **LanguageServerProtocol** — https://github.com/ChimeHQ/LanguageServerProtocol — confidence: high. Pure Swift LSP type definitions usable by both client and server code (`TwoTypeOption`/`ThreeTypeOption` for LSP's anonymous-union JSON shapes, `Snippet`, `TokenRepresentation` for semantic tokens, `DataChannel.withMessageFraming` for the `Content-Length:` header framing LSP uses over stdio). Targets current LSP 3.x spec while staying compatible with older servers. Swift 5.9+. License BSD-3-Clause.
- **JSONRPC** (ChimeHQ) — underlying transport/protocol layer used by LanguageServerProtocol/LanguageClient (not independently fetched this run — confidence: medium, inferred from LanguageClient's description of "wraps LanguageServerProtocol and JSONRPC").
- **LanguageClient** — https://github.com/ChimeHQ/LanguageClient — confidence: high (fetched README). Layered client abstraction (`ServerConnection` protocol → `InitializingServer` auto-handles the initialize/initialized handshake → `RestartingServer` adds transparent crash recovery with state restoration). Process launch via `DataChannel.localProcessChannel` (plain local subprocess) or `DataChannel.userScriptDirectory` (uses `NSUserUnixTask`, relevant for sandboxed/App-Store-style process spawning). README explicitly warns: **"pay careful attention to rootPath/rootURI/workspaceFolders, as different servers will have different expectations/requirements here"** — i.e. this is a known integration pitfall the library authors call out directly, not just a theoretical concern. UTF-16 position-encoding handling is not explicitly documented in the fetched excerpt — **unverified** whether LanguageClient negotiates `positionEncodings` (LSP 3.17 `general.positionEncodings` capability, allowing UTF-8/UTF-32) or hardcodes UTF-16; given SwiftTreeSitter's UTF-16-by-default posture, UTF-16 is the most likely default (medium confidence, not confirmed from source).
- **sourcekit-lsp's own LSP types**: Apple's sourcekit-lsp (part of the Swift toolchain, https://github.com/swiftlang/sourcekit-lsp) has its own internal `LanguageServerProtocol` Swift module (in `Sources/LanguageServerProtocol`) — a separate implementation from ChimeHQ's, not a shared dependency. **Not independently fetched this run — unverified** whether it could be reused/vendored; ChimeHQ's package is the practical choice for a new client since sourcekit-lsp's is an internal module of that toolchain component, not published as a standalone reusable SwiftPM product for client use (medium confidence, based on general knowledge of the sourcekit-lsp repo layout, not fetched this session).

## 10. SwiftPM build-integration recommendation

- **Grammars as C targets, compiled in for the "core" set, with a path to dylib-based extensibility later** (must, medium-high confidence — this is a design recommendation synthesizing the above, not a single sourced fact): Each tree-sitter grammar's `parser.c` (plus optional `scanner.c` for grammars with custom external scanners, which SystemVerilog/Perl-class grammars often have) becomes its own SwiftPM **C target** (`.target(name: "TreeSitterVerilog", path: "...", sources: ["parser.c", "scanner.c"])`), matching the pattern ChimeHQ's own ecosystem uses (grammars as separate SPM packages/targets) and matching how tree-sitter's own CLI (`tree-sitter generate`) emits per-grammar C sources. A thin Swift target wraps each with `LanguageConfiguration`/`Language` construction and bundles its `.scm` query resources.
- **Ship the "killer feature" languages (SystemVerilog, Swift, Python, Perl, Tcl, C, C++) compiled into the base app** (must) since those are explicitly priority-1 in the brief and the app should work fully offline/day-one without a plugin marketplace dependency.
- **Design the grammar-loading abstraction so a language pack *could* later be an extension** (should): define an internal protocol (e.g. `GrammarProviding { var language: Language { get }; var queries: QuerySet { get } }`) that both (a) statically-linked built-in grammars and (b) a future dynamically-loaded plugin conform to. A future "language pack" extension would ship a `.dylib` exposing the C ABI `tree_sitter_<name>()` symbol (the same mechanism Neon/Zed/Emacs 29's dynamic modules use) plus a resource bundle of `.scm` files; the host app `dlopen`s it and wraps the resulting `TSLanguage*` the same way SwiftTreeSitter wraps a compiled-in one. This is architecturally straightforward because tree-sitter's C ABI doesn't care whether the `TSLanguage*` came from a statically linked symbol or a `dlsym` lookup — the wrapper code is identical either way. **This dylib path was not confirmed as something SwiftTreeSitter does out of the box — unverified**, and should be prototyped early (a spike, not a research task) rather than assumed.
- **LSP/DAP servers are always external subprocesses, never linked in** (must) — this is both the standard architecture (confirmed by ChimeHQ's DataChannel/local-process model) and the license-safe choice (see section 8): swiftemacs ships a way to locate/configure each server binary (verible-verilog-ls, slang-server, sourcekit-lsp, pyright/basedpyright, PerlNavigator, tclint, clangd, lldb-dap, debugpy) but doesn't vendor their source.
- **Feed the parser via a UTF-16 rope-backed `TSInput` on a background thread/actor** (must) — matches SwiftTreeSitter's UTF-16-by-default posture, avoids blocking the UI, and avoids materializing whole-buffer strings on every keystroke; confirm SwiftTreeSitter's exposed input hooks (`Parser.parse(_:oldTree:)` overloads) support a custom read-callback `TSInput`, not just `String`/`Data`, before finalizing the design (unverified from README alone).
- **Verify `ts_parser_set_timeout_micros`/cancellation exposure in SwiftTreeSitter before relying on it for pathological-file protection** (should) — if unexposed, the fallback is a wrapper-level watchdog (cancel the background Task and drop the parse result) rather than relying on tree-sitter's own cooperative timeout.
- **Confirm slang-server's actual LSP feature surface and Tcl grammar availability before writing detailed specs for those two** (should, stop-loss item) — these are the two components in this survey where confidence stayed medium/low after using the full research budget; a follow-up pass (ideally with WebSearch available, since it was exhausted mid-session this run by something outside this task's control) should re-attempt tree-sitter-tcl / a Tcl LSP comparison and read slang's actual language-server subdirectory README directly.
