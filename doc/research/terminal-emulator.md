## 1. iTerm2 architecture & killer features [confidence: high for docs, medium for internal architecture not directly fetched]

Primary source: https://iterm2.com/documentation-shell-integration.html, https://iterm2.com/documentation-images.html, https://iterm2.com/documentation-badges.html (gnachman/iTerm2 is Objective-C/Swift, GPL2, not license-compatible for embedding — see §13).

- **Shell integration (OSC 133-family + iTerm2 custom OSC 1337)**: the shell (bash/zsh/fish) is configured to emit escape codes marking (a) where the prompt begins/ends, (b) where typed command text ends and output begins, (c) the last command's exit code, (d) username/hostname/cwd. This is the foundation for nearly every "killer feature": prompt marks (blue/red triangle in the left margin), Cmd-Shift-Up/Down to jump between command marks, "Select Output of Last Command," per-command exit-status coloring.
- **Semantic history**: uses the same marks plus filename/path regex recognition to let Cmd-click on a path or compiler error open it in an editor at the right line — this is the direct terminal-world analogue of Emacs `compile.el`'s error jump, and is one of the most valuable features to replicate natively (swiftemacs can do this *better* than iTerm2 since it *is* the editor — no need to shell out to `$EDITOR`).
- **tmux -CC integration**: shell integration is disabled by default under tmux/screen (must opt in via `ITERM_ENABLE_SHELL_INTEGRATION_WITH_TMUX=1`) because tmux's own screen multiplexing conflicts with mark tracking unless tmux is running in **control mode** (`tmux -CC`), where tmux hands iTerm2 structured protocol messages instead of raw VT bytes, and iTerm2 renders each tmux pane as a native split/tab. This is a fundamentally different integration path from "just another terminal app" — worth studying if swiftemacs wants first-class tmux support, but not required for v1 (Emacs users typically don't run tmux inside their editor).
- **Triggers**: regex-matched against output lines, can highlight, alert, run a command, or (with shell integration) trigger custom actions — conceptually identical to Emacs `compilation-error-regexp-alist` / `comint` output filters, and should be implementable as an Elisp-exposed hook (`add-terminal-output-trigger`) rather than a native-only feature.
- **Split panes, profiles, hotkey window, password manager, status bar, badges** (`OSC 1337 ; SetBadgeFormat=<base64>`, a large translucent text overlay showing e.g. git branch or hostname): all high-value but are UI/profile-management features orthogonal to the VT engine — build them as swiftemacs window/frame/mode-line features once the terminal grid exists.
- **Instant replay / copy mode**: iTerm2 keeps a rolling recording of terminal state (not just scrollback text but frame snapshots) letting the user scrub backward in time; "copy mode" is a modal, keyboard-driven text-selection mode over the grid. For swiftemacs, copy mode is largely redundant if the terminal grid is *editable text in a real buffer* (see §14) — Emacs' native selection/search already works.
- **Metal renderer & performance history**: iTerm2 added a Metal-based renderer (opt-in, GPU-accelerated) after years of a CPU/Core Graphics renderer; historically iTerm2 has had recurring performance complaints under heavy output (large `cat`/build-log bursts) relative to GPU-first newcomers (Alacritty, kitty, WezTerm, Ghostty, Warp), which is exactly why the newer generation of terminals (Ghostty, kitty, Alacritty) designed GPU rendering and SIMD-optimized parsing in from day one rather than retrofitting it. **Lesson for swiftemacs: design the renderer (Metal, dirty-region/damage tracking, glyph atlas caching) from the start, not as a bolt-on.**

## 2. Ghostty (Zig core + Swift/AppKit/SwiftUI macOS app) [confidence: high, primary sources: github.com/ghostty-org/ghostty README, generated libghostty header]

- **License: MIT** (confirmed from README) — freely embeddable, no GPL contamination risk. This is a major factor in its favor as a dependency (contrast iTerm2 itself, which is GPL2 and not usable as embedded code; only its *documented protocols* are freely reusable).
- **Architecture**: a large shared core written in **Zig**, with thin, fully-native platform shells — SwiftUI/AppKit on macOS, GTK on Linux. Multi-threaded: dedicated read, write, and render threads per terminal surface. The read thread runs a "heavily optimized terminal parser that leverages CPU-specific SIMD instructions."
- **libghostty embedding API (C ABI)**, confirmed from the generated `ghostty.h` header: opaque handle types `ghostty_app_t`, `ghostty_surface_t`, `ghostty_config_t`; lifecycle functions `ghostty_app_new/free/tick/set_focus/update_config`; per-surface functions `ghostty_surface_new/free/set_size/draw/refresh`; input functions `ghostty_surface_key/mouse_button/mouse_pos/mouse_scroll/text`; config functions `ghostty_config_new/load_file/load_default_files/finalize/get`. This is a genuine "embed a terminal in your own app" C ABI — Ghostty's own macOS app is itself a client of this API, i.e. **the macOS app and a hypothetical swiftemacs terminal pane would be architecturally symmetric consumers of the same library.** This is the strongest embedding option technically, provided the Zig build can be vendored via SwiftPM's C-target / binary-target mechanism (a Zig static/dynamic library + C header, not raw Zig sources, so Swift's build graph doesn't need to understand Zig — **unverified**: exact SwiftPM packaging story / whether Ghostty publishes a versioned libghostty release artifact suitable for `Package.swift` binaryTarget consumption; treat as a build-integration risk to prototype early).
- **Rendering**: Metal on macOS (OpenGL on Linux); font discovery via CoreText on macOS, with shaping presumably via HarfBuzz for complex scripts (**unverified in this pass** — not independently confirmed which shaper is default on macOS vs when HarfBuzz is invoked).
- **Protocols**: kitty graphics protocol, kitty keyboard protocol, clipboard operations (OSC 52-style), synchronized rendering (mode 2026), light/dark mode notification sequences — described by the project as "one of the most compliant and feature-rich terminal emulators available."
- **Config**: plain-text key=value config file (not Lua/TOML), loaded via `ghostty_config_load_file`/`load_default_files`.
- **Maturity/maintenance**: young relative to iTerm2 (public 1.0 in 2024), led by Mitchell Hashimoto (HashiCorp co-founder) with an active OSS community; fast-moving but the C ABI is explicitly designed for third-party embedding, which is a strong signal of intended stability of that surface even while internals churn.

## 5. macOS PTY API [confidence: medium — general POSIX/BSD knowledge, Apple-specific doc fetch failed (404); not independently re-verified against current Apple headers in this pass]

Apple's PTY layer is the standard BSD/POSIX pseudo-terminal API (`<util.h>`, `<termios.h>`, `<sys/ioctl.h>`); Apple's own "PTYs" developer doc page returned 404 in this session so specifics below are **general Unix/BSD knowledge, not freshly re-confirmed against Apple's current docs**:

- **Session setup**: `posix_openpt(O_RDWR | O_NOCTTY)` opens the PTY master; `grantpt`/`unlockpt` prepare the slave; `ptsname` resolves the slave device path (`/dev/ttysXXX` on macOS). Alternatively BSD's convenience wrapper `forkpty()` (in `<util.h>` on macOS/Darwin, from the old BSD `libutil`) combines `posix_openpt`+`fork`+session/controlling-tty setup+`dup2` of the slave onto stdio in one call — most terminal emulators (xterm, iTerm2, and per its GitHub source, likely Ghostty and Alacritty on macOS) use some form of this pattern rather than assembling `posix_openpt` by hand, because `forkpty` correctly handles `setsid()`/`TIOCSCTTY` controlling-terminal assignment which is easy to get wrong manually.
- **Child process setup for a login shell**: after fork, in the child, set `TERM` (`xterm-256color` is the most broadly compatible choice; Ghostty and kitty use `xterm-kitty`/`xterm-ghostty` to advertise their extended capabilities, which requires shipping a matching **terminfo** entry so `tput`/ncurses-based programs recognize the terminal correctly — a real integration cost swiftemacs must budget for if it invents its own `TERM` string), set `LANG`/`LC_*` for UTF-8 locale, `exec` the user's shell with `argv[0]` prefixed with `-` (e.g. `-zsh`) to make it a **login shell** so `.zprofile`/`.profile`/`.bash_profile` are sourced — this is exactly what iTerm2/Terminal.app do and is required for the shell to behave the way users expect (PATH, prompt, etc. set up correctly), and it's also the plumbing that shell-integration scripts hook into (`precmd`/`preexec` in zsh, `PROMPT_COMMAND` in bash).
- **Window size**: `ioctl(fd, TIOCSWINSZ, &winsize)` on the PTY master informs the kernel (and thus `SIGWINCH` to the child) of terminal cell/pixel dimensions whenever the pane resizes; must be re-issued on every resize and once at startup.
- **I/O model**: PTY master fd is bidirectional; on Darwin, non-blocking reads via `DispatchIO`/`DispatchSource` (GCD) reading in a background queue is the idiomatic Swift approach, feeding bytes into the VT parser (§6) which must be safe to call off the main thread, with parsed screen updates marshaled to the main/render thread — mirrors Ghostty's separate read/write/render-thread design.
- **Practical note**: Apple's App Sandbox restricts some PTY/process-spawning capabilities for sandboxed Mac App Store apps; if swiftemacs is distributed outside the Mac App Store (like iTerm2, and most serious terminal apps) this is moot, but worth flagging as a distribution-channel constraint (**unverified** specifics of current sandbox entitlement rules — recommend a small PTY spike early to confirm no App Sandbox is required, or budget for `com.apple.security.inherit`-style entitlements if sandboxing is ever desired).

## 6. VT/xterm state machine design (Paul Williams parser) [confidence: high, primary source]

Source: https://vt100.net/emu/dec_ansi_parser (Paul Flo Williams' VT500-series parser state diagram — the de facto reference used by xterm, and cited by most modern terminal emulator implementations including Alacritty, Ghostty, and Wezterm).

- Goals: **completeness** (every character has a defined transition in every state) and **correctness** (matches observed real-DEC-terminal behavior, not just the ANSI X3.64 spec, which leaves error recovery undefined).
- 11 states: `ground`, `escape`, `escape intermediate`, `csi entry`, `csi param`, `csi intermediate`, `csi ignore`, `dcs entry`, `dcs param`, `dcs intermediate`, `dcs passthrough`/`dcs ignore`, `osc string`, `sos/pm/apc string`.
- Byte classes drive transitions: C0 controls (00-1F, 7F) execute-or-cancel depending on state; C1 controls (80-9F) cancel+execute or move to specialized states; params (30-39, 3B) accumulate; intermediates (20-2F) collect; finals (40-7E) dispatch.
- Key architectural lesson for swiftemacs: **separate the parser (byte-stream → structured actions) from the interpreter (actions → grid mutation)**. The DCS `hook`/`put`/`unhook` actions are explicitly designed so protocols like Sixel, ReGIS, or (in modern terminals) Kitty graphics can be plugged in as a handler invoked once the DCS final byte is seen, without polluting the core state machine. This is exactly the seam a Swift implementation should keep: a `VTParser` (pure state machine, no side effects) feeding a `VTPerformer`/`TerminalScreen` protocol, mirroring how `alacritty_terminal`'s `vte` crate and Ghostty's parser separate the two.
- Recommendation: implement this parser directly in Swift as an enum-based state machine (an actor or a plain struct advanced byte-by-byte) — it is small (~11 states), well-specified, and there is no benefit to depending on a binding of a different language's parser for this piece even if the rest of the VT engine is embedded.

## 3. SwiftTerm (pure-Swift VT emulator library) [confidence: high, primary source: github.com/migueldeicaza/SwiftTerm]

- What it is: "a VT100/Xterm terminal emulator library for Swift applications," embeddable in macOS/iOS/headless apps. Ported from XtermSharp (Miguel de Icaza's C#/Xamarin terminal), which itself derives from **xterm.js**'s terminal-state logic ported to Swift/C#.
- License: **MIT** — no copyleft or attribution-in-binary complications, freely embeddable in a closed or open Swift app.
- Maintenance: actively maintained (1,360+ commits on main at time of check), has a Discord, GitHub Discussions, and issue tracker. De Icaza is a well-known maintainer (Mono, GNOME, Xamarin) so the project has continuity, but it is a small side project relative to a full terminal app — treat "actively maintained" as medium confidence on long-term velocity.
- Platform surface: `TerminalView` (AppKit NSView) for macOS, UIKit view for iOS, a curses-based headless emulator via the companion **TermKit** library, and reported visionOS/GPU-accelerated rendering support.
- VT/feature coverage: ANSI, 256-color, TrueColor (24-bit); bold/italic/underline/strikethrough/dim; mouse reporting; resize; OSC 8 hyperlinks; bidi text (Arabic/Hebrew) with contextual shaping; **Sixel, iTerm2 inline-image, and Kitty graphics protocols**; Unicode/grapheme-cluster-aware rendering; session recording/playback (termcast format).
- Performance: described by the maintainer as "seems pretty fast," with optional Metal-accelerated rendering path on Apple platforms — no independently verified benchmark numbers found in the budget available (**unverified**: exact throughput vs iTerm2/Ghostty).
- Known adopters: commercial SSH/terminal apps — Secure Shellfish, La Terminal, CodeEdit (a SwiftUI code editor) — is notable prior art for "SwiftUI/AppKit editor embeds SwiftTerm for its integrated terminal," directly analogous to what swiftemacs would do.
- Implication for swiftemacs: SwiftTerm is the most turn-key "own the whole stack in Swift, no C ABI, no Zig toolchain" option, and CodeEdit already proves the embedding pattern (an editor app with SwiftTerm-backed terminal panes) works in production-adjacent software.

## 7. Wide chars / CJK / grapheme handling [confidence: medium — general terminal-emulation knowledge, not independently re-verified against a spec source this pass]

- Terminal grids are cell-addressed, but Unicode text is not 1 cell = 1 codepoint. Every serious emulator needs: (a) **East-Asian Width** (UAX #11) classification to know CJK/fullwidth characters occupy 2 cells; (b) **combining marks / zero-width joiners** that attach to the preceding cell without advancing the cursor; (c) increasingly, full **grapheme cluster** segmentation (UAX #29) so emoji-with-ZWJ sequences and flags render and select as one unit, which SwiftTerm explicitly advertises ("Unicode and grapheme cluster rendering").
- Swift has a structural advantage here: `Swift.String` and `Character` are already grapheme-cluster-based (extended grapheme clusters per Unicode), and `Foundation`/`Swift.Unicode` expose `Unicode.Scalar.Properties` including `isEmojiPresentation` and East-Asian width data is obtainable via ICU-backed APIs or a small bundled width table (`wcwidth`-equivalent) — this is a place where a Swift-native VT engine can be *more correct by default* than a C/Rust one, since grapheme handling doesn't need to be bolted on. **Recommendation**: build the terminal grid's cell model on top of `Character` (grapheme cluster) as the addressable unit with an explicit stored "cell width" (1 or 2), not raw UTF-32 codepoints, to avoid re-deriving grapheme logic that Swift's stdlib already gets right.
- CJK width ambiguity ("ambiguous width" characters in UAX #11, e.g. some box-drawing/Cyrillic in legacy CJK encodings) is a long-standing source of terminal misalignment bugs across all emulators (mismatched assumptions between terminal and the TUI program, e.g. tmux/vim, about a character's width) — this class of bug is a `TERM`/terminfo-adjacent capability negotiation problem, not something a "smarter" implementation fully avoids; document swiftemacs' width policy (Unicode version pinned, ambiguous-width-as-narrow default matching most modern terminals) and expose it as user-configurable, matching kitty/Ghostty/WezTerm's own escape hatches for this.

## 8. Scrollback storage design [confidence: medium — synthesized from general terminal-emulator implementation patterns, not fetched from a single primary source]

- Classic design (xterm, most C terminals): a fixed-capacity ring buffer of line objects, each a packed array of `(codepoint, fg, bg, attrs)` cells; scrollback is capped (a config option) and evicts oldest lines — bounded memory, O(1) append, but scrollback is lossy and not full text.
- Modern trend (Warp, and to a lesser extent iTerm2's "unlimited scrollback"): treat scrollback as an **append-only log of logical lines** (reflow-aware — when the window resizes, wrapped lines re-flow instead of the naive "hard line break at column N" that plain grids bake in), and separately keep command-boundary metadata (from OSC 133) so scrollback can be sliced per-command.
- For swiftemacs specifically, given the ground-rule "editor buffer and terminal grid coexist" design goal (§14), the *most natural* storage is to make scrollback simply **appended text in a real Emacs buffer** (using swiftemacs' own gap-buffer/rope buffer implementation, not a separate grid-only structure) with text properties marking per-cell SGR attributes (like `ansi-color.el`/`xterm-color.el` does today, but computed live instead of post-hoc regex) and per-command boundaries as buffer markers/overlays (directly analogous to comint's `process-mark` and vterm's/eat's prompt tracking) — this unifies "scrollback" and "Emacs buffer with undo/search/kill-ring" into one data structure rather than keeping a separate terminal-grid scrollback that has to be copied into a buffer on demand. The **live cursor-addressed region** (the last N rows where a full-screen program like vim/htop is running) is the part that still needs true grid semantics (in-place overwrite, cursor addressing, alternate screen buffer per DEC mode 1049) — so the design is a **hybrid**: append-only buffer text for scrollback + a small mutable "grid overlay" for the active screen when in alternate-screen/full-cursor-addressing mode, switching back to plain appended text when the program returns to the primary screen (this mirrors how Emacs' own `term.el`/`vterm`/`eat` already distinguish "line mode output" from "raw terminal mode," and is the direct enabler of "terminal output is normal editable/searchable buffer text" from the brief).

## 9. OSC 7 (cwd), OSC 8 (hyperlinks), OSC 133/1337 (shell integration) [confidence: high for OSC 8 (fetched primary gist), medium for OSC 7/133 (general knowledge, not freshly fetched this pass due to budget]

- **OSC 8** (confirmed, https://gist.github.com/egmontkob/eb114294efbcd5adb1944c9f3cb5feda — the de facto spec doc, written by a VTE/GNOME Terminal developer and widely cited): `ESC ] 8 ; params ; URI ST` opens a hyperlink over subsequent cells, `ESC ] 8 ; ; ST` closes it; optional `id=` key groups discontiguous spans (e.g. a link wrapped across lines) so hover/click affects all of them together. VTE and iTerm2 cap URI length at 2083 bytes. Direct applicability: swiftemacs can both *emit* OSC 8 (e.g. wrapping compiler-error paths so other terminals can click them) and *consume* it (turn received OSC 8 spans into real Emacs buttons/`button.el` overlays with `find-file` actions) — consuming is strictly more valuable given swiftemacs is the editor.
- **OSC 7** (`ESC ] 7 ; file://hostname/path ST`, medium confidence / not re-fetched this pass): shell hook (again via `precmd`) reports the shell's current working directory to the terminal, letting new panes/tabs/windows opened "from" a session inherit its cwd — the terminal-level equivalent of Emacs `default-directory` tracking; swiftemacs should parse it to keep its own `default-directory` (and thus `find-file`, `dired`, TRAMP-equivalent prefixing) in sync with whatever directory the shell inside the terminal pane is actually in, which is a genuinely differentiating feature no existing Emacs terminal package (vterm/eat) currently ties back into `default-directory` as tightly as this could.
- **OSC 133** (medium confidence / not re-fetched this pass, but well-documented convention originated by iTerm2/FinalTerm and adopted by VTE, kitty, WezTerm): `A` = prompt start, `B` = prompt end / command start, `C` = command output start, `D[;exit-code]` = command finished. This is the single most valuable sequence family to support well, since it is the basis of prompt marks, per-command output selection, and (per §8) the buffer-marker scheme that would make swiftemacs' terminal pane behave like an editable, navigable structure rather than a plain scrollback.

## 10. Image protocols [confidence: medium-high — iTerm2 fetched primary source; Kitty/Sixel from general knowledge this pass]

- **iTerm2 inline images** (confirmed, iterm2.com/documentation-images.html): `ESC ] 1337 ; File=[args]:<base64> ^G` (`^G` = BEL as terminator), args are `key=value;...` (name, size, width/height in cells/pixels/percent/auto, `preserveAspectRatio`, inline=1 vs download). A 3.5+ `MultipartFile`/`FilePart`/`FileEnd` chunked variant exists to work around tmux's control-mode message-length limits.
- **Kitty graphics protocol** (medium confidence, not re-fetched this pass): APC-based (`ESC _ G ... ESC \`), transfers raw pixel data or PNG, referenced by numeric or string `id`/`placement id`, supports partial updates, animation frames, and transfer via shared memory or temp file for large images (avoiding base64 overhead through the PTY for big payloads) — generally considered the most capable and most widely adopted of the three (adopted by Ghostty, WezTerm, and others per §2/§4).
- **Sixel** (medium confidence): the oldest of the three (DEC-origin), a DCS-based bitmap format with a limited (typically 256-color) palette, lower resolution/efficiency than Kitty graphics but the widest legacy tool support (gnuplot, some image viewers, `img2sixel`).
- **Recommendation for swiftemacs**: implement the **Kitty graphics protocol** as the primary path (best capability, growing adoption, and if libghostty or SwiftTerm is embedded, likely already implemented — SwiftTerm confirmed to support all three: Sixel, iTerm2, and Kitty), with iTerm2's format as a compatibility fallback given how many CLI tools (e.g. `imgcat`) target it specifically, and Sixel last/optional.

## 11. Bracketed paste, mouse reporting, 24-bit color [confidence: medium — general, well-established xterm-protocol knowledge, not re-fetched this pass except kitty keyboard protocol]

- **Bracketed paste** (DEC mode 2004): wraps pasted text in `ESC [200~ ... ESC [201~` so the receiving program (shell/readline, vim) can distinguish "pasted" from "typed" text and avoid auto-indent/history-expansion mangling. Essential for a terminal pane pasting from the Emacs kill-ring or macOS pasteboard.
- **Mouse reporting**: multiple incompatible-but-layered protocols — X10 (basic), VT200 (`1000`), button-motion (`1002`), any-motion (`1003`), with encoding schemes UTF-8 (`1005`, deprecated/broken above 223 cols), SGR (`1006`, the modern default, unambiguous and unlimited coordinates), and URXVT (`1015`, legacy). **Recommendation**: implement DECSET 1000/1002/1003 + SGR (1006) encoding only; skip UTF-8/URXVT legacy encodings as dead weight.
- **Kitty keyboard protocol** (confirmed via sw.kovidgoyal.net fetch, §"11" cross-ref): solves the fundamental ambiguity of legacy terminal key reporting (Ctrl+I == Tab, no way to report key-up, limited modifier support, Esc-key ambiguity requiring fragile timing hacks). Apps opt in via `CSI > 1 u`; keys are then reported as `CSI number ; modifiers u` with a modifier bitfield (shift/alt/ctrl/super/hyper/meta/caps/num-lock) and progressive-enhancement flags (disambiguate, report event types incl. release/repeat, alternate/shifted-key reporting, associated-text). **This directly matters for §14**: if swiftemacs wants Emacs-style chords (e.g. `C-c C-c`) to reach the shell/TUI program unambiguously (and shell-side programs like fzf/vim inside the terminal pane to receive unambiguous key-up/modifier info), implementing the kitty keyboard protocol on the "terminal grid" side is strictly better than legacy xterm key encoding, and Ghostty/kitty/WezTerm already treat it as the modern baseline.
- **24-bit color**: `ESC [ 38;2;r;g;b m` (foreground) / `48;2;r;g;b` (background), universally supported by all terminals surveyed here; no design risk, just implement it alongside 256-color and 16-color fallback.

## 12. Emacs-side patterns (comint, shell-command, compile, eshell, vterm, eat) [confidence: high — fetched GNU Emacs manual, akermu/emacs-libvterm README, and codeberg akib/emacs-eat]

| Package | Model | Editable buffer? | Full-screen TUI apps (vim/htop)? | Notes |
|---|---|---|---|---|
| **comint.el / shell-mode** (confirmed, gnu.org manual) | Line-oriented I/O to a subprocess; a `process-mark` tracks where unsent input begins | **Yes** — a fully normal Emacs buffer; cursor can move anywhere, prior commands can be edited/resubmitted (`C-c C-a`, `M-p`/`M-n` history) | No — no VT emulation, so curses/full-screen programs render garbled escape codes | Foundation for `M-x compile`, `M-x shell-command`/`M-!`, `M-x eshell`'s subprocess plumbing; `compile.el` layers `compilation-error-regexp-alist` over comint/process output to jump to source, the direct ancestor of "semantic history"/iTerm2 triggers (§1). |
| **eshell** | Elisp-native shell, not a real subprocess-attached PTY for its own command loop (spawns real processes for external commands but its own line editing/globbing/pipes are pure Elisp) | Yes | No | Cannot run interactive full-screen programs at all without a helper (traditionally shelled out or, more recently, delegated to eat's `eat-eshell-visual-command-mode`). |
| **vterm** (confirmed, akermu/emacs-libvterm) | Wraps the C **libvterm** library via a compiled Emacs dynamic module; genuine VT/xterm emulation | **No** — described by its own docs as "not a normal buffer"; cursor addressing and screen redraw are libvterm's, not Emacs'; keys go to the shell, not Emacs editing commands, by default | **Yes** — "like using Gnome Terminal inside Emacs," handles vim/htop/tmux fine | Fast (C core) but the buffer/editing-command tradeoff is exactly the tension the brief wants swiftemacs to resolve better; also not evil-mode compatible, requires module support, no Windows. |
| **eat** (confirmed, codeberg.org/akib/emacs-eat) | Pure Emacs Lisp VT emulator (no C dependency) | Depends on mode: **semi-char mode** (default, most keys forwarded to the shell but Emacs prefix keys like `C-x`/`C-c` reserved for Emacs), **char mode** (nearly everything forwarded), **line mode** (comint-like, editable before send) | Yes, in semi-char/char mode | ~3x faster than `term.el`, ~1.5x slower than vterm despite being pure Elisp; its **multi-mode input dispatch (semi-char/char/line)** is the single closest existing prior art for swiftemacs' §14 keybinding-coexistence problem, and is pure Elisp so its exact mode-switching logic could be a direct design reference (or even a porting source of *ideas*, not code, since eat is Elisp not Swift). |

- Cross-cutting insight: **every existing Emacs terminal solution trades off "real terminal emulation" against "normal editable buffer"** — comint/eshell pick editable-buffer-and-no-real-TTY, vterm picks real-TTY-and-non-editable, eat is the only one that tries to have both via **modal input dispatch**. swiftemacs, being a from-scratch Swift app rather than bolting onto 40-year-old Emacs internals, does not have to make this tradeoff at all if the terminal grid is designed as real buffer text from day one (§8, §14) — this is the single biggest opportunity identified in this research pass.

## 13. Recommendation: own VT engine vs SwiftTerm vs libghostty [confidence: high on facts cited above; the recommendation itself is a judgment call, flagged as such]

| Option | License | Language fit | Maintenance risk | Feature completeness today | Integration effort |
|---|---|---|---|---|---|
| **Own VT engine in Swift** | N/A (owned) | Perfect — no FFI, no build toolchain beyond Swift/Xcode, full control of threading model and buffer integration (§8) | All on swiftemacs | Starts at zero; the Williams parser (§6) is small and well-specified, but full xterm-compatibility (hundreds of DECSET modes, terminfo quirks, edge cases real-world programs depend on) takes years to reach parity (iTerm2/xterm/kitty have a decade+ of bug-driven refinement) | High effort, but *fully* aligned with the "terminal grid = buffer text" design (§8/§14) since there's no foreign data model to bridge |
| **Embed SwiftTerm** | MIT | Native Swift, no FFI/build-toolchain risk | Medium — small maintainer base relative to a full terminal project, but MIT lets swiftemacs fork/vendor and self-maintain if abandoned | High — already implements Sixel/iTerm2/Kitty images, hyperlinks, mouse, 24-bit color, grapheme clusters, bidi; proven in production-adjacent apps (CodeEdit, Secure Shellfish, La Terminal) | Low-medium — but SwiftTerm owns its own `Terminal`/buffer model (a grid, not an Emacs buffer), so achieving "terminal output is real editable buffer text" requires either (a) using SwiftTerm only for the VT *parsing/state* and building swiftemacs' own buffer-backed rendering on top (partially defeating the "just embed it" simplicity), or (b) accepting SwiftTerm's `TerminalView` as a separate, non-buffer widget for full-screen/alt-screen programs while your own buffer handles scrollback (a hybrid, matching §8's grid-overlay idea) |
| **Embed libghostty (C ABI)** | MIT | Requires Swift↔C interop (straightforward, Swift has first-class C interop) plus vendoring a Zig-built library into a SwiftPM build graph (**unverified** packaging maturity — see §2) | Medium-high — Ghostty itself is younger than SwiftTerm and led by one primary maintainer's organization; the C ABI is explicitly designed for embedding which is a good sign, but the *build toolchain risk* (needing Zig in the build pipeline, or a prebuilt binary artifact) is a real and somewhat novel risk for a Swift-only project | Very high — best-in-class parser (SIMD), Metal renderer already built, kitty graphics+keyboard protocol, synchronized rendering | Medium-high — gains a complete, high-performance terminal *surface* (including its own renderer) but that pulls swiftemacs toward "host a Ghostty surface in a window" rather than "terminal output is Emacs buffer text," which cuts against the brief's explicit differentiator; also means shipping/maintaining a Zig toolchain dependency in a Swift project, adding real build/CI complexity |

**Recommendation (judgment call, not a fetched fact)**:
- **must**: Do **not** adopt libghostty for v1. Its embedding model treats the terminal as an opaque rendered surface (§2's API is `draw`/`key`/`mouse`, not "give me structured cell/attribute data for my own buffer"), which works against the core differentiator the owner asked for (terminal output as real, editable, searchable Emacs buffer text, per §8/§12's insight that Emacs' existing tools force an editable-buffer-vs-real-TTY tradeoff that swiftemacs shouldn't inherit). It also adds a Zig build dependency to an otherwise pure-Swift/Xcode project, a real CI/toolchain cost given how new that packaging path is (unverified maturity, §2). Reconsider only if a future milestone specifically wants Ghostty-grade Kitty-graphics/GPU-shading fidelity for a *dedicated* full-screen terminal mode.
- **must**: Write the VT parser (Williams state machine, §6) as **native Swift code**, regardless of which path is chosen for the rest — it's small, foundational, and needs to sit directly on top of the buffer-backed cell model (§8) for the buffer-text design to work at all.
- **should**: Use **SwiftTerm** (MIT) as the initial reference/fallback implementation for full VT/xterm *semantic* correctness (DECSET modes, OSC parsing edge cases, image protocol decoding) — either by vendoring it directly for a v1 "alt-screen/full-cursor-addressing" grid-overlay mode (§8's hybrid design: plain scrollback is swiftemacs' own buffer text; only the alternate-screen region for vim/htop/tmux uses a SwiftTerm-backed grid view), or by reading its source as a design/porting reference while writing an equivalent Swift engine whose cell model is buffer-native from the start. Given the "extreme performance/no plugin architecture regressions" priority in the brief, **prototype both early** (a 1-2 week spike: SwiftTerm-in-a-pane vs a minimal own-engine buffer-backed prototype) before committing, since the buffer-text differentiator is high-value enough to justify some throwaway spike cost.
- **could**: If SwiftTerm's alt-screen `TerminalView` proves good enough and its maintenance risk (medium, small team) is judged acceptable, skip writing an own engine's alt-screen path entirely and only build the scrollback-as-buffer path natively — this is the pragmatic "80% of the value, 30% of the effort" option.

## 14. Design: terminal grid + editor buffer coexistence, keybinding coexistence [confidence: this section is original synthesis/design proposal, not a fetched fact — treat as a recommendation]

**Data model** (builds on §8's hybrid): a terminal pane is a normal swiftemacs buffer (same gap-buffer/rope, same undo, same `isearch`, same kill-ring as any file buffer) with:
- A `process-mark`-equivalent (a buffer marker) at the boundary between "committed" text and "live" text, exactly like comint.
- SGR color/attribute spans stored as text properties (like `ansi-color.el` computes today, but applied live token-by-token as the VT parser emits styled runs, not via post-hoc regex).
- Prompt/command-boundary markers derived from OSC 133 (§9) stored as overlays, giving "jump to next/previous prompt," "select last command's output," and (per Warp's insight, §4) optionally collapsible per-command regions — all as native Emacs overlay/marker operations, which is strictly more powerful than iTerm2's mark UI since Elisp can compose over it (e.g. a `compile.el`-style error-regexp scan restricted to the last command's output region).
- When the child program enables the alternate screen (DECSET 1049, used by vim/htop/tmux/less), swiftemacs switches that buffer's live region into a **grid-overlay mode**: a fixed-size, in-place-updated cell matrix (own engine or a vendored SwiftTerm `TerminalView`, §13) rendered where the buffer text would be, since alt-screen content is inherently non-linear/redrawn and doesn't want to be literal appended buffer text. On DECSET 1049 reset (program exits), collapse back to plain buffer text.

**Keybinding coexistence** (the concrete mechanism the brief asks for): follow **eat.el's proven three-mode model** (§12), reimplemented natively rather than ported line-for-line:
1. **Semi-char / "shell-focused" mode** (default when the terminal pane has real subprocess focus and no alt-screen program is running): most keystrokes are forwarded byte-for-byte to the PTY (so shell line-editing, readline/zsh bindings, arrow-key history work exactly like a real terminal), **except** a small, user-configurable reserved set of Emacs chords (by default things like `C-x` prefix, `C-h`, and whatever the user's `swiftemacs-terminal-escape-keys` list contains) which are intercepted by Emacs first — mirroring eat's default reservation of `C-\`, `C-c`, `C-x`.
2. **Full passthrough / "char" mode**: an explicit toggle (analogous to `eat-char-mode` or vterm's copy-mode toggle) for when the user is running a full-screen TUI program that wants every key (vim, htop, tmux) — in this mode nearly all keys including the kitty-keyboard-protocol-negotiated (§11) unambiguous encodings go straight through, with only one guaranteed "panic" escape hatch chord to get back to Emacs (e.g. a double-tap or a dedicated function key, since `C-x`/`C-c` etc. are legitimately needed by vim/tmux inside).
3. **Buffer/edit mode**: whenever the live PTY isn't focused for input (user clicked into scrollback, or is search/selecting), the pane behaves as a completely normal read/editable Emacs buffer with zero forwarding — this is the mode that makes "copy output into another buffer," "jump to error," and normal `isearch`/`occur` just work without any terminal-specific "copy mode" (directly obviating iTerm2's copy mode and instant replay UI, §1, since the scrollback *is* real buffer text with real undo/search).
- Mode indication should be a mode-line/cursor-shape/border-color signal (comparable to evil-mode's state indicator) so the user always knows whether keys go to the shell or to Emacs — this is the most common source of confusion in eat/vterm today and worth getting right visually from day one.
- This design directly satisfies the brief's explicit ask (terminal-as-editor with M-!, shell-command, compile, and iTerm2-class shell use in the same window) without requiring the user to pick "TUI-in-a-window" vs "GUI-editor" — the pane is simultaneously both, depending on mode.
