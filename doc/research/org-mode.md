## 1. Org syntax spec and org-element parser design

**Source: orgmode.org/worg/dev/org-syntax.html (confidence: high — primary spec, fetched directly)**

- Document = optional "zeroth section" (content before first heading) + a tree of headings/sections.
- Headline grammar: `STARS KEYWORD PRIORITY COMMENT TITLE TAGS`
  - Stars: 1+ `*` = depth.
  - TODO keyword: member of `org-todo-keywords-1` (flattened union of all sequences).
  - Priority: `[#A]`..`[#Z]` or `[#0]`..`[#64]` (single letter/number cookie).
  - COMMENT: literal token right after priority marks the subtree as a comment (excluded from export).
  - Tags: colon-delimited, alphanumeric + `_@#%`, right-aligned in Emacs display.
- Element taxonomy (three tiers): **headings/sections** (widest) → **greater elements** (can contain other elements: blocks, drawers, lists, tables, footnote-definition, headline, inlinetask, item, plain-list, property-drawer, section, table, org-data) → **lesser/elements** (paragraph, keyword, comment, fixed-width, etc., cannot nest) → **objects** (smallest scope, live inside paragraphs: bold, link, timestamp, footnote-reference, entity, latex-fragment, macro, statistics-cookie, etc.).
  - Confirmed directly against Emacs 30.2's `org-element.el` at runtime (confidence: high, local probe `emacs -Q --batch`, 2026-09-05):
    - `org-element-all-elements` = babel-call, center-block, clock, comment, comment-block, diary-sexp, drawer, dynamic-block, example-block, export-block, fixed-width, footnote-definition, headline, horizontal-rule, inlinetask, item, keyword, latex-environment, node-property, paragraph, plain-list, planning, property-drawer, quote-block, section, special-block, src-block, table, table-row, verse-block.
    - `org-element-all-objects` = bold, citation, citation-reference, code, entity, export-snippet, footnote-reference, inline-babel-call, inline-src-block, italic, line-break, latex-fragment, link, macro, radio-target, statistics-cookie, strike-through, subscript, superscript, table-cell, target, timestamp, underline, verbatim.
    - `org-element-greater-elements` = center-block, drawer, dynamic-block, footnote-definition, headline, inlinetask, item, plain-list, property-drawer, quote-block, section, special-block, table, org-data.
    - Local Emacs version: org 9.7.11 bundled with Emacs 30.2.
    - Local probe also confirmed `org-todo-keywords` default `((sequence "TODO" "DONE"))` and priority char codes: `org-priority-highest`=65 (`A`), `org-priority-lowest`=67 (`C`), `org-default-priority`=66 (`B`) — i.e. priorities are plain ASCII char codes internally, sorted `A < B < C` alphabetically = highest→lowest.
- Timestamps: active `<Y-M-D DAY HH:MM>`, inactive `[Y-M-D DAY HH:MM]`, ranges with `--`, diary `%%(SEXP)`, repeaters `+1d`/`++1w`/`.+1m`, warning delays `-2d`. Scheduling/deadline lines are "planning" elements (context-free, always right under a headline).
- Drawers: `:NAME:` ... `:END:`; property drawers are a specific drawer named `:PROPERTIES:` holding `:KEY: value` node-properties, must appear immediately after a headline (or in the zeroth section) — this is a **context-free** element per spec.
- Tables: pipe-delimited `|a|b|`; a row of `|-...-|` is a rule; `#+TBLFM:` lines hold spreadsheet formulas (formula language and evaluation are a separate subsystem, org-table.el's `calc`-based engine — not covered by org-syntax.html; treat as its own component).
- Lists: bullets `*`/`-`/`+`, ordered `1.`/`1)`, optional `[@N]` counter reset, optional checkbox `[ ]`/`[X]`/`[-]`, optional descriptive tag `term ::` — indentation-sensitive nesting.
- **Parser design note from the spec itself (high confidence, verbatim intent)**: most elements are *context-dependent* — only headlines, sections, property drawers, and planning lines are context-free. This is why `org-element-at-point` in real Org is documented to walk up to the parent heading and re-parse top-down to locate the element at point precisely, rather than parsing bottom-up from arbitrary buffer position. **Design implication for pellicle**: a robust org-element-equivalent parser should be structured as (a) a fast headline/section skeleton scan (cheap, regex-like, defines a tree of ranges) plus (b) on-demand recursive-descent parsing of a section's contents when that section is displayed/queried/exported, rather than one flat single-pass tokenizer. This naturally supports incremental re-parse: edits inside one section only invalidate that section's element cache, not the whole buffer's.
- org-element.el's actual public parsing entry points to emulate: `org-element-parse-buffer` (full AST), `org-element-at-point` (element containing point, coarse), `org-element-context` (object containing point, fine-grained, descends into objects), `org-element-cache` (a buffer-local cache of parsed elements keyed by position, invalidated on edit via markers) — the cache is what makes interactive Org usable on large files; confidence medium (from general Org knowledge / not re-fetched from source this run, but consistent with the spec's context-dependent parsing note and widely documented behavior).

## 2. Essential features, ranked, and how Emacs implements them (confidence: high for behavior, medium for exact internal mechanism where not re-verified this run)

Ranking rationale: tier 1 = unusable as "org-mode" without it (basic outliner/PIM daily-driver level); tier 2 = what makes Org distinctive vs. a generic Markdown outliner; tier 3 = power-user / integration features that a large fraction of long-time users rely on but a v1 can launch without.

**Tier 1 — table-stakes outliner**
- Headlines + folding/visibility cycling (`TAB`/`S-TAB`, `org-cycle`, global `org-shifttab`): built on Emacs's invisible-text-property overlays; Reticle's own `org.el` already replicates this via its own invisible-region primitive (see section 8).
- TODO keywords + custom sequences (`#+TODO: TODO(t) | DONE(d)`, multi-sequence with `|` separating "active" vs "done" states, fast-select keys in parens).
- Priorities `[#A]-[#C]` (extendable to `[#0]-[#64]`), cycling via `org-priority`.
- Tags (`:tag1:tag2:`) with **inheritance** from parent headlines and file-level `#+FILETAGS:`; tag search/matching supports boolean queries.
- Timestamps: plain, SCHEDULED/DEADLINE planning lines, repeaters (`+1d`, `++1w`, `.+1m`), warning periods (`-3d`).
- Plain lists with checkboxes `[ ]/[X]/[-]`, and checkbox statistics cookies `[2/5]`/`[40%]` that auto-update.

**Tier 2 — what makes it "Org" rather than a folding outliner**
- Agenda views: a cross-file aggregation (`org-agenda-files`) producing day/week task+timestamp views, powered by scanning planning lines and TODO states across all agenda files — this is the single most performance-sensitive feature at scale (see index design, section 5).
- Capture templates (`org-capture`): a keystroke-driven quick-entry system that inserts a templated entry into a target file/headline; heavily used for GTD-style inboxes — directly relevant since the owner also runs a GTD web app ("orgtd").
- Refile (`org-refile`): move a subtree to another location/file with completion over headline paths; relies on the same target-file cache the agenda and capture systems use.
- Archiving (`org-archive-subtree`): move a done subtree to a sibling `*.org_archive` file or an `:ARCHIVE:` target, preserving properties.
- Clocking (`org-clock-in/out`) and Effort estimates (`:EFFORT:` property) — time tracking integrated with agenda's clock report.
- Tables with spreadsheet formulas (`org-table`, `#+TBLFM:` lines, Calc-based formula language) — a full mini-spreadsheet engine; non-trivial subsystem on its own.
- Links (`[[target][desc]]`), internal (`*Heading`, `#custom-id`, `(coderef)`), and file/http/id/attachment link types, each with its own "follow" handler — an extensible link-type registry (`org-link-set-parameters`).
- Property drawers + inheritance for structured metadata (used heavily by agenda column view and org-roam-like tools).
- Footnotes (`[fn:1]` inline or as a separate `[fn:1] definition` block).

**Tier 3 — power-user / integration**
- org-babel: fenced `#+begin_src lang ... #+end_src` blocks, executable per-language, with `:tangle` to extract to source files, `:noweb` for block transclusion, results captured back into the buffer. This is effectively "embed a REPL/build system in the document" — large scope, many language backends in real Org.
- Export (`ox-*`): a backend-pluggable exporter walking the `org-element` AST to HTML/LaTeX(→PDF)/Markdown/ODT/etc. Architecturally this is the strongest argument for building a real AST parser (org-element-equivalent) rather than a line-oriented renderer, since export needs structural traversal, not just fontification.
- org-roam / denote-style backlinks: Zettelkasten-style ID-based linking with a SQLite (`emacsql`) cache mapping IDs → files/positions and links → backlinks (confirmed: org-roam depends on `emacsql`, medium confidence on exact schema, not fetched from source this run).
- Inline image and LaTeX fragment preview (rendered in-buffer as overlays replacing the source text region).
- org-modern-style visual polish: pill-shaped tag rendering, bulleted/iconified headline stars, bordered tables/blocks, all achieved via text properties/overlays over the real text, never mutating the underlying file content (confidence: high, fetched from org-modern README).
- Mobile sync (MobileOrg-style, now largely superseded by orgzly/organice + git or WebDAV sync).

**Cross-cutting lesson (high confidence, triangulated from 3 independent sources — org-syntax.html itself, tree-sitter-org's README, orgize/organice's design notes):** every serious non-Emacs Org implementation converges on the same two facts: (1) a rigid context-free grammar (tree-sitter or similar) **cannot** exactly reproduce Org's context-dependent parsing rules, so full Emacs-fidelity requires either porting org-element.el's actual algorithm (uniorg's approach) or accepting known edge-case divergence (tree-sitter-org's approach); (2) **roundtrip/lossless fidelity is treated as a first-class requirement**, not a nice-to-have, by every project that lets users edit and save real Org files (orgize's rowan tree, organice's "no unrelated diffs" goal) — because Org files are usually the user's only copy of years of notes, corrupting formatting on save is the single most trust-destroying bug class.

## 4. Recommended parser architecture for pellicle (recommendation, not a citation — synthesized from sections 1 and 3)

**Recommendation: hand-written recursive-descent parser producing a lossless (rowan/red-green-style) syntax tree, structured as a cheap skeleton pass + lazy per-section deep parse. Do NOT use tree-sitter-org as the primary/only parser.**

Reasoning, tagged must/should/could:

- **must** — build a lossless tree (every source byte reconstructable from the tree, à la orgize's rowan tree and organice's "no unrelated diffs" goal). This is non-negotiable given Org files are irreplaceable personal data; a parser that reformats on save will destroy user trust immediately (this is the single most consistent lesson across every surveyed implementation, high confidence).
- **must** — implement the two-tier structure the org-syntax.html spec itself implies: (1) a fast, context-free skeleton scan that only needs to find headline/section/property-drawer/planning-line boundaries (cheap, can run on every keystroke or via incremental re-scan of the touched region only); (2) on-demand recursive-descent parsing of a section's *contents* (paragraphs, lists, tables, blocks, objects) only when that section is actually rendered, folded open, exported, or babel-executed. This mirrors Emacs's own `org-element-cache` behavior and is what makes both editors usable on 10k+ line files.
- **should** — do not adopt tree-sitter-org as the org-element replacement. Its own README concedes it cannot reproduce Org's context-dependent grammar exactly, which is precisely the correctness property pellicle should not compromise on for a "solve every Emacs pain point" flagship feature. It could still be *useful* as a fallback/quick fontifier for the very first milestone (fast, well-tested, gets folding+highlighting working in days), to be replaced by the hand-written parser as the deep AST/export/babel layers come online — this is a **could**, an acceptable bootstrapping shortcut, not the end-state.
- **should** — model the element/object taxonomy directly on org-element.el's own three-tier design (greater-elements / elements / objects, confirmed via the local Emacs 30.2 probe in section 1) rather than inventing a new taxonomy — this maximizes the odds that ox-export-equivalent code and org-roam-equivalent tooling can be ported/adapted later with the same conceptual model third-party Emacs packages already assume.
- **could** — expose the AST through a stable, versioned public API from day one (unlike orgize's explicitly-unstable low-level tree) if pellicle intends a plugin ecosystem that reads Org structure (agenda-like or roam-like plugins) — cheap to design in now, expensive to retrofit later.

## 5. Project-wide org index design (agenda/refile/ID lookup)

**must** — a persistent, incrementally-updated index is required; scanning every `org-agenda-files` file on every agenda open (the naive approach) is the most commonly cited real-Emacs org performance complaint (general knowledge, medium confidence — not independently re-verified via a benchmark source this run, but consistent with why org-roam and org-element-cache both exist as caching layers).

Recommended shape, informed directly by org-roam's confirmed design (depends on `emacsql`/SQLite, confidence high — fetched from README) and Reticle's own document that its GC root-set / overlay work had to solve very similar "don't rescan everything on every edit" problems (section 8):

- **must** — one on-disk index (SQLite via Apple's own SQLite3 C API or a Swift wrapper, no third-party dependency needed since SQLite ships with macOS) keyed by file path + mtime/hash, storing per-file: headline positions + levels, TODO state, priority, tags (including a materialized inherited-tags column so agenda/tag search doesn't need to walk the tree at query time), planning timestamps (SCHEDULED/DEADLINE/plain), `:ID:` properties, and link targets/sources (for backlinks).
- **must** — incremental update on save/edit: re-index only the changed file (or, for very large files, only the changed subtree using the section-level parse boundaries from section 4), not a full-workspace rescan. This is the same lesson Reticle learned the hard way with its overlay O(L²) bug (section 8) — anything that's O(file count × file size) on every keystroke or every agenda open will not scale and will visibly degrade the longer the app runs, which directly violates the owner's "must not get slower/hotter the longer it runs" requirement.
- **should** — separate the "fast path" queries (agenda: all TODOs + timestamps in a date range across N files; refile: headline-path completion; ID lookup: `:ID:` → file+position) as indexed SQL queries rather than in-memory tree walks once file count grows past a few hundred — but for a v1 targeting one user's vault, an in-memory index rebuilt incrementally (no SQLite yet) is a legitimate **could**-defer if it measurably keeps agenda-open latency low; promote to SQLite when profiling shows otherwise.
- **should** — the index is also the natural backing store for org-roam/denote-style backlinks (a `links` table: source file+id, target id/file, link type) — build this in the same index rather than as a bolt-on second subsystem, since org-roam itself is architecturally "org files + a link/ID cache," not a separate data model.

## 6. Recommended milestone ordering (recommendation, informed by Reticle's own ordering in section 8 and the tier ranking in section 2)

Given org-mode is explicitly **priority 2, after Verilog/coding features** (owner's stated ordering) and that the owner already has a separate GTD web app (orgtd) covering some task-management needs, the recommendation is to sequence org-mode's own internal milestones so that **file-format-compatible editing ships long before agenda/babel/export**, mirroring Reticle's own "Approach B" decision (section 8) which the owner apparently found sound enough to keep (Reticle explicitly deferred agenda/babel and it is not recorded as a regretted decision in PLAN.md).

1. **must, M-org-1 (core outliner)**: skeleton parser (section 4), headline folding/visibility cycling, TODO keyword cycling with custom sequences, priorities, tags with inheritance, plain lists + checkboxes with auto-updating statistics cookies, basic timestamp insertion/display, syntax highlighting (fontification) — full read/write file-format compatibility with real Org from day one, verified by round-tripping real `.org` files byte-for-byte on no-op open/save.
2. **must, M-org-2 (structure + tables + links)**: property drawers with inheritance, tables (alignment + at least basic `#+TBLFM` arithmetic — full Calc-equivalent formula language can be a should/could split, see below), links (internal + file + http, extensible link-type registry), footnotes, SCHEDULED/DEADLINE planning lines with repeaters.
3. **should, M-org-3 (index + single-user agenda/capture/refile)**: the project-wide index (section 5), a single-file-vault agenda view, capture templates, refile, archiving — this is the point where pellicle starts overlapping functionally with orgtd, so the owner should decide at this milestone how much duplicate GTD logic they actually want in the editor vs. treating orgtd as the "real" GTD system and pellicle's agenda as a lightweight complement.
4. **should, M-org-4 (visual polish)**: org-modern-style rendering — pill tags, headline bullets/iconography, bordered tables/blocks, inline image and LaTeX fragment preview — all via non-destructive overlays/text-attributes over the real text (never mutating file content), consistent with the "extreme visual beauty" goal being priority 3 overall but cheap to layer onto an already-correct parser.
5. **could, M-org-5 (babel + export)**: source block execution/tangling/noweb, export backends (HTML first, then LaTeX/PDF/Markdown) — largest remaining scope item; **recommend deferring past v1** (see section 7) unless the owner's actual daily workflow depends on babel/export, which was not stated in the brief.
6. **could, M-org-6 (roam/backlinks + mobile sync)**: ID-based backlinks reusing the section-5 index; mobile/remote sync is **low priority** given the app is explicitly macOS-only for now and the owner did not mention a phone workflow.

## 7. What to defer (explicit recommendation)

- **defer past v1**: org-babel execution for anything beyond maybe a single "run this shell/python block" convenience — full noweb+tangle+multi-language babel is one of the largest subsystems in real Org and orthogonal to "killer coding features for Verilog" (priority 1) or basic org file editing (priority 2's core ask).
- **defer past v1**: full ox-export backend matrix. If any export is wanted early, HTML alone (simplest AST walk, no external toolchain) is a reasonable **could** for M-org-4/5; LaTeX/PDF export depends on an external TeX toolchain the owner hasn't mentioned having, and Markdown export is comparatively cheap once the AST exists.
- **defer past v1**: the full Calc-based table formula language; ship alignment + simple arithmetic sums first (many users' actual usage is `#+TBLFM: $3=$1+$2` style, not full Calc).
- **defer past v1**: mobile sync (MobileOrg/orgzly/organice-equivalent) — out of scope for a macOS-only v1 per the owner's own environment brief.
- **defer, needs an explicit owner decision, do not build silently**: how much agenda/capture/refile logic to duplicate given the owner's separate orgtd GTD web app already exists — building a second, weaker GTD system inside the editor risks wasted effort; a thinner "open today's agenda / jump to a headline" viewer that *complements* orgtd may be enough. This is flagged as a scope question, not resolved here.

## 8. Reticle's prior org-mode work (local source, confidence high — read directly)

No agenda, capture, refile, clocking, property-drawer, footnote, or babel code found in this file — consistent with PLAN.md's stated scope.
- Reticle's own performance history with org files (PLAN.md ~lines 1490-1592, read directly) is a directly relevant cautionary tale: org fontification's real bottleneck turned out **not** to be regex/string search but **O(L²) overlay bookkeeping** (linear-scan `overlays-in` + `delete-overlay` on every line), measured at 60k lines / 20k lines scaling 6.1x (worse than linear) before the fix, and 2.68x (better than linear) after switching to a sorted-overlay-by-start-position structure with binary-search insertion/lookup and a running prefix-max-end for early-stopping range queries (616ms → 131.8ms on a 60k-line file; per-overlay-query microbenchmark 5.2µs → 519ns). **Direct lesson for pellicle**: whatever overlay/decoration data structure backs org folding + highlighting must be designed for O(log n) or better insert/query from the start, not retrofitted after a large-file performance complaint — this is exactly the kind of "gets slower/hotter the longer files get" failure mode the owner's brief explicitly wants solved, not merely avoided by luck.
- Reticle's M5.5 milestone framed org-mode as **"also a real-world validation of elisp extensibility"** — i.e. org-mode's implementation doubled as the integration test for the embedded Lisp/extension system. If pellicle keeps an embedded Elisp interpreter (per the owner's brief), the same dual-purpose framing is worth reusing: implement core org-mode as an extension/plugin exercising the real extension API, not as privileged built-in-only code, to prove the extension system works for something non-trivial from day one.
